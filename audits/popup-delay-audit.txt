4. Any timeout on these fetch calls?
====================================================================
No. Neither fetchPopupConfig() nor fetchDiscountConfig() sets any
client-side timeout, deadline, or AbortController on its fetch() call
-- a plain `fetch(url).then(...).then(...).catch(...)` chain in both
cases, with no `signal` option passed to fetch() and no
setTimeout/clearTimeout anywhere in either function body.

A file-wide search for "AbortController" (case-insensitive) and
"timeout" turned up no AbortController usage anywhere in this file,
and exactly one unrelated timeout construct: a service-worker
"activated" wait inside the push-subscription setup code (lines
1720-1726), which has nothing to do with either config fetch:

Practical consequence: if the App Proxy / backend is slow to respond
(cold start, network issue, etc.), fetch() will wait as long as the
browser's own default fetch timeout allows (typically very long / no
enforced ceiling in most browsers) before either resolving or the
underlying network layer itself gives up. Since start()'s
Promise.all() (section above) gates initIntentTriggers() on BOTH
promises settling, a slow/hanging config fetch directly delays -- or,
in the worst case (a fetch that never settles at the network layer),
indefinitely blocks -- every soft-prompt trigger and the product-page
discount nudge for that entire page load. Both functions' own
.catch() blocks only run on an actual fetch rejection (e.g. a network
error) or a thrown error in the .then() chain -- they do not create a
timeout of their own, so a fetch that is merely SLOW (not erroring)
has nothing forcing it to give up early.
