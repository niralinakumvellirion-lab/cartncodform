1. IS payload ALREADY RETURNED BY THE ENDPOINT?
─────────────────────────────────────────────────────────────────────────────
Yes. The endpoint at profiles.js:96–98 selects:

  'profileId signalType channel payload status runAt reason
   cartToken sentAt createdAt updatedAt'

`payload` is the entire Mixed field — every sub-key comes through:
  payload.title       ← push notification title
  payload.body        ← push body OR email body
  payload.subject     ← email subject (brain email jobs)
  payload.imageUrl    ← push hero image (festival/manual; '' for brain)
  payload.url         ← push click destination

All of these are already in every `m` object in component state. No
backend change is needed to add fields.

SIDE FINDING (out of scope but worth noting): `outcome` is NOT in the
.select() list. This means m.outcome is undefined for every row, so
getStatusConfig() always falls through to the "delivered" / status-name
default — "clicked" and "converted" badges on the Messages screen never
actually render. This is a pre-existing bug separate from the preview task.

4. INTERACTION: INLINE EXPAND vs MODAL vs SIDE PANEL
─────────────────────────────────────────────────────────────────────────────
Current row structure (desktop): display:grid with 5 fixed columns
(line 527: '110px 180px 24px 1fr auto'). No existing expand/detail
interaction anywhere in the component.

Options:
  A. Inline expand — row expands below grid row on click.
     Pro: stays in-context. Con: `display:grid` makes this fiddly —
     an expanded section can't span columns inside a flat grid children
     list without resetting to block layout per-item. Requires wrapping
     each row in a container, restructuring the current flat map().

  B. Modal — click row → modal overlay with preview.
     Pro: zero layout disruption, one new state variable (expandedId),
     trivial to close. Standard Shopify/Polaris pattern for row details.
     Con: slightly less "in context" than inline, but fine for a preview.

  C. Side drawer/panel — slide in from right.
     Pro: modern UX, doesn't lose list position. Con: most code of the
     three; no existing drawer component in the codebase.

RECOMMENDATION: Modal (B).
  Rationale: the flat grid layout makes inline expand structurally
  expensive (map() must emit a wrapper + two children instead of one
  flat child; mobile branch would also need to change). A modal adds
  ~30 lines: `const [preview, setPreview] = useState(null)` + a
  single `onClick` prop on each row + a conditional modal div at the
  bottom of the return. The grid rows are untouched. This matches how
  Polaris admin apps handle detail views, and it fits the existing
  screen structure with minimal change.
  Implementation note: make the whole row `cursor: pointer` + on click
  set `preview = m`. Modal renders as a fixed overlay with the
  notification card inside, matching the push/email shape above.

5. EMAIL vs PUSH PREVIEW SHAPE
─────────────────────────────────────────────────────────────────────────────
Push:  title (bold) + body (text) + imageUrl (optional image) + url
       All four are in payload for every push row.
       imageUrl is '' for brain jobs; may be set for festival/manual.

Email: subject (bold "Subject:" line) + body (text, preserve \n)
       Both in payload for email rows. No imageUrl field.
       m.channel === 'email' distinguishes which shape to render.

Both shapes are derivable from data already in state. No new endpoint
field required.
