================================================================================
recordProfileMessage(job) is awaited (with a .catch that only logs) in BOTH
success branches of processScheduledJobs:
  - push:  after `[automation] Job <id> sent successfully`
  - email: after `[automation] Job <id> email sent successfully`
It is NOT called on the failed / skipped paths. It $push'es one entry
{channel: job.channel, type: job.signalType || 'manual', sentAt: now,

5. CONFIRM — send-time re-validation added to the poller
================================================================================
Immediately after `if (!claimed) continue;` (claim succeeded):
  if (job.profileId && job.runAt > new Date()) {
    await ScheduledJob.findByIdAndUpdate(job._id, { status: 'pending' });
    continue;
  }
Only brain jobs (job.profileId set) are re-validated; a future runAt releases
the claim back to 'pending' for a later tick. (The poll query already filters
runAt <= now, so this is a clock-skew / reschedule guard.)
Copy re-resolution at send time (re-check the signal is still true, ask AI for
copy) is Phase E — this phase only adds the runAt guard + message log.

9. NOTICED BUT NOT TOUCHED  (out of scope for Phase C)
================================================================================
- AutomationRule model, routes/automation.js, utils/automationEngine.js, and
  the old scheduleCartAbandonJobs -> ScheduledJob(ruleId) path in
  webhooks.js/handleWebhook are ALL still live. The handover says "Delete
  AutomationRule.steps editor and the trigger enum" in Phase C, but this prompt's
  STEP 9 only removed the ADMIN components and STEP 5 explicitly says the old
  poller still reads ScheduledJob's rule fields. So: model + trigger enum +
  backend automation code are untouched, still scheduling cart_abandon jobs in
  parallel with the brain. This means for a shop with an active AutomationRule,
  a cart can get BOTH an old rule job and a brain job. Flagged for a Phase C2 or
  the Phase G rebuild to fully retire.
- Brain-scheduled EMAIL jobs have no working send path yet. The poller's email
  branch looks up AbandonedCustomer by { shopDomain, sessionId: job.cartToken }
  and needs customer.email; a brain email job for a profile whose address lives
  only in Profile.channels.email.address (no matching abandoned-cart row) will
  hit `status:'skipped', error:'No customer email for this cart'`. Wiring the
  email sender to read the profile is Phase E (copy resolution) territory.
- Brain PUSH jobs reuse sendPushToCustomers(shopDomain, ..., cartToken) which
  targets by cartToken; a profile with a stale/rotated cartToken (or none) will
  not be reached even though channels.push.subscribed is true. A
  profile-/pushToken-targeted send path is needed (Phase E/F).
- computeRunAt: `profile.activeHours` is treated as a LIST of hour values whose
  mode is the preferred hour. Phase A never populates activeHours, so this
  branch is dead until a later phase writes it. If it is meant to be a
  fixed 24-length histogram, the "mode" logic needs to become argmax.
- Nightly job is still an in-process setTimeout (per the existing poller style);
  a sleeping free-tier dyno misses 02:00. Handover already flags this.
- No index build is forced; Mongo builds the new SignalConfig unique index and
  the two revised ScheduledJob partial indexes lazily. On an existing
  ScheduledJob collection the OLD partial index must be dropped and rebuilt for
  the `ruleId: {$type:'objectId'}` filter change to take effect — `syncIndexes()`
  or a manual drop is an owner deploy step.
- The 12 SignalConfig rows are never seeded; GET returns only rows that exist
  and the brain treats "no row" as enabled=true. The admin (Phase G) is
  expected to render all 12 with defaults filled client-side.
- STEP 5 snippet used `Schema.Types.ObjectId`; ScheduledJob.js uses
  `mongoose.Schema.Types.ObjectId` throughout, so the new fields match that.
