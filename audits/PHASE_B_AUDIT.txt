Orchestrator computeSignalsForProfile(profileId, shopDomain):
  loads Profile.findById; returns [] if missing or profile.suppressed; runs the
  10 live fns via Promise.all (each individually .catch'd -> null); upserts each
  non-null via Signal.findOneAndUpdate({shopDomain,profileId,type}, {$set:{...}},
  {upsert:true,new:true}); then Signal.deleteMany({shopDomain,profileId,
  type:{$nin: activeTypes}}); logs `[signals] profile <id>: <n> active`;
  returns the computed signal objects.

runNightlySignals(shopDomain): Profile.find({shopDomain, suppressed:{$ne:true}},
  '_id', {lean:true}); processes in batches of 100 (Promise.all within a batch,
  sequential between batches); logs `[signals] nightly run complete: N profiles
  processed`.

5. CONFIRM — nightly cron wired in server.js
================================================================================
scheduleNightlySignals() is defined and called once at module load, right after
the automation poller's setInterval. It computes ms until the next 02:00 local,
setTimeout's a run that loops every Store and awaits runNightlySignals, then
calls itself again to reschedule. A `[signals] Nightly signal job scheduled`
log line confirms wiring at boot.
(Note: this is an in-process timer, not a real cron — same pattern as the
existing 30s poller. It resets on every deploy/restart; fine for a single
Render instance. See open questions.)

8. NOTICED BUT NOT TOUCHED  (out of scope for Phase B)
================================================================================
- AbandonedCustomer has NO updatedAt field (no `timestamps:true`), so
  computeCartAbandon uses `createdAt` as the abandon clock. `createdAt` is set
  once on first sighting and NOT bumped by carts/update, so it effectively
  measures "cart first seen N minutes ago", not "last touched N minutes ago".
  For a long-lived cart the shopper could be active right now and still score
  cart_abandon. A real "last activity" needs either timestamps on
  AbandonedCustomer or a join to the newest StorefrontEvent / CPS.lastActivityAt.
  Flagged; not fixed (would be a model change).
- add_to_cart events store the added VARIANT id under `meta.productId` (a
  storefront-embed naming quirk — see push-notifications.liquid ~line 755),
  while product_view stores the real product id under `meta.productId` and the
  variant under `meta.variantId`. computePriceHesitation works around this by
  matching a candidate against {productId} ∪ {its seen variantIds}. Still
  best-effort; a shopper who added variant X of product P where X was never in
  a product_view meta would slip through.
- routes/events.js (raw /api/events ingest) still does NOT trigger
  computeSignalsForProfile — Phase B only wired the cart webhook (per STEP 5).
  Browse/high_intent/price_hesitation therefore only recompute on the next
  cart webhook or the nightly run, not the instant a product_view lands.
  Same open item carried from Phase A ("events.js has no profile touch").
- profileService.upsertProfile is unchanged — no orders/interests deep-merge
  was added (still a Phase A open question).
- The nightly job uses an in-process setTimeout (not node-cron / a real
  scheduler), matching the existing 30s poller style. On Render free tier the
  dyno can sleep and miss 02:00 entirely (the handover already flags "move off
  free tiers before the brain runs for real").
- No index build is forced for the new Signal collection; Mongo builds the
  unique + TTL + brain indexes lazily on first write.
- Signal.evidence is capped to 5 entries in sig(); the schema comment says
  "max 5" but there is no schema-level validator — enforced only in code.

9. OPEN QUESTIONS
================================================================================
1. cart_abandon recency — acceptable to use AbandonedCustomer.createdAt as the
   clock for now, or should Phase B add `timestamps:true` to AbandonedCustomer
   (a safe additive change) so "abandoned 60 min ago" means "not touched for
   60 min"? Recommend the model change early in Phase C.
2. Should the raw event ingest (routes/events.js POST /) also fire
   computeSignalsForProfile (needs a profile lookup by sessionId first)?
   STEP 5 only asked for the cart webhook. Browse-type signals are latency-
   sensitive for the Brain's real-time path in Phase C.
3. checkout_abandon "no order since" proxy = AbandonedCustomer.status ===
   'abandoned'. If a checkout is reached but no carts/* webhook ever created an
   AbandonedCustomer row (possible for a fast checkout), the signal never
   fires. Is a StorefrontEvent-only fallback (no reached_checkout followed by
   an orders/create for that session within 24h) wanted?
4. price_hesitation add_to_cart matching relies on the variant/product id
   overlap hack. Worth normalising add_to_cart.meta to carry the real
   product_id in the storefront embed (Phase D storefront rework)?
5. Nightly runner scans EVERY non-suppressed profile every night with no
   "changed since last run" filter. Fine at hundreds of profiles; at scale it
   should be bounded to profiles with recent activity (lastSeenAt within N
   days) or an updatedAt watermark.
6. computeSignalsForProfile returns the in-memory computed objects, not the
   persisted Signal docs. If a caller needs `_id` it must re-query. Acceptable?
