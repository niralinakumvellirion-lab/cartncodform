PART A - EXACT IMPLEMENTATION (backend/routes/profiles.js)
=========================================================================
Added directly after the today-stats endpoint, matching the task's
given code almost verbatim -- one fix was required:

DEVIATION - `.select(...)` string literal had an embedded line break.
The given code was:
    .select('identifiers channels.push channels.email
             lastSeenAt messages')
A single-quoted JS string cannot contain a literal newline -- this
would be a SyntaxError ("Invalid or unexpected token" /
"Unterminated string literal") the moment the file is loaded,
crashing the whole route module (and therefore the backend, since
profiles.js is required unconditionally by server.js). Collapsed onto
one line: `.select('identifiers channels.push channels.email
lastSeenAt messages')`. This is the same class of copy-paste line-wrap
artifact caught in earlier tasks this session (the Phase 4
ActivityScreen fetch URL, the journey-panel-layout Send-notification
card's template literal) -- clearly a formatting artifact from how the
task text was wrapped for display, not intended literal source.

Everything else implemented exactly as given: the 24h `since` window,
the push-subscribed + subscribedAt-in-range query, the .sort/.limit(50)/
.lean() chain, the in-memory filter excluding any profile with ANY
message (not just push) sent within the same 24h window, and the
response shape ({ count, subscribers: [{profileId, email,
subscribedAt, lastSeenAt}] }).


PART B - EXACT IMPLEMENTATION (backend/routes/push.js)
=========================================================================
Added directly after send-journey. One necessary fix, verified against
the real function signature before implementing (not guessed):

DEVIATION 1 - generateCopy() was called with the wrong argument shape.
The given code:
    const voice = {};
    const signal = { type: 'email_capture', strength: 0.5 };
    const { title, body } = await generateCopy(shop, signal, voice);
Read backend/services/aiService.js's actual generateCopy() definition
first: `async function generateCopy(store, signalType, product,
channel)` -- 4 positional params, not 3, and shaped very differently
from what the given code passes:
  - `store` must be an object exposing `.shopDomain` and `.voice`
    (used to build the cache key and the AI prompt) -- the given code
    passed the bare `shop` STRING in this position. A string's
    `.shopDomain`/`.voice` properties are both undefined, so
    `shopDomain` internally would resolve to `''` for every call --
    meaning the copy CACHE KEY (built from shopDomain + signalType +
    productId + channel + voiceHash) would be blank-shopDomain for
    every shop, opening a cross-tenant cache-collision risk (two
    different merchants' generated notification copy could hash to
    the same cache key and one shop could see another's generated
    text).
  - `signalType` must be a plain STRING (it's concatenated directly
    into the prompt text, e.g. `Signal: ${signalType}`, and into the
    cache key) -- the given code passed the OBJECT `{ type:
    'email_capture', strength: 0.5 }` in this position, which would
    stringify to the literal text "[object Object]" inside the AI
    prompt and corrupt the cache key.
  - `channel` ('push' or 'email') was not passed AT ALL in the given
    3-arg call -- it would be `undefined` inside generateCopy(),
    which controls BOTH which fallback copy is used
    (`channel === 'email' ? FALLBACK_EMAIL : FALLBACK_PUSH` -- always
    resolves to FALLBACK_PUSH when undefined) AND which JSON shape the
    prompt asks the AI to return (`channel === 'push' ? '{"title":
    ...}' : '{"subject":...}'` -- with channel undefined, ALWAYS asks
    for the EMAIL {subject,body} shape, never {title,body}, regardless
    of whether this was actually meant to be a push notification).
    Combined with the given code's own destructuring
    (`const { title, body } = ...`), a push-channel send-now call
    would silently end up with `title: ''` (FALLBACK_PUSH is never
    reached; the live-generated result's `title` stays empty since the
    prompt never asked the AI for one) -- an empty-title push
    notification going out to a real customer, every time.
  Fixed by building an actual `store`-shaped object
  (`{ shopDomain: shop, voice: {} }` -- kept `voice` empty, matching
  the given code's own apparent intent of not fetching the merchant's
  real voice config for this quick manual-send path, just nested where
  the function actually reads it from) and passing the plain string
  `'email_capture'` and the already-computed `channel` variable (see
  DEVIATION 2) as the 2nd/4th arguments:
    const { title, body, subject } = await generateCopy(store, 'email_capture', null, channel);
  Also captured `subject` (silently dropped by the given code's
  2-field destructure) and included it in the job's payload (see
  below) -- cheap, zero-risk, and matches what a channel:'email' job
  actually needs downstream.

DEVIATION 2 - `channel` computed once and reused, not recomputed.
The given code computed `profile.channels?.push?.subscribed ? 'push'
: 'email'` only once, inline inside the ScheduledJob.create() call
(for the job's own `channel` field) -- it was never available earlier
for the generateCopy() call itself (which needs it too, per DEVIATION
1). Hoisted this into a single `const channel = profile.channels
?.push?.subscribed ? 'push' : 'email';` right after loading `profile`,
reused for both the generateCopy() call and the ScheduledJob's
`channel` field, rather than computing the same ternary twice
independently.

DEVIATION 3 (documented, not fixed — out of scope) - the 'email'
branch of `channel` selection is effectively unreachable from the
Today screen's own new-subscriber flow, and if it WERE reached by a
different caller, the underlying poller's email-send path (server.js,
`channel === 'email'` branch) would very likely skip the job anyway.
Traced this precisely: server.js's poller, for `channel === 'email'`
jobs, looks up `AbandonedCustomer.findOne({shopDomain, sessionId:
job.cartToken})` and requires `customer.email` to exist -- it does
NOT use `Profile.channels.email.address` or the job's own `payload`
at all for finding a recipient (payload.subject/payload.body are only
used as a fallback for the COPY TEXT if the poller's own live
generateCopy() call fails, never as the actual send target). Every
profile returned by Part A's new-subscribers endpoint has
`channels.push.subscribed === true` (it's the endpoint's own filter
condition), so `send-now`, when invoked from THIS Today-screen flow,
will always compute `channel === 'push'` and never actually exercise
the email branch — this specific new-feature's happy path is
unaffected. Flagging this as a genuine, pre-existing structural gap in
the broader system (a "send-now" call against a profile that has an
email but is NOT push-subscribed and has no linked AbandonedCustomer
row would silently produce a permanently-skipped job, no email ever
sent) that this task's explicit file scope (routes/profiles.js,
routes/push.js, Today.jsx — not server.js) does not cover fixing.

Everything else in send-now matches the given code exactly: the 400/
404 guards, the cartToken derivation
(`identifiers.cartTokens.slice(-1)[0]`), cancelling existing pending
jobs before creating the new one (necessary given ScheduledJob's own
partial-unique index on {shopDomain, profileId, signalType} scoped to
status:'pending' — confirmed by re-reading backend/models/
ScheduledJob.js, read in full in the immediately preceding read-only
audit this session), `runAt: new Date()`, and the response shape.
