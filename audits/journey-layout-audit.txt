5. How product data is currently available - does selectedCustomer
   have product info; topProducts structure
====================================================================
Yes -- `selectedCustomer.topProducts` (and, before selection,
`c.topProducts` for each row in the customer list) is an array
produced by the backend's getJourneyData() (backend/routes/events.js),
built from that customer's recent product_view events:
  topProducts: Object.values(productViews)
    .sort((a, b) => b.count - a.count)
    .slice(0, 3)
Each entry's shape (per that same backend aggregation):
  { productId, title, count, lastSeen }
-- though only `title` and `count` are actually read anywhere in
Journey.jsx (`productId` is read too, in one spot -- see below;
`lastSeen` is never read in this file at all). Capped to the top 3
products by view count.

Where it's consumed in Journey.jsx:
  - Left customer list, "Top product" column (line 683-684):
    `c.topProducts?.[0]?.title` -- just the single top product's
    title, with a numeric-ID fallback check (`/^\d+$/.test(...)`
    displays '—' instead of a raw numeric product ID).
  - Right panel, "Most interested in" section (lines 778-798): ALL of
    `selectedCustomer.topProducts` (up to 3), each rendered as
    `{p.title}` + `{p.count} view(s)`.
  - NotificationComposer's auto-fill (line 225): `rawProduct =
    customer?.topProducts?.[0]?.title || ''`, with the same numeric-ID
    guard, fed into the SUGGESTIONS title()/body() functions as
    `product`.
  - NotificationComposer's send() (lines 246-248): uses
    `customer.topProducts[0].productId` (the only place `productId`
    is read in this file) to build the notification's click-through
    URL: `https://${shop}/products/${customer.topProducts[0].productId}`,
    falling back to the bare shop URL when there's no top product.
  - EmailComposer's auto-fill (line 439): same
    `customer?.topProducts?.[0]?.title` pattern as
    NotificationComposer, independently duplicated (not shared via a
    common helper).
