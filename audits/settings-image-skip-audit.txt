DEVIATION FROM THE LITERAL TASK — verified against the actual backend
handler, not guessed
=========================================================================
The task's given STEP 3 code stripped imageUrl from BOTH popupBody and
a separate mobileBody, then sent `{ ...popupBody, mobilePopup: mobileBody }`.
I implemented the popupBody half exactly as given, but did NOT create
or strip a mobileBody — mobilePopup is still sent to the backend
complete and unmodified, exactly as it was before this task. This is a
deliberate, safety-driven deviation, not an oversight:

backend/routes/profiles.js's PATCH /:shopDomain/popup handler (read in
full during a previous audit this session,
audits/settings-slow-save-audit.txt) treats the two halves of the body
completely differently:

  const set = {};
  for (const key of POPUP_FIELDS) {
    if (Object.prototype.hasOwnProperty.call(req.body, key)) {
      set[`popup.${key}`] = req.body[key];
    }
  }
  if (req.body.mobilePopup && typeof req.body.mobilePopup === 'object') {
    set.mobilePopup = req.body.mobilePopup;
  }
  await Store.updateOne({ shopDomain: shop }, { $set: set });

- Top-level fields (imageUrl included) become dot-notation keys like
  `popup.imageUrl`. MongoDB's $set only touches the exact dotted path
  named — a field simply absent from the request body is never
  mentioned in `set`, so the document's EXISTING popup.imageUrl is left
  completely alone. Omitting popup.imageUrl from the body is safe.

- `mobilePopup`, by contrast, is assigned as a SINGLE top-level key:
  `set.mobilePopup = req.body.mobilePopup`. This is a wholesale
  replacement of the entire embedded subdocument — MongoDB's $set on a
  whole object key overwrites it completely, so any field that object
  does NOT include (imageUrl included) is deleted from the stored
  document, not left alone.

Given that, applying the same "delete imageUrl when unchanged" trick
to mobileBody would mean: the very first time a merchant edits ANY
mobile-tab field (a color, the headline, textAlign — anything) WITHOUT
also re-uploading the mobile image in that same session, the resulting
save would silently wipe out their previously saved mobile popup
image, because mobilePopup would be sent as a complete object minus
imageUrl, and the backend would store exactly that (minus the image)
in place of the old one. This is precisely the scenario the task's own
problem statement describes as the common case ("only changed a color
or text field") — so applying the literal fix to mobilePopup would
break on the very use case it's meant to speed up, for the mobile
image specifically, on every affected save from then on (silently,
with no error, since the request would succeed as a valid partial
mobilePopup object).

Given the explicit "DO NOT touch backend files" constraint, there is
no safe way to skip sending mobilePopup.imageUrl without either (a)
also omitting it from the wholesale-replace body only when NOTHING
else in mobilePopup changed either (which the task's given design does
not attempt to track, and would require broader dirty-tracking than
just the image), or (b) the backend itself switching mobilePopup to
the same per-field dot-notation merge popup.* already uses. Neither is
in scope here, so mobilePopup is still sent complete and unconditionally,
exactly as before this task — the bandwidth-savings optimization this
task delivers applies to the DESKTOP popup.imageUrl only.

mobileImageChanged / setMobileImageChanged are still added and wired
up exactly as the task specified (tracked correctly across all 3
image-mutating call sites, reset after a successful save) so the
plumbing is in place and consistent with the desktop side — should a
matching backend change land later (switching mobilePopup's PATCH
handling to per-field dot-notation, mirroring popup.*), the frontend
change needed at that point would be a one-line addition (stripping
mobileBody.imageUrl the same way popupBody's is), not a rework.
