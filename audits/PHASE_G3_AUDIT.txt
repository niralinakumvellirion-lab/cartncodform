4. CONFIRM — saveSettings calls PATCH /settings
================================================================================
  async function saveSettings() {
    setSaving(true); setError(''); setSuccess(false);
    try {
      await apiSend(`/api/profiles/${shop}/settings`, 'PATCH',
        { voice, caps, quietHours, timezone });
      setSuccess(true);
    } catch (e) { setError(e.message || 'Save failed'); }
    finally { setSaving(false); }
  }
Backend PATCH /:shopDomain/settings (Phase E) dot-notation-merges
voice.* / caps.* / quietHours.* and sets timezone; returns { updated: true }
and evicts the weekly-narrative cache for the shop.

5. CONFIRM — updateSignalConfig: optimistic update + fire-and-forget PATCH
================================================================================
  function updateSignalConfig(signalType, patch) {
    setConfigs(prev => {                          // OPTIMISTIC, synchronous
      const existing = prev.find(c => c.signalType === signalType);
      if (existing) return prev.map(c =>
        c.signalType === signalType ? { ...c, ...patch } : c);
      return [...prev, { signalType, enabled: true, channelOverride: null, ...patch }];
    });
    apiSend(`/api/profiles/${shop}/signal-configs/${signalType}`, 'PATCH', patch)
      .catch(e => console.error('[settings] signal config error:', e.message));  // FIRE-AND-FORGET
  }
No await, no reload — the local `configs` state is the source of truth for the
UI; the PATCH persists in the background. Backend PATCH
/:shopDomain/signal-configs/:signalType (Phase C) validates the enum -> 400,
upserts { enabled?, channelOverride?, maxSteps? }.

6. CONFIRM — Onboarding screen: 4 steps with localStorage done state
================================================================================
frontend/app/admin/screens/Onboarding.jsx — props { shop, onNavigate }.
STEPS (4):
  embed      -> Button url = `https://${shop}/admin/themes/current/editor?context=apps` (external)
  automation -> Button onClick = onNavigate('settings')
  push       -> Button url = `https://${shop}` (external)
  cod        -> Button onClick = navigator.clipboard.writeText(codLink)
Each step: a <Card> with a Checkbox (labelHidden) + bold title + subdued
description + a slim Button.
Manual done state: localStorage key `ccf_step_${id}_done` ('true'/'false').
  - readDone(id): try { localStorage.getItem(`ccf_step_${id}_done`) === 'true' } catch { false }
  - writeDone(id, done): try { localStorage.setItem(...) } catch {}
  - useState initializer seeds `done` from readDone for each step; the Checkbox
    onChange calls writeDone + setDone.
Progress: <Text variant="headingMd">{completed} of {STEPS.length} steps done</Text>
at the top. NO dismiss button — permanent screen.
<Page title="Setup">.

⚠ DEVIATION vs CLAUDE.md: CLAUDE.md / the handover's hard rules say
"No localStorage on the admin side." STEP 5 of THIS phase prompt explicitly
specifies localStorage keys `ccf_step_{id}_done` with exact read/write code.
Implemented per the phase prompt (all accesses try/caught so a blocked/
partitioned iframe storage degrades to in-memory-only). RECOMMENDATION
(open question #1): move this to `Store.onboarding.steps` — that field already
exists on the Store schema (added Phase C: `[{ id, done, doneAt }]`) and is the
intended home. That needs a small backend endpoint (e.g. extend PATCH
/settings to accept `onboarding`, or a dedicated
PATCH /:shop/onboarding/:stepId). Not done here to avoid unrequested scope.

12. NOTICED BUT NOT TOUCHED  (out of scope for Phase G3)
================================================================================
- CLAUDE.md "no localStorage in admin" vs STEP 5 (see §6). Implemented per the
  phase prompt; flagged as open question #1.
- Settings "Signals" section: `configs` only contains rows that EXIST in the DB.
  The 12 rows are rendered from SIGNAL_TYPES with a default fallback, so the UI
  is complete, but toggling a signal that had no row creates one lazily via the
  PATCH upsert. No bulk "seed all 12" call.
- Settings save does NOT re-fetch after PATCH — the local state is left as the
  user set it. If the backend normalises anything (it doesn't currently) the UI
  wouldn't reflect it until remount.
- caps.perDay / perWeek / maxUnopenedPush and quietHours.start / end accept any
  number the user types (no min/max/int validation client-side). The backend
  PATCH also does no range validation. A nonsense value (e.g. quietHours.start
  = 99) would just make the brain's isQuietHour comparison never true.
- The Onboarding "push" step ("Verify push notifications") has no actual
  verification — it's a manual checkbox. The prototype's step 4 ("Send yourself
  a test") implied a real test-send; not built.
- Onboarding is a nav screen but there is no first-run redirect / nudge to it
  (the old checklist auto-showed on the dashboard). A merchant has to click
  "Setup" in the nav.
- Timezone Select offers only IST + UTC. Real multi-tz support (the brain's
  computeRunAt already handles arbitrary IANA strings) would need a fuller list
  or a free-text field.
- Prototype screens still NOT built: "Insights" (product/collection tables with
  dwell/scroll — the plan's Part 5) and the richer "What to act on" grouped
  signal view. Today's "Insights" card + Settings' flat signal list are the
  minimal stand-ins. Presumably a later G-phase or deferred.
- No search / stage filter / pagination on Customers, Messages, COD (routes
  support limit/page; screens fetch page 0). Carried from G1/G2.
