  Once per session (sessionStorage 'ccf_prompt_shown').

Cart quantity at popup time:
  ccf-push.js does NOT read the Shopify cart at popup-show time.

Subscribe → generate discount flow:
  handleSubscribeClick() → Shopify push permission → FCM token → saveToken()
    → /apps/cartncodform/generate-discount (App Proxy → POST /api/discounts/:shop/generate)
    → backend generateDiscount() → Shopify Admin API discountCodeBasicCreate GraphQL
    → returns { code, percentage, expiryDays }
  Email capture also posted with the same request (body.email).

3. DISCOUNT CODE CREATION — current capability
══════════════════════════════════════════════════════════════

File: backend/routes/discounts.js
File: backend/models/DiscountConfig.js

DiscountConfig schema sub-docs:
  pushDiscount, emailDiscount, phoneDiscount, bothDiscount
    → { enabled, percentage (0–100), maxUses, expiryDays, prefix, offerText }
  whatsappCapture: { enabled }
  offerHeadline: String
  NOTE: phoneDiscount + bothDiscount are always saved with enabled:false
    (DISABLED_KEYS in discounts.js:55). The admin route forces them off on every
    PATCH. They exist in the schema for historical documents only.

generateDiscount() logic (discounts.js:86–345):
  1. Validates action ∈ ['push','email','phone','both','whatsapp']
  2. Resolves cfg = primaryCfg || bothDiscount (fallback)
  3. Creates code = prefix + '_' + 6 random chars
  4. Calls discountCodeBasicCreate GraphQL mutation:
     { percentage: cfg.percentage/100, all items, appliesOncePerCustomer: true,
       usageLimit: cfg.maxUses, context: { all: 'ALL' } }
  5. Returns { code, percentage, expiryDays, shop }

Shopify API version: API_VERSION from utils/shopify (not read; likely 2024-10 or 2025-01).
GraphQL mutation: DiscountCodeBasicInput — supports single flat-% only.
  There is NO quantity-tier support in discountCodeBasicCreate.
  Tiered/volume discounts in Shopify require Shopify Functions (a separate
  extension type) — NOT present in shopify.app.toml.

Workaround for quantity tiers WITHOUT Shopify Functions:
  Generate a flat-% code at subscribe time, choosing the % based on the cart
  quantity at that moment. The code is still flat-% but the merchant configured
  different %s per quantity threshold. This is achievable with the current API.

Admin routes:
  GET  /api/discounts/:shopDomain/config   — requireAuth + requireStoreOwner ✓
  PATCH /api/discounts/:shopDomain/config  — requireAuth + requireStoreOwner ✓
  POST /api/discounts/:shopDomain/generate — App Proxy signature verified ✓

4. SCHEDULER / BRAIN — birthday job feasibility

Brain signal types (brain.js BASE_VALUE map):

  price_hesitation, cod_to_prepaid, browse_abandon, post_purchase_d3,
  lapsing, winback, email_capture.

ScheduledJob fields relevant to birthday:
  profileId (ObjectId ref Profile), signalType (String), channel (push|email|whatsapp),
  runAt (Date), payload (Mixed — resolved at send time by poller), origin.
  Unique index: (shopDomain, profileId, signalType) where status=pending —

    which is correct behaviour (only one birthday job outstanding per profile).

  runBrainForShop() is called in the nightly job loop.
  Birthday jobs would need a separate daily query:
    Profile.find({ shopDomain, 'birthday.month': today.month, 'birthday.day': today.day })
    → schedule a ScheduledJob(signalType:'birthday', runAt: morning of birthday).
  This can run in the same nightly sweep or as its own poller pass.
  Copy (push title/body or email subject/body) resolved by poller at send time
  via generateCopy() — CLAUDE.md rule: copy is never locked in at schedule time.

Discount code for birthday send:
  The poller calls generateDiscount() inline at send time (not at schedule time).
  generateDiscount() is already exported from routes/discounts.js:
    module.exports.generateDiscount = generateDiscount;
  It can be imported by the poller / email sender without going through HTTP.
  The birthday discount % would come from a new DiscountConfig sub-doc 'birthdayDiscount'.

6. BIRTHDAY COLLECTION — approaches and gaps
══════════════════════════════════════════════════════════════

Approach 1: Storefront popup birthday input (feasible without new scopes)
  - Add a date-of-birth field (month + day only — year often not needed) to the
    existing push/email popup capture flow.
  - Visitor enters birthday → stored in Profile.birthday.{ month, day }.
  - No new Shopify scopes needed (Profile is our own DB).
  - Limitation: only reached by visitors who see the popup; not all customers.

Approach 2: Post-purchase email with birthday link (requires email template)
  - After an order, send "Share your birthday for a surprise" email.
  - Link goes to a Shopify customer account page or a custom form (COD-form pattern).
  - More reach (all buyers), but requires a landing page and email template.
  - Out of scope for a single prompt per CLAUDE.md. Not recommended for v1.

Approach 3: Shopify Customer object birthday field + customers/update webhook
  - Shopify stores birthday on the customer object. write_customers scope is granted.
  - Would need: register customers/update webhook in shopify.app.toml, parse the
    birthday field, upsert into Profile.
  - More complete (catches birthdays set via Shopify account), but adds webhook
    overhead and complex identity matching (customerId link needed).
  - Not recommended for v1. Approach 1 is simpler.

Recommended v1 scope: Approach 1 (popup birthday capture).

Gaps for birthday feature:
  1. Profile.birthday field missing  → add { month: Number(1-12), day: Number(1-31) }
  2. Popup birthday input missing    → add month+day fields in ccf-push.js capture flow
  3. Popup submit sends birthday     → include in POST to /api/discounts/:shop/generate
  4. generateDiscount() birthday action → new 'birthday' action type (saves to Profile)
  5. DiscountConfig.birthdayDiscount → new sub-doc (enabled, percentage, prefix, expiryDays)
  6. Admin UI for birthday offer     → new section in Settings.jsx Discounts card
  7. brain.js birthday signal        → new signalType 'birthday'
  8. Nightly birthday scheduler      → daily sweep: find profiles whose birthday = today,
     schedule ScheduledJob(signalType:'birthday')
  9. Poller birthday send            → resolve copy + generate discount code + send push/email
  10. CopyCache birthday templates   → new copy keys for birthday push title/body + email

7. QUANTITY TIERS — approach and gaps
══════════════════════════════════════════════════════════════

Shopify constraint: discountCodeBasicCreate = single flat-%.
  True volume/tiered discounts require Shopify Functions. Adding a Shopify
  Functions extension to shopify.app.toml is out of scope per CLAUDE.md rules
  ("No ScriptTags" — Shopify Functions is similarly a platform extension).

Feasible workaround: cart-quantity-resolved flat-% code
  At popup show time, read the cart quantity via Shopify's storefront Cart API
  (GET /cart.js — available on any Shopify storefront, no auth needed).
  Map quantity → % from a merchant-configured tier table:
    { minQty: 2, percentage: 10 }, { minQty: 3, percentage: 15 }, { minQty: 4, percentage: 20 }
  Generate a single flat-% code for the matching tier.
  The popup offer headline updates dynamically ("Add 2+ items for 10% off").
  This is honest (not a true volume discount applied at checkout) but delivers
  the merchant's intent for the subscribe-and-buy flow.

Storefront implementation:
  ccf-push.js: add fetchCart() (GET /cart.js) at intent-trigger time.
  ccf-push.js: resolve tier before showing prompt; show tier-specific headline.
  POST to generate-discount: include cartQty in body.
  generateDiscount(): read quantityTiers from DiscountConfig, pick matching tier's %.

Backend / model changes:
  DiscountConfig: add quantityTiers: [{ minQty: Number, percentage: Number }]
  discounts.js: new EDITABLE_KEYS entry 'quantityTiers' (sanitize each tier row).
  generateDiscount(): accept cartQty in body; resolve which tier applies; use that %.

Admin UI:
  Settings.jsx: new quantity tiers section — table of rows (min qty, %) with add/remove.

Gaps for quantity tiers:
  1. DiscountConfig.quantityTiers field missing
  2. discounts.js PATCH: sanitize/persist quantityTiers array
  3. ccf-push.js: fetchCart() + resolveQuantityTier() at popup time
  4. ccf-push.js: dynamic headline reflecting current tier
  5. POST body sends cartQty → generateDiscount() resolves %
  6. Admin UI: quantity tiers table in Settings.jsx

8. RISKS AND CONSTRAINTS
══════════════════════════════════════════════════════════════

Birthday popup field:
  - Only a single-field date picker (month + day) is practical in the narrow
    popup. A full datepicker widget is too heavy; two <select> dropdowns work.
  - Birthday is NOT PII in the same sense as email/phone (no direct contact),
    but it is personal data. Must not appear in any console.log.
  - Must validate: month ∈ 1–12, day ∈ 1–31 (no date-validity check needed at
    capture; invalid Feb 30 never fires because the matching query won't find it
    on a real calendar day).

Quantity-tier /cart.js fetch:
  - GET /cart.js is synchronous-ish (~100ms) and adds latency before popup shows.
  - Should be fired in parallel with fetchDiscountConfig() at init, not blocking.
  - Returns { item_count } — use that as the quantity proxy.
  - If /cart.js fails (e.g., guest with empty cart), default to no-tier (use the
    pushDiscount/emailDiscount flat % as fallback).

DiscountConfig backward compat:
  - Existing docs that pre-date these changes have no birthdayDiscount /
    quantityTiers fields. defaultConfig() in discounts.js must fill them with
    safe defaults (enabled:false, empty tiers). Already the pattern for other sub-docs.

Shopify Functions hard constraint:
  True volume discounts (applied automatically at checkout on ANY cart, regardless
  of how the customer got there) require Shopify Functions. This workaround only
  applies the tier benefit to visitors who interact with the popup.
