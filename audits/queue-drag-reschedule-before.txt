--- 1. PATCH /api/queue/:shop/festival/:id ---

File: backend/routes/queue.js
Line: 527

Accepts scheduledAt? YES. It is in FESTIVAL_PATCH_FIELDS.
Format accepted:
  - "YYYY-MM-DDTHH:mm" (store wall-clock) → resolveScheduledAt() → zonedTimeToUtc()
  - ISO string (existing UTC instant from DB) → new Date(str) directly

Does it reject past dates? NO. Only the POST handler (line 304-313) rejects past
dates. The PATCH handler has no such check.

Does it check status?
  findOneAndUpdate scope: { _id, shopDomain, status: { $ne: 'sent' } }
  → 'cancelled' items can still be edited (only 'sent' is blocked).
  After the update, if item is null, it fetches the item to check if status='sent'
  and returns 409 in that case; otherwise returns { success: true, item: null } (200).

Does it check sendClaimedAt? NO. Nothing prevents rescheduling a claimed item.

groupId / multi-date campaigns: PATCH supports applyToGroup=true which propagates
content fields (not scheduledAt) to sibling documents still draft/approved. By
default (applyToGroup=false), only the target document is updated. Drag-reschedule
must not set applyToGroup — confirmed default is false.

Festival collision (same festival + same date): PATCH does not check for this.
  The POST handler has an idempotent findOneAndUpdate for (festival, scheduledAt)
  — but only when festival is truthy. PATCH has no such guard.
  If item A (festival="Diwali") is dragged to a date where item B (festival="Diwali")
  already exists with status draft/approved, both items end up with the same
  scheduledAt. No unique index on (shopDomain, festival, scheduledAt) in the model.
  → Unsafe: creates two items for the same festival on the same date.

Unique index? None on (shopDomain, festival, scheduledAt). POST is idempotent by
application logic (findOneAndUpdate), not by index constraint.

--- 4. What PATCH cannot do safely for drag-reschedule ---

a) No past-date rejection — a dragged item dropped on today-but-past-time would be
   accepted by the backend (only start-of-today is checked in POST, PATCH has no check).
   UNSAFE.

b) No sendClaimedAt check — dragging a just-claimed item (poller is mid-send) would
   reschedule it, causing the poller to send to an unexpected date.
   UNSAFE.

c) Status scope includes 'cancelled' (query: $ne: 'sent') — cancelled items should
   not be draggable at all; the backend should also reject them.
   UNSAFE (though UI will guard this via draggable attribute).

d) No festival collision check — dragging "Diwali" item to a date that already
   has another "Diwali" draft/approved item creates two Diwali items on that date.
   UNSAFE.

CONCLUSION: PART 1 backend changes are required.

--- 5. What PART 1 must add to PATCH ---

1. Pre-fetch target item before update to check status and sendClaimedAt.
   - Not found → 404
   - sendClaimedAt set → 409 "This item is currently being sent..."
   - status not in ['draft', 'approved'] → 409 with specific message

2. Past-date check for YYYY-MM-DDTHH:mm shaped scheduledAt:
   - Before start of today in store timezone → 400 "scheduledAt must not be before today"
   - Today but time already passed → 400 "That time has already passed today."
   ISO strings (date field untouched in edit modal) are exempt from past-date check.

3. Festival collision check:
   - If updates.scheduledAt is set AND target.festival is truthy:
     check for any other item with same festival, shopDomain, overlapping day,
     status draft/approved → 409 "A 'Diwali' item is already scheduled on that date."

4. Change findOneAndUpdate status scope: { $in: ['draft', 'approved'] } (was $ne: 'sent').

5. Change "not found after update" from { success: true, item: null } (200)
   to 409 "Item was modified concurrently, please retry."
