2. HOW /api/dashboard COUNTS — AND WHAT IT MISSES
======================================================

GET /api/dashboard/:shop/channels  (routes/dashboard.js:68)

--- Push ---
sent:    ScheduledJob.aggregate { channel:'push', status:'sent',
         sentAt:{$gte:from,$lte:to} }  groupBy signalType
pending: ScheduledJob.aggregate { channel:'push', status:'pending' }
MISSES:  send-customer (no record), send-journey (no record),
         send (admin browser, should be excluded anyway)

--- Email ---
sent:    emailSentTotal = Profile.aggregate $unwind messages,
         match { 'messages.channel':'email', 'messages.sentAt':{$gte,$lte} }
         → captures: brain-email channel jobs, bonus email (poller)
         MISSES: email broadcast (ScheduledJob but not Profile.messages),
                 journey email (no record), template single (no record)
pending: ScheduledJob.aggregate { channel:'email', status:'pending' }
email drawer items:
         ScheduledJob { channel:'email', status:'sent', sentAt in range }
         MISSES: bonus email (Profile.messages only), journey email,
                 template single send

BUG: Card and drawer use DIFFERENT sources.
  Scenario A: shop sends only via bonus email path → card > 0,
              drawer empty (ScheduledJob has no channel=email rows)
  Scenario B: shop sends email broadcasts only → drawer has rows,
              card = 0 (Profile.messages not updated by logBroadcastSend)

--- WhatsApp ---
sent:    ScheduledJob.find { channel:'whatsapp', status:'sent',
         sentAt:{$gte,$lte} }
pending: Profile.find opted-in minus ScheduledJob.distinct profileId
MISSES:  none — all WA sends go through ScheduledJob

--- OLD "Emails Sent" tile (before commit 9df1147) ---
That commit replaced the conversion funnel with channel cards.
The pre-9df1147 code (DashboardScreen.jsx old notifStats fetch) called
  GET /api/profiles/:shop/today-stats  (not in dashboard.js at all)
which counted Profile.messages for the day, same limitation as above.

GET /api/dashboard/:shop/channels/:channel/items  (routes/dashboard.js:204)

Queries ScheduledJob for all channels and statuses.
For email: misses bonus email (Profile.messages only).
For push: misses send-customer, send-journey (no records).
Items already have: id, type, label, status, time, customer, preview,
outcome, outcomeChip (WA). No origin field.

3. DATE RANGE HANDLING
======================================================

parseDateRange (routes/dashboard.js:40):
  from = new Date(req.query.from)   — ISO 8601 string from frontend
  to   = new Date(req.query.to)
  Falls back to: from = 7 days ago, to = now
  NaN check: falls back to defaults if parsing fails

Field compared against: sentAt (sent jobs) / runAt (pending jobs)

Timezone:
  new Date() on server = UTC (Render server is UTC by default).
  Frontend getDateRange (frontend/app/admin/dashboard/DashboardScreen.jsx)
  builds ISO strings from JS Date objects, which are also UTC-wall.
  No timezone conversion on either side.
  RISK: a seller in IST will see "Last 7 days" as UTC days, not IST days.
  This is pre-existing; not introduced by this task.

5. RECOVERABILITY OF PAST MANUAL SENDS
======================================================

send-customer (push broadcast from Journey/Messages):
  → NO record in DB, no Resend log (push, not email)
  → NOT recoverable

send-journey (single push from Journey):
  → NO record, NOT recoverable

send-journey-email (single email from Journey):
  → No ScheduledJob; Resend API logs CAN be queried via Resend dashboard
    or GET /emails/:id but there's no local tag/metadata linking a Resend
    email_id back to a shop+profile. NOT recoverable into a local record.

email-templates/:id/send (single template to one customer):
  → Same — Resend-only, no local tag. NOT recoverable.

send-email-test:
  → Debug path; recovery not warranted.

CONCLUSION: No reliable server-side source exists for the unrecorded
manual sends (no jobId, no local tag written at send time).
→ The optional BACKFILL script does NOT have a reliable source.
→ Skip it and say so in the self-audit.

WHAT THIS MEANS FOR STEPS 1–3
======================================================

ScheduledJob: needs optional fields origin, sentBy, contentSnapshot.
NO new model needed — ScheduledJob already has the right shape for all
send types, including per-recipient rows (logBroadcastSend pattern).

Paths to add a record (currently NO record):
  push: send-customer → call logBroadcastSend after send (per token)
  push: send-journey  → insert one ScheduledJob status:'sent' after send
  email: send-journey-email → insert one ScheduledJob status:'sent' (or 'failed')
  email: email-templates/:id/send → insert one ScheduledJob status:'sent'/'failed'

Paths already recording, need origin added:
  push:  send-now           → origin:'manual' at ScheduledJob.create
  push:  send-store         → origin:'manual' in logBroadcastSend call
  push:  processFestivalQ   → origin:'scheduled' in logBroadcastSend call
  push:  brain/poller       → origin:'automated' in brain.js ScheduledJob.create
  email: broadcast          → origin:'manual' in logBroadcastSend call
  email: bonus-email path   → create a ScheduledJob row (currently only writes Profile.messages)
  email: email channel job  → origin:'automated' in brain.js ScheduledJob.create
  wa:    /send route        → origin:'manual' in ScheduledJob.create

Dashboard /channels email fix:
  Switch emailSentTotal from Profile.messages to ScheduledJob.count
  after all email sources write ScheduledJob rows.
  No de-duplication risk: each send is one ScheduledJob row (or one per
  recipient for broadcasts). Profile.messages will still exist for
  brain cooldown checks (unchanged).

Per-recipient vs aggregate decision:
  Broadcast with known recipient list (send-customer, send-store, broadcast):
    → per-token/per-recipient rows (existing logBroadcastSend pattern)
  Single-target manual sends (send-journey, send-journey-email, /:id/send):
    → one row per send (already per-recipient by definition)
