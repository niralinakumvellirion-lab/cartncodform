====================================================================
GET /:shopDomain/festival, PATCH /:shopDomain/festival/:id, and
DELETE /:shopDomain/festival/:id were all added exactly as given,
inserted after the existing POST /:shopDomain/festival route (added
in Phase 1) and before module.exports.

Unlike Phase 1's given POST /festival route (which was missing
:shopDomain entirely and would have 403'd on every request -- see
audits/dashboard-phase1-audit.txt), all three of these new routes
already correctly included :shopDomain in their path as given, so
none of them needed that fix. Confirmed requireStoreOwner's hard
`req.shopDomain !== req.params.shopDomain` 403 check would pass for
all three.

PATCH's `{ $set: req.body }` was implemented literally as given, with
NO field whitelisting added. Reasoning: the query itself is already
scoped to `{ _id: req.params.id, shopDomain: shop }`, so even an
unexpected field in the body can only ever be written onto a document
the caller's own shop already owns -- there is no cross-shop write
path here, only a same-shop field-injection risk. The only real-world
caller (the Planning List's Approve button) only ever sends
`{ status: 'approved' }`. Whitelisting would be defensible
hardening, but it was not asked for and the actual blast radius is
already bounded by the shop-scoped query, so it was left as given
rather than silently expanding scope on a route the task presented as
complete. Flagging this explicitly as a considered, not overlooked,
decision.

PART C — FRONTEND: QueueScreen.jsx completely rewritten
====================================================================

MonthCalendar was added before QueueScreen, essentially as given,
with two deliberate deviations:

1. DEVIATION -- `festivals` prop source. The task describes the prop
   as "FESTIVAL_CALENDAR upcoming festivals" but doesn't literally
   mandate getUpcomingFestivals()'s output. getUpcomingFestivals only
   returns festivals within a 60-day-from-TODAY rolling window and
   caps the result to `count` entries. Since the task also explicitly
   requires month navigation (<- [Month Year] ->), a merchant browsing
   to any month outside that 60-day window would see festival markers
   silently disappear if the filtered/capped helper were used as the
   `festivals` prop, even though MonthCalendar's own day-matching
   logic has no such limitation. Passed the raw, unfiltered
   FESTIVAL_CALENDAR array as the `festivals` prop instead, so
   festival badges correctly show for whatever month is on screen.
   getUpcomingFestivals is still copied into the file (per the literal
   "copy them into QueueScreen.jsx as well" instruction) even though
   MonthCalendar itself doesn't consume its output.

2. DEVIATION (bug fix) -- React key collision in the day grid. The
   given code keyed leading empty cells by `key={i}` (array index) and
   real day cells by `key={day}` (day-of-month number) within the same
   `.map()` over `days`. Since `i` and `day` are both small integers
   starting near 0/1, an empty cell and a real day cell can end up
   with the identical key within the same sibling array (e.g. index 1
   is an empty leading cell in a month starting on Tuesday, but day 1
   is also a real cell later in the same array) -- a genuine React key
   collision that causes incorrect reconciliation on re-render (stale
   DOM/state reuse), which would surface specifically when navigating
   between months via the newly-added nav buttons. Fixed by keying
   every cell (empty and real) by the array index `i`, which is
   unique across the whole array regardless of cell type. This is the
   same class of "given code has a real bug, fix it and document it"
   deviation this session has made repeatedly (see e.g. the Phase 1
   :shopDomain finding above).
