4. CONFIRM — cache checked before every LLM call
================================================================================
aiService.generateCopy step order:
  1. build voiceHash = md5(JSON.stringify(store.voice))
     cacheKey    = buildCacheKey(shop, signalType, productId, channel, voiceHash)
  2. CopyCache.findOne({ cacheKey })  -> HIT: log `[ai] cache hit for <key[:8]>`,
     return { title, body, subject } from the row. NO fetch.
  3. MISS + no LLM_API_KEY -> return fallback. NO fetch.
  4. MISS + key -> ONE fetch to Anthropic -> parse -> CopyCache.create(... 24h TTL)
     -> log `[ai] generated copy for <signal>/<channel>, tokens=<n>`.
There is no code path that calls fetch() without a prior CopyCache.findOne.
(Tested: test 1 = hit returns cache, fetch not called; test 2 = miss triggers
fetch.)

9. CACHE HIT RATE — how it will be measured
================================================================================
Every generateCopy outcome emits exactly one line:
    cache HIT      ->  "[ai] cache hit for <8hex>"
    cache MISS+gen ->  "[ai] generated copy for <signal>/<channel>, tokens=<n>"
    (no-key / error fallbacks emit a "[ai] ... failed" or nothing)

    hit_rate  =  count("[ai] cache hit")  /  ( count("[ai] cache hit")
                                             + count("[ai] generated copy") )

over any log window. Both lines are unique-prefixed and PII-free, so this is a
plain `grep -c` on Render logs. (A DB-side proxy also works: with 24h TTL, at
steady state CopyCache row count per shop ≈ distinct (signal, product, channel,
voice) tuples; sends beyond that are cache hits.)

11. DEVIATIONS FROM THE LITERAL SPEC (all deliberate)
================================================================================
(a) MODEL: spec says `claude-sonnet-4-6`. Implemented as
    `process.env.LLM_MODEL || 'claude-sonnet-4-6'` so the owner can point it at
    the current model without a code change. Per the running environment's
    guidance the latest is `claude-sonnet-5`; the owner should very likely set
    LLM_MODEL=claude-sonnet-5 in Render. (See Open Questions.)
(b) poller store var named `jobStore` not `store` — the surrounding code already
    has a lean `const store` (timezone only) in the same loop iteration;
    reusing that name would shadow it and read confusingly.
(c) `product.price` is passed as `''` on every job (spec: "not stored on the
    job yet — leave blank for now"). Kept verbatim; a price would improve copy
    quality once the brain stores it on the job payload.
(d) computeWeeklyStats.`conversions` is `recoveredCarts.length` (from the same
    `find` used for revenue/topProduct) rather than a separate
    `countDocuments` — identical result, one fewer query.
(e) STEP 6 said ScheduledJob `updatedAt >= sevenDaysAgo` for messagesSent —
    ScheduledJob has NO `updatedAt` field (Phase C added profileId/signalType/
    reason, no timestamps). Used `sentAt >= sevenDaysAgo`, which is what the
    poller actually stamps.
(f) `bestChannel` (weekly) and BEST_CHANNEL (insight) join sent ScheduledJobs to
    recovered AbandonedCustomers by cartToken == sessionId (a heuristic, not the
    attribution join). Adequate for a weekly summary; a precise version would
    walk AbandonedCustomer.attributedJobId.
(g) generateInsights LLM path parses a `[...]` block and only uses the result if
    it's an array of the same length as the input; otherwise it returns the
    deterministic evidence strings.

12. NOTICED BUT NOT TOUCHED  (out of scope for Phase E)
================================================================================
- With LLM_API_KEY UNSET (current reality), the poller now overwrites EVERY
  job's payload copy with the generic fallback — including legacy AutomationRule
  jobs that had merchant-authored title/body frozen at schedule time. This is
  the spec's `payload.title = copy.title || payload.title` (copy.title is always
  truthy). It matches the handover's "copy resolves at send time" but is a
  visible regression for the old scheduler until either (a) LLM_API_KEY is set,
  or (b) the old AutomationRule path is retired (already a Phase C open item).
- Brain EMAIL jobs still can't reach a profile whose address is only in
  Profile.channels.email.address (the poller's email branch looks up
  AbandonedCustomer by cartToken and needs customer.email). generateCopy now
  produces good email copy, but the SEND path for profile-only emails is still
  a Phase F/G gap (carried from Phase C).
- No CopyCache index build is forced; Mongo builds cacheKey-unique + TTL lazily.
- narrativeCache is a per-process Map — not shared across dynos and lost on
  restart. Fine for one Render instance; a real cache (Mongo/Redis) is a later
  optimisation.
- computeWeeklyStats / computeInsights scan the last 7 / 30 days of
  AbandonedCustomer + ScheduledJob with no pagination. Fine at current volume.
- aiService has no rate-limit / retry / backoff on the Anthropic call — one
  attempt, then fallback. Acceptable for now (fallbacks are safe); revisit if
  429s show up in logs.
- STEP 7 route returns `stats` verbatim to the admin; `stats.topProduct` is a
  product title (not PII). The admin (Phase G) renders it.
