10. DEVIATIONS FROM THE LITERAL SPEC (all deliberate)
================================================================================
(a) pushNotification.js broadcast path: kept the `!skipStaleCleanup` guard
    around the new `for … handleStaleToken` loop. The spec's snippet showed the
    bare for-loop, but /send-customer's broadcast call passes
    skipStaleCleanup=true (no-cartToken path) specifically to avoid pruning
    during a broad send; removing the guard would change that caller's
    behaviour. The cartToken-loop replacement IS unconditional (matches the
    old code there, which had no guard).
(b) server.js push branch: `result` not `sendResult` (spec's var name). `result`
    is the sendPushToCustomers return in the push branch.
(c) STEP 5c targeted routes/push.js POST /cart-activity, but the storefront
    only ever sends `add_to_cart` (not `page_view`) to /cart-activity —
    page_view events land at POST /api/events (the batch pipe). Added the
    clearPushSuppression hook to BOTH: /api/events (the one that actually
    fires) and /cart-activity (literal spec, harmless). Same class of
    /cart-activity mismatch flagged in the Phase D audit.
(d) `updateDeliveredRate` is called ONLY in the success `else` branch (per the
    spec's "after recordProfileMessage"). A totally-failed batch
    (result.sent === 0) does NOT update pushStats, so the rate skews slightly
    optimistic — it reflects "of batches that reached >=1 device, what % of
    targeted tokens delivered". Moving the call to also run on the failed
    branch would make it a true attempted/delivered rate; left per spec.
(e) `isStaleCode` added as a shared export so pushNotification.js and
    pushHygiene.js agree on the 3 FCM dead-token codes (spec listed them only
    in handleStaleToken's doc; pushNotification's detection previously covered
    just 2).

11. NOTICED BUT NOT TOUCHED  (out of scope for Phase F)
================================================================================
- The message `outcome` on Profile.messages is only ever written as 'sent'
  (recordProfileMessage). Nothing yet writes 'clicked' / 'converted', so
  checkUnopenedThreshold's clicked_count is always 0 in practice — which means
  after maxUnopenedPush brain pushes to a profile, push is ALWAYS suppressed
  until a page_view resubscribes it. Wiring PushClick / order attribution back
  into Profile.messages[].outcome is a Phase H (feedback loop) concern; until
  then this is aggressive-by-design but worth knowing.
- `updateDeliveredRate` treats `tokensFound` as "attempted". In the cartToken
  path sendPushToCustomers returns tokensFound = cartSubs.length (rows matching
  the cart), and `sent` is 0 or 1. So a single-recipient brain push reports
  attempted = (number of stale rows tried) which can be > 1. Rate is still
  directionally right (delivered/attempted) but "attempted" is token-attempts,
  not people.
- No index is added for Profile lookups by `identifiers.sessionIds` /
  `identifiers.pushTokens` specifically for the hygiene queries — the sparse
  identifier indexes from Phase A already cover `{ shopDomain, identifiers.* }`.
- pushStats reset is nightly and window-approximated by accumulation (the spec
  explicitly accepts this). A precise rolling 7-day rate would need per-send
  timestamped rows; not built.
- clearPushSuppression fires on EVERY page_view beacon for a matched profile
  (one extra Profile.findById + possible updateOne). Cheap, and it early-returns
  when already subscribed, but it is per-page_view, not throttled.
- The `/send-customer` admin route and `sendPushToStore` owner-push path are
  unchanged; only the customer broadcast/targeted send got hygiene wiring.

   a different numerator/denominator.

   both is fine, or drop the dead /cart-activity one.

   confirm 5.

   daily never resets and accumulates forever (window never closes). Should the
   reset instead be unconditional each night, or subtract a trailing day?
   Current behaviour matches the spec's snippet exactly.
