DEVIATIONS - both necessary, verified by reading the actual code before
and after each change, not guessed
=========================================================================
1. `phone: phone,` removed from BOTH generate-discount request bodies.
   The task's literal instructions named removing the `phoneEl`/`phone`
   variable declarations and simplifying the action-detection cascades,
   but never mentioned the two `body: JSON.stringify({ action: ...,
   email: email, phone: phone, ... })` calls that also reference
   `phone`. Once the `phone` variable declaration was removed (as
   explicitly instructed), these two references would throw
   `ReferenceError: phone is not defined` the instant a customer clicks
   Allow -- a guaranteed runtime crash on the app's own core discount-
   capture flow, not a cosmetic gap. Removed `phone: phone,` from both
   JSON bodies (leaving `action`, `email`, `sessionId`, `cartToken`
   unchanged). Per "DO NOT touch backend discount logic": the backend's
   generateDiscount() (backend/routes/discounts.js, unmodified by this
   task) already reads `body.phone` defensively (`const phone =
   body.phone ? String(body.phone).trim() : '';`), so a request that
   simply omits the `phone` key entirely is already handled gracefully
   server-side -- no backend change was needed or made.

2. The "card" layout's own duplicate phone-input block (item 4 above)
   was removed even though the task's Fix 1 instructions only
   explicitly named ccfBuildDiscountFields(). Read the file in full
   while implementing this fix (not just the two spots the task named)
   and found this second, functionally-identical #ccf-phone-input
   block, gated behind the same ccfShowPhoneField() (now hard-false)
   used for the SPLIT/banner layouts' shared field-builder. Two
   reasons this was fixed rather than left alone: (a) it becomes dead
   code the moment ccfShowPhoneField() always returns false, so leaving
   it in place has zero functional benefit and only adds confusion for
   a future reader wondering why an unreachable phone input still
   exists; (b) the task's own stated goal is "Remove phone number field
   from popup completely" -- leaving one of two near-identical
   phone-input blocks in place, purely because it happened to live in a
   different popup layout branch than the one explicitly named, would
   not meet that stated goal. Confirmed via `function injectProductNudge`
   / `function showSoftPrompt` line positions that this block sits
   inside showSoftPrompt() (not injectProductNudge()), so it is not the
   "separate phone field handling" the task explicitly excluded.

3. Fix 3 hides BOTH phoneDiscount AND bothDiscount toggle cards from
   Discounts.jsx, not just the literal "phone discount toggle card."
   Read Discounts.jsx in full: DISCOUNT_ITEMS has exactly 4 entries --
   pushDiscount, emailDiscount, phoneDiscount ("📱 Phone number"), and
   bothDiscount ("⭐ Email + Phone... Customer provides both email and
   phone"). With the popup's phone input now removed completely (Fix
   1), leaving "Email + Phone" toggleable and enabled-by-default-
   visible in the merchant admin UI would be actively misleading: a
   merchant could enable it expecting phone capture + a "both" discount
   tier, and the popup would silently never collect a phone number at
   all (the discount config itself would still technically function on
   the backend -- action 'both' now can never actually be sent from the
   main popup post-Fix-1, since the action-detection cascades no longer
   produce 'both' or 'phone' -- only 'push' or 'email' -- so a merchant-
   enabled bothDiscount rule would simply never be selected by the
   popup, a confusing silent no-op rather than an outright error).
   Hidden both from render via a filtered VISIBLE_DISCOUNT_ITEMS array
   built from the original, UNMODIFIED DISCOUNT_ITEMS (which still
   lists all 4 entries) -- satisfying "Keep backend unchanged — just
   hide from merchant UI" for both, not just one.
