DEVIATION FROM THE GIVEN SPEC — `shop` was NOT added to the Approve /
Add to Queue request bodies. The task's own template for those two
buttons includes a `shop` field ("body: { shop, title: editorTitle,
... }"), but the ACTUAL pre-existing code for both of those two calls
(POST /api/queue/:shop/festival) has never included `shop` in the
body — shop travels via the URL path segment only
(`` `/api/queue/${encodeURIComponent(shop)}/festival` ``), and the
backend's requireStoreOwner middleware reads shop exclusively from
`req.params.shopDomain`/the verified session token, never from
`req.body.shop`. This was explicitly documented and deliberately
removed in an earlier task (see audits/dashboard-phase1-audit.txt:
"Dropped the `shop` field from the request body in both calls since
the backend handler never read `req.body.shop` in the first place
[...] it was purely dead weight once shop travels via the URL path
instead"). Re-adding it here would silently reintroduce that same
dead weight against this file's own established, documented pattern
for these two specific endpoints, for no functional benefit — treated
as incidental template copy-paste (the same `{shop, title, body}`
shape was likely just reused across all three code blocks) rather
than a deliberate new instruction, and not applied. Send Now's body
keeps `shop` unchanged, since that endpoint (`/api/push/send-store`)
has always read shop from the request body, not the URL — both before
and after this task, matching the given template correctly for that
one button.

Also removed `imageUrl: editorImageUrl` entirely from all three
bodies (not kept alongside the two new fields) — none of the three
given body snippets include an `imageUrl` field, and the frontend
state producing it (`editorImageUrl`) no longer exists after Change 1,
so there is nothing left to send under that key from this screen.

====================================================================
CRITICAL FINDING — the backend routes that PERSIST these fields do
NOT read mobileImageUrl/desktopImageUrl yet; uploaded images will
silently fail to save until a follow-up task updates them
====================================================================
This task's own scope, git-add list, and verification steps name only
frontend/app/admin/dashboard/DashboardScreen.jsx and
backend/models/FestivalQueue.js — backend/routes/queue.js and
backend/routes/push.js were explicitly NOT in scope ("DO NOT change
any other logic," no other file listed to read/edit/stage). Neither
was touched. But checking them (via grep, not edited) surfaced a real,
concrete consequence worth flagging clearly, since it directly affects
whether uploaded images actually reach the database or a sent
notification:

1. backend/routes/queue.js's `POST /:shopDomain/festival` handler
   (used by both Approve and Add to Queue) destructures only
   `{ title, body, imageUrl, scheduledAt, festival, status }` from
   req.body and writes `imageUrl: imageUrl || ''` into the new
   FestivalQueue document. It does NOT read `mobileImageUrl` or
   `desktopImageUrl` at all. Now that the frontend sends
   `mobileImageUrl`/`desktopImageUrl` instead of `imageUrl` (Change 5),
   every Approve/Add-to-Queue request from this editor will silently
   persist `imageUrl: ''`, `mobileImageUrl: ''` (schema default, never
   set), and `desktopImageUrl: ''` (schema default, never set) — the
   merchant's uploaded mobile/desktop images will NOT be saved to
   Mongo at all, even though they display correctly in the editor's
   live preview right up until the button is clicked. This is a
   regression relative to the state before this task (which at least
   correctly persisted the single `imageUrl`).

2. backend/routes/push.js's `POST /send-store` handler (used by Send
   Now) destructures only `{ title, body }` from req.body — it has
   NEVER read any image field (not even the old singular `imageUrl`;
   this exact gap was already documented in
   audits/dashboard-phase1-audit.txt as a pre-existing, undone issue).
   Sending `mobileImageUrl`/`desktopImageUrl` in Send Now's body
   (Change 5) does not change this: both fields are silently ignored
   by this endpoint today, same as before.

Neither backend file was modified, since both are outside this task's
explicit scope (not read-first, not listed in Changes 1-5's file
targets, not in the git-add list, and the task said "DO NOT change any
other logic"). Flagging this prominently, in the same spirit as the
Phase 1 dashboard audit's own "Known, Undone Gap" section, because a
merchant using this editor today would reasonably believe uploading
mobile/desktop images and clicking Approve/Add to Queue/Send Now
actually stores or sends those images — it does not yet, for any of
the three buttons. A follow-up task updating
backend/routes/queue.js's festival POST handler (to destructure and
persist mobileImageUrl/desktopImageUrl) and, ideally,
backend/routes/push.js's send-store handler (to forward at least one
of the two images into the actual push payload) would be needed to
close this gap.
