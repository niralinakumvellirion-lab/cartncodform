CRITICAL FINDING — sendPushToStore ALREADY EXISTS, with a DIFFERENT
signature and purpose, and is used by a live route
====================================================================
PART E's own text anticipates this ("Check if sendPushToStore exists
in pushNotification.js. If it does NOT exist, add it") — and it DOES
exist:

  backend/utils/pushNotification.js line 40:
    async function sendPushToStore(shopDomain, title, body) { ... }
  exported at line 271: module.exports = { sendPushToStore, sendPushToCustomers };

This existing function sends to the STORE OWNER's own admin-device
PushSubscription (the `PushSubscription` model — separate from
`CustomerPushSubscription`), and is already used by the existing
POST /api/push/send route (backend/routes/push.js line 50-75) with
3 positional string arguments: sendPushToStore(shopDomain, title, body).

The task's given "if missing, add it" implementation is a COMPLETELY
DIFFERENT function under the SAME name:
  async function sendPushToStore(shopDomain, { title, body, url }) { ... }
(object-destructured second parameter, queries CustomerPushSubscription
instead of PushSubscription — i.e. "all storefront customers" rather
than "the store owner's own device").

Since sendPushToStore already exists, PART E's own stated condition
("If it does NOT exist, add it") is not met — so nothing should be
added under that name. Beyond just following that literal condition,
actually adding the given function under this name would have been
actively destructive: `module.exports.sendPushToStore = sendPushToStore`
would have OVERWRITTEN the real export, and the existing /send route's
positional call `sendPushToStore(shopDomain, title, body)` would then
destructure `{ title, body, url }` off the STRING `title`, silently
yielding `title: undefined, body: undefined, url: undefined` for
every future call to that route — no thrown error, just silently
broken owner-device notifications from then on.

RESOLUTION: backend/utils/pushNotification.js was NOT modified at
all. The new POST /api/push/send-store route instead reuses the
ALREADY-EXISTING `sendPushToCustomers(shopDomain, title, body, url,
imageUrl, mobileOnly, cartToken, skipStaleCleanup)` helper (already
imported at the top of push.js, already used by /send-customer and
/send-journey). Called with `cartToken: null`, it already queries
every CustomerPushSubscription row for the shop with no cart-specific
filter — i.e. exactly "all subscribers" — which is precisely what the
Suggestions feature needs. This is documented inline in push.js at
the new route, and is a direct application of this session's standing
practice: implement the given feature's actual intent, not a literal
snippet that would silently break existing, live functionality, and
flag the substitution explicitly.
