  How large could imageUrl be: imageUrl is a base64 data URI
  (`data:image/jpeg;base64,...`) produced by the canvas compression in
  section 1. Base64 encoding itself inflates the underlying binary size
  by roughly 1.33x (4 output bytes per 3 input bytes) on top of
  whatever the compressed JPEG bytes are. Since both popup and
  mobilePopup carry their OWN independent imageUrl (desktop image and
  mobile image are separate uploads, per the popup-responsive feature),
  a single save can carry TWO such base64 strings at once -- one at the
  top level (`popup.imageUrl`, spread in) and one nested inside
  `mobilePopup.imageUrl`. In the typical case (a real photo compressed
  to 800px/q0.7) each is commonly in the tens-of-KB range as base64
  text, but this is not enforced by any explicit cap in this file (see
  the note at the end of section 1) -- it is only as small as the
  canvas compression happens to make it for a given input image.

What does it write to MongoDB: a single `Store.updateOne({ shopDomain

dot-notation keys like `popup.imageUrl`, `popup.headline`, etc. (one
per POPUP_FIELDS entry present in the request body) plus, if provided,
a single `mobilePopup` key holding the entire nested object verbatim.
This is one MongoDB update command carrying however many base64 image
strings were included (potentially both `popup.imageUrl` and
`mobilePopup.imageUrl` in the same $set, since saveSettings() always
sends both `...popup` and `mobilePopup` together every save -- see

but not an unbounded or pathological amount given the frontend's

frontend section 1).
