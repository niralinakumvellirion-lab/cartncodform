DEVIATIONS - Part B
=========================================================================
1. Collapsed a template literal that embedded a raw newline. The
   task's given fetch call wrapped mid-string:
     apiGet(`/api/activity?shop=${encodeURIComponent(shop)}&from=${from}&to=${to}
       ${activeType ? '&eventType=' + activeType : ''}`)
   A JS template literal preserves an embedded line break as a literal
   "\n" character in the resulting string -- pasted verbatim, this
   would produce a URL with a raw newline in the middle of the query
   string (something like "...&to=2024-01-15T00:00:00.000Z\n
   &eventType=..."), which is invalid/unreliable. Read as an obvious
   formatting artifact from wrapping the line for display, not
   intended literal source -- written as a normal single-line template
   string (`url += ...` for the optional eventType part) instead.

2. Encoded `from`/`to` with encodeURIComponent, matching how `shop` was
   already encoded in the same given line and how every other
   dynamic query value elsewhere in this codebase is encoded. The
   ISO date strings getDateRange() produces (e.g.
   "2024-01-15T00:00:00.000Z") don't strictly require it (":" and "."
   are valid unencoded in a query-string value per RFC 3986), but this
   matches the codebase's own consistent convention rather than
   introducing the one unencoded interpolation in this file.

3. BADGE_CONFIG label text kept exactly as the task specified for this
   section ("Checkout started"), which reads slightly differently from
   Today.jsx's tile label for the same event type ("Started checkout",
   Phase 3). Not reconciled -- the task gave this exact wording
   specifically for the table badge, so it was used verbatim; flagging
   the inconsistency here rather than silently "fixing" it into
   matching Today's wording, since that would be a product-copy
   decision beyond this task's literal spec.

Everything else (state shape, filter tabs, getDateRange, the fetch
effect's guard/dependency array, the 4 tile definitions, the table
columns, empty/loading states) was implemented to match the task's
given spec as closely as the actual codebase's conventions allow.


PART C - NavMenu item, added to ALL 9 EXISTING page.js files (not
just the new one)
=========================================================================
The task's Part C said "Read frontend/app/admin/layout.jsx or wherever
NavMenu items are defined" -- read frontend/app/admin/layout.js (note:
the real filename is layout.js, not layout.jsx) first: it is a bare
passthrough (`export default function AdminLayout({ children }) {
return children; }`), NOT where NavMenu is defined. Grepped the whole
admin/ tree for `<a href="/admin/customers"` (a link that would only
appear inside a NavMenu block) and found it duplicated identically in
all 9 existing admin/*/page.js wrapper files -- there is no shared
layout that renders NavMenu once; each route's own page.js
independently renders its own <AppProvider><NavMenu>...</NavMenu>
<Screen /></AppProvider>, because layout.js does not wrap children in
either of those.
Given that, adding the Activity link to only the NEW activity/page.js
would mean the nav item only appears while a merchant is ALREADY on
the Activity screen, and disappears again on every other screen --
clearly not the intent of "Add 'Activity' as a new nav item." Read all
9 existing page.js files in full (cod, customers, discounts, insights,
journey, messages, admin/page.js, settings-page, signals) before
editing any of them, confirmed their NavMenu blocks are byte-identical,
and added the same one line
(`<a href="/admin/activity" rel="activity">Activity</a>`) to each, in
the same position (immediately after the Today link, before
Customers) -- the "after Today" placement the task listed first among
the two options given ("after Today, before or after Customers").
admin/page.js has a different indentation level than the other 8 (it
wraps NavMenu in `{!showOnboarding && (...)}`, one level deeper) --
matched that file's own existing indentation rather than copying the
other 8 files' indentation into it.
Verified afterward: grepping the whole admin/ tree for `rel="activity"`
returns all 10 files (9 existing + the new activity/page.js), each
exactly once.
