1. CUSTOMERS.JSX
====================================================================

--- How the customer list is fetched ---
loadData() (useCallback, lines 212-256), debounced 300ms via a
useEffect (lines 258-266, setTimeout on every [loadData] change, i.e.
every time shop/filter/search changes). Fetches, in parallel via
Promise.all:
  GET /api/profiles/:shop/profiles?limit=50[&filter=...][&search=...]
  GET /api/profiles/:shop/signals?limit=200
Results:
  profiles -> setProfiles(profRes.profiles), setTotal(profRes.total)
  signals  -> reduced client-side into two maps:
    signalMap[profileId]      = { type, strength } of the STRONGEST
                                 signal for that profile
    signalCountMap[profileId] = total signal count for that profile
There is no separate call for "top interest" — that comes from each
profile object's own `interests` field (p.interests, an object of
interest-name -> weight), sorted client-side per row.

--- How it's rendered ---
A single scrollable table/card (desktop: CSS-grid table with
GRID_COLS = '2fr 1fr 2fr 1fr 1.5fr 1fr'; mobile: stacked 3-line
cards), filtered via FILTER_TABS (everyone / has_cart / bought_once /
repeat_buyer / going_quiet -> sent as the `filter` query param) and a
debounced text search box (name/email, sent as `search`). Loading
state shows 5 skeleton rows; empty state shows "No customers match
this view."

--- What each customer row shows ---
Desktop columns (6):
  1. Customer    - display name (first email, else first phone, else
                    "Anonymous shopper · #<last5ofId>") + "seen <relative
                    time>" from p.lastSeenAt if present
  2. Stage       - a badge: "Repeat buyer" (orders.count>=2, blue),
                    "Bought once" (orders.count===1, green), "Has a
                    cart" (has a cartToken and 0 orders, yellow), else
                    falls back to STAGE_CONFIG[p.stage] label
                    (customer/identified/anonymous/lapsed)
  3. Most interested in - the profile's top `interests` entry (by
                    weight) as plain text, plus the label for that
                    profile's strongest signal (from signalMap,
                    SIGNAL_LABELS lookup) underneath in indigo; "—" if
                    no signal
  4. Reach       - three icons (🔔 push, ✉️ email, 📱 phone), each
                    dimmed to 20% opacity when that channel is absent
  5. Last messaged - relative time of p.messages[last].sentAt, or
                    "Never"
  6. Spent       - p.orders.ltv formatted as ₹X,XX,XXX (en-IN), or "—"
                    if 0/absent
Mobile cards show the same information condensed into 3 rows (name +
stage badge; last-seen + "<n> signals" count from signalCountMap;
channel icons + LTV).

--- What happens when a customer row is clicked ---
onClick sets selectedProfileId to that profile's _id (line 475/605).
When selectedProfileId is truthy, the ENTIRE Customers component
short-circuits (line 268-276) and renders, in place of the list:
  <ProfileScreen shop={shop} profileId={selectedProfileId}
                 onBack={() => setSelectedProfileId(null)} />
i.e. a FULL-SCREEN REPLACEMENT (imported from './Profile', a separate
screen file not included in this audit's scope), not a side panel —
the list, search box, and filter tabs all disappear while a profile
is open; clicking "Back" inside ProfileScreen (via the onBack prop)
is what restores the list view.

3. SHARED API CALLS BETWEEN BOTH SCREENS
====================================================================

NONE. Zero identical endpoint strings are called by both files:

  Customers.jsx calls:
    GET /api/profiles/:shop/profiles?...
    GET /api/profiles/:shop/signals?limit=200

  Journey.jsx calls:
    GET  /api/events/:shop/journey?limit=50
    POST /api/push/send-journey
    POST /api/push/send-journey-email

Customers.jsx builds its "most interested in" / signal view by
fetching profiles and signals SEPARATELY and joining them client-side
(signalMap/signalCountMap). Journey.jsx instead calls one combined
backend endpoint (/api/events/:shop/journey) that already returns
each customer bundled with .profile, .signals, .topSignal,
.topProducts, and .recentEvents pre-joined server-side — a different,
richer endpoint built for a different purpose (individual customer
journey detail, not a filterable/searchable list). There is real DATA
overlap (both ultimately show profile identity + top signal/interest
per customer) but no shared API CALL — a merge would need to either
pick one of these two backend endpoints as the single source of truth
or keep both fetches running side by side.

Additional non-API overlap worth noting for a merge: both files
independently define an IDENTICAL DS design-token object, an
IDENTICAL PageHeader() component, and a near-identical SIGNAL_LABELS
map (Customers.jsx's SIGNAL_LABELS uses "Reached checkout" /
"Price dropped"; Journey.jsx's uses "Checkout left behind" /
"Price dropped" for the same two keys — one small wording
difference between the two copies). This matches the same
no-shared-layout, per-file-duplicated-DS pattern already documented
for every other screen in this codebase (see e.g.
audits/dashboard-merge-audit.txt for the same pattern in Today.jsx /
Insights.jsx).
