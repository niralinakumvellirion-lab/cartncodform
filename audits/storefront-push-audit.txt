1. HOW PUSH SUBSCRIPTION IS INITIALIZED
====================================================================
Neither the raw browser Push API directly, nor a native FCM SDK — it
uses the FIREBASE JS SDK's (compat build) `messaging.getToken()`
method, which internally wraps the browser's native Push API
(pushManager.subscribe()) via the registered service worker, but
returns an FCM-specific value rather than a raw PushSubscription.

Two `<script>` tags load the Firebase compat SDK at the top of the
file (lines 3-4):
  https://www.gstatic.com/firebasejs/10.12.0/firebase-app-compat.js
  https://www.gstatic.com/firebasejs/10.12.0/firebase-messaging-compat.js

The actual flow (triggered from the Allow button's click handler,
lines 1253-1264, and again on every return visit via checkAndInit(),
lines 1878-1910):
  1. registerSW() — registers/reuses a service worker from
     `{origin}/apps/cartncodform/sw.js` (App Proxy, same-origin as the

     stale/wrong-scope SW registrations first (lines 1690-1702).
  2. getToken(swReg) — lines 1764-1795:

2. WHAT KIND OF TOKEN/SUBSCRIPTION OBJECT IS STORED
====================================================================
A bare FCM REGISTRATION TOKEN STRING — NOT a raw Web Push
PushSubscription object (which would have `.endpoint`, `.keys.p256dh`,
`.keys.auth`, etc.).

getToken()'s Promise resolves with whatever
`messaging.getToken({...})` returns, which per the Firebase SDK is
always a plain string. That string is passed straight into
saveToken(token) (line 1780: `resolve(token)`) and from there directly
into the POST body as `token: token` (line 1819) with no
transformation. localStorage also stores it verbatim under
`TOKEN_KEY = 'ccf_fcm_token_' + SHOP_DOMAIN` (line 1832). At no point
in this file is `.endpoint`/`.keys` ever referenced or extracted —
confirmed via search, zero occurrences of either term anywhere in the
file. This matches exactly what backend/utils/pushNotification.js
expects and stores in CustomerPushSubscription.token (per the prior
mobile-push-audit.txt) — an FCM token string, sent to FCM's
sendEachForMulticast({tokens: [...]}) API, which is the correct
counterpart for this kind of token.

3. THE /subscribe-customer POST BODY
====================================================================
Two call sites POST to `BACKEND_URL + '/api/push/subscribe-customer'`
(BACKEND_URL is the hardcoded constant at line 9:
'https://api.shopireachboost.com') — both send the exact same field
shape:

  saveToken() — lines 1814-1827 (normal `fetch`, used right after a
  fresh subscribe or on checkAndInit()'s token-rotation check):
    {
      shopDomain: SHOP_DOMAIN,
      token: token,
      oldToken: oldToken,
      page: window.location.pathname,
      deviceType: deviceType,
      cartToken: cartToken,
      customerId: customerId,
      ccfSessionId: getSessionId()
    }

  resyncCartTokenBeacon() — lines 2217-2226 (uses navigator.sendBeacon
  when available, falling back to a fire-and-forget fetch; called
  after a cart add/change so the subscription's cartToken stays
  current):
    { shopDomain, token, oldToken: token (always equal to token itself
      here — this call never rotates the token, only re-syncs
      cartToken), page, deviceType, cartToken, customerId, ccfSessionId }

Every field's source:
  - shopDomain: SHOP_DOMAIN (window.Shopify.shop, or hostname fallback)
  - token: the FCM registration token string from getToken()
  - oldToken: the previously-stored token from localStorage (saveToken)
    or the current token itself (resyncCartTokenBeacon, i.e. a no-op
    rotation)
  - page: window.location.pathname
  - deviceType: see section 4
  - cartToken: fetched fresh from /cart.js each time, with the
    `?key=...` suffix stripped
  - customerId: window.Shopify.customerId if the shopper is logged in,
    else null
  - ccfSessionId: from getSessionId() (not read in this task — a
    session-id helper defined elsewhere in the file, out of this
    audit's read scope)

4. HOW deviceType IS DETECTED AND WHAT VALUES IT CAN TAKE
====================================================================
Both call sites (saveToken() line 1799, resyncCartTokenBeacon() line
2212) use the IDENTICAL detection logic:

  var isMobile = /Android|iPhone|iPad|iPod|Mobile/i.test(navigator.userAgent);
  var deviceType = isMobile ? 'mobile' : 'desktop';

This is the ONLY place deviceType is ever computed in this file. It
can take EXACTLY TWO values, always lowercase, always one of these two
literal strings: 'mobile' or 'desktop'. There is no third value (no
'tablet', no 'unknown', no capitalized variant) ever sent from this
file. This directly resolves an open question flagged in the prior
mobile-push-audit.txt (backend/utils/pushNotification.js's mobileOnly
filter does an exact match against `{$in:['mobile','unknown']}`) —
the storefront's own deviceType values are consistently exactly
'mobile' or 'desktop', so the exact-match filter risk previously
flagged as "unconfirmed" is NOT an active mismatch source for THIS
sender; 'mobile' rows from this file will always match a
mobileOnly:true query's 'mobile' branch correctly if that parameter
were ever wired up to a real caller (it currently isn't, per the
previous audit).

Caveat: the regex is a simple substring/OR match against
navigator.userAgent — it will correctly classify the vast majority of
real phones/tablets as 'mobile' (including iPads, which report
"iPad" in their UA on older iOS/iPadOS, and increasingly report as
desktop-Safari-like UAs on newer iPadOS by default unless the site
requests the mobile UA — a known platform quirk this code does not
account for) and everything else as 'desktop'. Modern iPadOS Safari
(13+) defaults to a DESKTOP-class User-Agent string that does NOT
match this regex at all (no "iPad", no "Mobile" token) — so recent
iPads would be silently classified as 'desktop' by this code, despite
being a mobile/tablet device. This is a real, concrete gap directly
relevant to "mobile not receiving/displaying correctly," specific to
iPadOS.

6. FOREGROUND NOTIFICATION DISPLAY + imageUrl/icon HANDLING — A REAL,
VERIFIED BUG
====================================================================
setupForegroundMessages() (lines 1658-1675):

  function setupForegroundMessages() {
    try {
      var app = firebase.apps && firebase.apps.length > 0
        ? firebase.apps[0] : firebase.initializeApp(firebaseConfig);
      var messaging = firebase.messaging(app);
      messaging.onMessage(function(payload) {
        var title = payload.notification && payload.notification.title
          ? payload.notification.title : 'ShopiReachBoost AI';
        var body = payload.notification && payload.notification.body
          ? payload.notification.body : 'New notification';
        if (Notification.permission === 'granted') {
          new Notification(title, { body: body, icon: '/favicon.ico' });
        }
      });
    } catch(err) {}
  }

Two concrete problems, both verified against the exact backend
message shape documented in audits/mobile-push-audit.txt:

  (a) This handler reads `payload.notification.title` /
      `payload.notification.body` — but backend/utils/
      pushNotification.js's sendPushToCustomers() NEVER sends a
      top-level `notification` field in the FCM message it builds
      (only `data` and `webpush` blocks — see that audit's exact
      payload dump). This means `payload.notification` will ALWAYS be
      undefined for every push this app actually sends, so `title`
      and `body` here ALWAYS fall back to the hardcoded generic
      strings 'ShopiReachBoost AI' / 'New notification' — the
      merchant's actual composed title/message is silently discarded
      and NEVER shown to a customer whose tab happens to be in the
      foreground when the push arrives. This is not a mobile-specific
      symptom by itself (any foreground tab, mobile or desktop, hits
      this), but it's a genuine, concrete, cross-file bug directly
      relevant to "why doesn't my notification look right."
  (b) Regardless of (a), this handler's own `new Notification(title,
      { body: body, icon: '/favicon.ico' })` call NEVER reads or
      passes an image at all — `icon` is hardcoded to '/favicon.ico',
      and there is no `image` option anywhere in this call. Even if
      (a) were fixed and payload.notification/data were read
      correctly, this specific code path has no way to display
      mobileImageUrl/desktopImageUrl/imageUrl under any circumstance —
      it structurally cannot show an uploaded image, ever, for a
      foreground-tab notification.

Practical impact by device: mobile users are statistically much less
likely to have the storefront tab open/focused when a push arrives
(they've typically navigated away, locked the phone, or closed the
browser) — most mobile deliveries would go through the BACKGROUND
path (the separate, unaudited sw.js), not this foreground handler.
Desktop users leaving a store tab open in the background are more
likely to be affected by this specific bug. This file cannot confirm
whether the SAME title/body/image-reading mistake also exists in the
background SW path — that would require auditing sw.js directly.

ADDITIONAL FINDING — saveToken() reports success before its own
network call resolves
====================================================================
Not explicitly asked for in the task's 7 points, but directly relevant
to "mobile not receiving notifications" and verified while reading
this file, so included here:

saveToken() (lines 1797-1872) kicks off its fetch chain
(`fetch('/cart.js').then(...).then(...POST to /subscribe-
customer...).then(...).catch(...)`) but does NOT return or await that
chain. Instead, immediately after starting it, the function
synchronously executes (line 1871):
  return Promise.resolve({ success: true });
This means the caller chain —
  registerSW().then(getToken).then(saveToken).then(function() {
    setupForegroundMessages();
    allow.textContent = '✓ Subscribed!'; ...
  })
— proceeds to show "✓ Subscribed!" and treats the flow as complete
BEFORE the actual POST to /subscribe-customer has necessarily
completed, or even if it ultimately FAILS (network error, backend
500, CORS issue, etc. — the fetch chain's own .catch at line
1866-1868 only console.errors, it does not reject/propagate anything
back to the outer Promise.resolve({success:true}) already returned).
A customer could see "✓ Subscribed!" in their browser while the
backend never actually received or stored their token+deviceType row
at all — meaning every future push attempt to that customer would
simply find no matching CustomerPushSubscription and skip them, with
zero visible indication anywhere (browser or backend) that the
original subscribe attempt silently failed.
