DEVIATIONS / MISMATCHES BETWEEN THE TASK'S SPEC AND THE ACTUAL CODE
====================================================================

1. TILES / old Insights stat tiles have no home in the new IA.
   The task's given Information Architecture (Sections 1-5) has no
   slot for the old "4 stat tiles" row (Product views this week /
   Allowed notifications / Add-to-cart rate / Sessions tracked),
   which was driven by insightsStats. The new KPI row uses notifStats
   instead (a completely different data source). Rather than silently
   inventing a 7th location for insightsStats data (which the task
   did not ask for) or leaving a dead, unused `TILES` derived-variable
   declaration sitting in the file, the TILES block itself was
   removed. insightsStats/setInsightsStats state is UNCHANGED (still
   fetched every loadInsights() call, per "keep all state/effects")
   but is now write-only -- nothing in the JSX reads it anymore. This
   is a real, flagged gap in the task's own IA, not something I
   introduced or fixed unilaterally.

2. "Most Viewed Products" table's 4th column: task says
   "Rank | Product | Views | Last Seen". No `lastSeen` (or any
   per-product timestamp) field exists anywhere on insightsProducts
   items (fields are: productId, productTitle, productPrice, views,
   uniqueViewers, addToCarts, cartRate, avgDwell -- confirmed in the
   immediately preceding structure audit). Since API call URLs may
   not change and no new fetch was added, "Last Seen" was substituted
   with "Avg time" (avgDwell), the same 3rd data column the original
   Insights table already showed. Flagging this substitution rather
   than fabricating a fake "last seen" value or silently dropping the
   column.

3. "AI Insight banner ... Text: narrative content" / "From
   weeklyNarrative (existing)". There is no `weeklyNarrative` state
   variable in this file, and the weekly-narrative endpoint's
   `.narrative` field (full prose) is fetched by the backend but never
   stored into any state -- only `.insights` (array of short strings)
   is captured, into `aiInsights`, and only `aiInsights[0]` was ever
   rendered by the original code. Kept that exact pre-existing
   behavior (aiInsights[0] under the "Weekly insight" label) since
   adding a new narrative state variable would violate "DO NOT change
   any state declarations."

4. Activity row "Number ... colored per type": ACTIVITY_STATS (the
   module-level const) has never included a `color` field for any of
   its 4 entries -- the original JSX destructured `color` from each
   entry and it was always `undefined`, silently falling back to
   `#111827` for every row. Since editing ACTIVITY_STATS itself is a
   module-level constant change (outside "JSX structure and inline
   styles," and the task's "DO NOT change" list does not explicitly
   permit touching data constants), per-type color was implemented
   instead as a small local lookup object (ACT_COLORS) defined at
   render time and referenced only inside the JSX, leaving
   ACTIVITY_STATS itself untouched.

5. "6 metric cards in 2 rows of 3": implemented as a single CSS grid
   with 6 items and 3 columns (`repeat(3, 1fr)` desktop), which wraps
   into 2 visual rows automatically, rather than two separately
   coded 3-item row `<div>`s. Same visual result, less duplicated
   markup.

6. KPI card "New Subscribers Today" shares the same `notifLoading`
   gate as the other 5 cards (all 6 render '-' while notifLoading is
   true), even though newSubscribers is fetched by a separate,
   independent polling effect with no loading flag of its own. Minor
   cosmetic inconsistency (this card may briefly show '-' even after
   its own data has already arrived, whenever notifStats is still
   loading) -- not fixed, since adding a new loading state would
   violate "DO NOT change any state declarations."

7. Sticky top bar: implemented with `position: sticky; top: 0;
   z-index: 10` on desktop (isMobileView === false) and
   `position: relative` on mobile, exactly per the "RESPONSIVE" note.
   Because it sits inside DS.page's own 24px top padding rather than
   at the true document edge, it will visually "jump" flush to the
   very top of the viewport once the user scrolls past that initial
   24px -- a normal, expected consequence of nesting a sticky element
   inside a padded container, not treated as a bug.

8. PageHeader() is still declared (per "DO NOT change any function
   definitions") but is no longer called anywhere -- the new sticky
   top bar has a different visual structure (title+date on the left,
   filter pills+Refresh on the right, no centered gradient underline)
   that does not match PageHeader's original centered-title design,
   so a literal reuse was not possible without contradicting the
   task's own explicit Section 1 layout. This also means the
   PageHeader gradient underline (`linear-gradient(90deg, #4f46e5,
   #818cf8)`) no longer renders anywhere in this screen, which is
   consistent with the "No gradients" design principle.

9. insightsError and todayError banners: the task's IA does not
   specify where these should appear. Kept both (removing them would
   silently drop existing error-surfacing behavior), placed at the
   most semantically relevant spot: insightsError just above the
   products table (left column, top), todayError just below the
   two-column section and above the new-subscribers alert.
