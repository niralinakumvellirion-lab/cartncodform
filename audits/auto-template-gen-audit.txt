1. WHEN to generate — RECOMMENDATION: option b (lazy on first visit)
─────────────────────────────────────────────────────────────────────────────

a) At install (OAuth callback):
   PROBLEM: The callback already does fetchShopInfo + fetchBrandData + registerAllWebhooks.
   Adding 3 LLM calls (or a Promise.all of 3) makes it slower and adds a new failure
   mode to install. If the LLM key is unset at install, the merchant gets no templates
   silently. Brand data IS available here (shopName, voice defaults), but voice has
   not been customised yet (all defaults). This is also the wrong moment — the merchant
   hasn't opened the email screen and doesn't know templates exist yet.
   VERDICT: don't touch the install path.

b) On first visit to the Email Templates screen, if no templates exist:
   - Frontend calls GET /api/email-templates → empty list
   - Frontend sees templates.length === 0 → triggers POST /api/email-templates/seed
   - Screen shows "Setting up your starter templates…" during the single request
   - 3 LLM calls in Promise.all ≈ 2-3 s total (each has 10s AbortController timeout)
   - On success: list renders with 3 templates + a one-time green notice
   - On failure: inline error with "Try again" button
   TRADEOFFS:
   + Zero install-path risk
   + Brand data (voice, shopName) may have been customised by the time the merchant
     reaches the email screen
   + Idempotent: if count > 0, skip immediately
   + Failure is recoverable and visible
   - ~2-3 s loading state on first visit (one time only)
   VERDICT: this is the right choice.

c) Button "Generate starter templates" on empty state:
   Explicit, but adds friction — the merchant has to discover and click it. Inferior
   to automatic lazy generation for a setup flow that should feel zero-effort.

RECOMMENDED: option b. Implement as a POST /api/email-templates/seed endpoint
that is idempotent (count > 0 → return existing templates, no generation).

─────────────────────────────────────────────────────────────────────────────
2. HOW MANY and which types — 3 templates (one per schema type)
─────────────────────────────────────────────────────────────────────────────

The EmailTemplate schema's `type` enum is locked to:
  ['special_offer', 'festival', 'normal']
Generate exactly one of each = 3 starter templates.

NAMES for the seeded templates (internal label, not subject line):
  special_offer → "Starter: Special offer"
  festival      → "Starter: <FestivalName> (upcoming)"   (see §6)
  normal        → "Starter: Welcome message"

PRODUCT TITLE — do NOT fetch a product:
  generateTemplateCopy accepts productTitle=null and the prompt handles it gracefully
  ("a note from our store" style). Adding a Shopify products API call here:
    GET /admin/api/2025-01/products.json?limit=1&fields=title
  is an extra dependency (auth token needed, store.accessToken), another failure mode,
  and unnecessary for a starter template the merchant is expected to personalise.
  For the festival type, use the festival NAME as productTitle instead (see §6) —
  it gives the AI useful context without a product lookup.

3. Reuses generateTemplateCopy — yes, loop in Promise.all
─────────────────────────────────────────────────────────────────────────────

Call signature already fits:
  generateTemplateCopy(shopDomain, storeName, type, productTitle, voice)

For the seed run:
  const [specialResult, festivalResult, normalResult] = await Promise.all([
    generateTemplateCopy(shopDomain, storeName, 'special_offer', null, voice),
    generateTemplateCopy(shopDomain, storeName, 'festival', festivalName, voice),
    generateTemplateCopy(shopDomain, storeName, 'normal', null, voice),
  ]);

RATE / COST:
  3 concurrent requests to Anthropic at ~500 tokens each = ~$0.01 per store seeded.
  Anthropic rate limit for claude-sonnet: 50 req/min (well within 3 concurrent calls).
  The 10s AbortController timeout per call is already wired in generateTemplateCopy.
  generateTemplateCopy never throws — fallback copies are returned on key-missing
  or timeout. So the seed endpoint is always safe to await.

COPY CACHE:
  CopyCache key includes shopDomain + type + productId(null for special/normal,
  festivalName for festival) + channel('email-template') + voiceHash.
  On the FIRST seed run: 3 cache misses → 3 LLM calls → 3 cache saves.
  On any accidental re-trigger (bug or direct API call): all 3 are cache hits →
  0 LLM calls. This is the natural replay protection, no extra work needed.

─────────────────────────────────────────────────────────────────────────────
4. Idempotency — count-first, no new schema field needed
─────────────────────────────────────────────────────────────────────────────

At the start of POST /api/email-templates/seed:
  const existing = await EmailTemplate.countDocuments({ shopDomain: req.shopDomain });
  if (existing > 0) {
    const templates = await EmailTemplate.find({ shopDomain: req.shopDomain }).sort({ createdAt: -1 });
    return res.json({ templates, seeded: false });
  }

This covers all cases:
  - Merchant has created their own templates manually → skip, return theirs
  - Seed already ran → return the seeded templates
  - Merchant deleted all templates → re-seed (intentional: empty = re-run)

No "starterSeeded" flag on Store, no migration. The empty list is the trigger
condition. If a merchant deliberately clears all templates, they get a re-seed
on next visit — that is useful, not a bug.

6. FESTIVAL TYPE — auto-pick next upcoming festival from festivals.json
─────────────────────────────────────────────────────────────────────────────

DATA AVAILABILITY:
  festivals.json is at backend/data/festivals.json and is already require()-able
  from any backend route (it's a static data file, no DB query).
  It is the same file the festival queue feature uses for the admin "upcoming"
  list. Today is 2026-10-06 → next entry is Navratri (2026-10-11).

  Helper (inline in the seed route):
    const festivals = require('../data/festivals.json');
    function nextFestivalName() {
      const today = new Date().toISOString().slice(0, 10);
      const f = festivals.find(f => f.date >= today);
      return f ? f.name : 'festive season'; // fallback if calendar exhausted
    }

  Pass the result as productTitle to generateTemplateCopy for the festival type.
  Effect: the AI prompt receives context like "festival: Navratri" and writes
  subject/body specific to that festival — far more useful than a generic
  "festival message".

FESTIVAL QUEUE (backend/models/FestivalQueue.js):
  The FestivalQueue holds per-shop approved push campaigns. It's NOT the right
  source here — new installs have an empty queue. festivals.json is correct.

TIMELINES:
  The festivals.json dates are yearly; the seed runs once per store and caches
  in CopyCache (TTL 24h by default). The festival template name will say
  "Navratri" for stores seeded this week, "Diwali" for stores seeded in 5 weeks,
  etc. — which is exactly what we want.
