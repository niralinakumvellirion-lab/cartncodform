  6. Write/update the per-style parity notes (comments in the registry
     + this style's two render implementations) so the admin preview and
     the storefront stay visually in sync — see
     audits/popup-style-audit-before.txt item 8 for why there's no
     shared render code between them.
  No database migration needed — Mongoose's subdoc defaults mean a shop
  that never touches the new style just keeps defaulting to Classic.

TO REMOVE:
  1. Delete the entry from frontend's POPUP_STYLES/STYLE_ORDER and its
     two render branches.
  2. Delete its id from backend/utils/popupStyles.js's STYLE_IDS/
     STYLE_EXTRA_FIELDS (so PATCH stops accepting it — an old saved
     value is simply treated as invalid on the next save attempt, same

  3. Delete its branch from the liquid file.
  4. Do NOT remove it from Store.js's enum retroactively — a shop that
     already has that id saved needs the field to remain a valid enum
     value so their document keeps loading without a Mongoose
     validation error; ccfResolveStyle()'s and StyleCardPreview's own
     fallback-to-classic guards already handle an id that's no longer
     "supported" by rendering Classic instead, which is the intended
     graceful degradation.

5. ASSUMPTIONS, SKIPPED ITEMS, KNOWN ISSUES
====================================================================
- "Discount expiry" countdown source shows NO ticking clock in either
  the initial popup OR the unlocked/code-revealed state, by design —
  see the long comment directly above renderDiscountCode() in the
  liquid file. Reasoning: before a customer redeems, there is no real
  per-customer expiry timestamp to count down to at all (only a
  duration-in-days, known from the Discounts config, becomes an
  absolute deadline once a code is actually minted) — consistent with
  decision #1's "if no real deadline exists, the timer is hidden".
  After redemption, the unlocked view auto-redirects in exactly 2
  seconds regardless of style (pre-existing behavior, untouched), so a
  live ticking clock there would move for under 2 seconds before the
  page navigates away — not meaningfully different from the existing
  static "Expires in N days" line already shown for every style. I
  chose not to add a redundant near-instant countdown on top of that
  already-real, already-honest fact. The genuinely live, real-time
  countdown IS fully implemented for the 'fixed_date' source, in the
  INITIAL popup, where it can actually be watched for as long as the
  popup stays open.
- The admin preview's countdown is NOT a live-ticking clock (no
  setInterval) — it's computed at render time and therefore updates on
  every edit/re-render, which happens on essentially every keystroke
  anyway. The STOREFRONT's actual popup does use a real setInterval
  (ccfStartCountdown), since real visitors watch it for much longer
  than a single admin edit. Disclosed simplification, not an oversight.
- "Isolated so admin styles don't leak in" (Phase 2C) was interpreted
  as "100% inline styles, no shared class selectors" — the existing
  convention every other screen in this codebase already uses — rather
  than an iframe sandbox, which would be a much larger, out-of-scope
  addition for a feature this size. No admin-global CSS class name is
  reused inside the preview.
- Card thumbnails (StyleThumbnail) are small abstract block mockups
  built from plain styled <div>s — not crops, screenshots, or traces of
  any reference image, and not raster/SVG assets requiring a build
  step, per the explicit instruction.
- "Style is selected per popup type" is implemented as "per desktop/
  mobile config", not as a new third dimension — see the checklist note
  above; this matches decision #3's literal storage instruction
  (popup.styleId / mobilePopup.styleId) rather than inventing a
  separate popup-type concept Phase 1 found no evidence this app
  actually has today.
- Two real, pre-existing-pattern bugs were found and fixed while wiring
  the storefront in (not part of the original ask, but necessary for
  correctness) — see section 6.
- Not tested in a live browser, live Shopify store, or against a real
  MongoDB instance — verification here is limited to the backend test
  suite and a clean production frontend build, per this task's "do not
  deploy" instruction.
- `theme` and `customTitle` (flagged as orphaned/unused-by-any-control
  in Phase 1) were left alone, as instructed.
- RECORDED FOR ROUND 2, NOT IMPLEMENTED HERE: decision #2 ("Editorial on
  mobile: renders as a stacked card, image on top, keeping its
  typography, divider, eyebrow and countdown") applies to a style that
  is not registered anywhere in this round — noted here only so it
  isn't lost before Editorial is actually built.

6. BUGS FOUND + FIXED DURING THIS CHANGE
====================================================================
Both are in push-notifications.liquid, both stem from the same root
cause: `layout` (popup.layout) is deliberately left untouched/stale
while a non-Classic style is selected (so switching back to Classic
restores it exactly), but two pieces of shared code downstream of the
layout if/else-if/else chain were still reading that possibly-stale
`layout` value directly:
  1. The shared discount-email-field insertion
     (`if (layout === 'split') { ccfBuildDiscountFields(); ... }`) could
     have double-inserted an email field into a Flash Sale/Gift Reveal
     popup (which already builds its own) whenever the shop's stored
     popup.layout happened to be 'split' — the schema's own default
     value, so this would have hit almost every shop that had never
     manually changed Classic's layout before trying a new style. Fixed
     by gating on `ccfStyle.id === 'classic' && layout === 'split'`.
  2. `wantsDiscount = layout !== 'banner' && ccfDiscountEnabled()` could
     have silently disabled the entire discount flow for Flash Sale/
     Gift Reveal (which are never actually banners) whenever the shop's
     stored popup.layout happened to be 'banner' from an earlier Classic
     session. Fixed by only applying the banner exclusion when
     `ccfStyle.id === 'classic'`.
Both were caught by tracing every remaining `layout ===` comparison in
showSoftPrompt() after adding the style branch, not by a test (this
file has no existing automated test coverage — it's a theme app embed,
outside backend/frontend's test runners).
