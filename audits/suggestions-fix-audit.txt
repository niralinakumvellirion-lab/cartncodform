FIX 1 — sidebar scroll: what was actually wrong vs. what the task
described
====================================================================
The task's own diagnosis was "the parent sidebar div may have
overflow: hidden preventing child scroll" and asked to "Fix the right
sidebar container: Change to: overflowY: 'auto' (not hidden)".

Checked the actual right sidebar container (the true outer 300px-wide
div, directly under the `{/* RIGHT sidebar — Notification Suggestions
+ Quick Stats (Part B) */}` comment): it already had `overflowY:
'auto'` — NOT `overflow: 'hidden'` — before this task started. No code
change was made there since there was nothing to fix; verified by
reading it directly rather than assuming the task's diagnosis was
correct.

The only actual `overflow: 'hidden'` anywhere near this area is on the
"Notification Suggestions" CARD wrapper (the white bordered/rounded
box that contains the header + festival list) — but that's a
different div than "the right sidebar container," and its
overflow:hidden serves a different, load-bearing purpose: clipping
the header/list's flat corners against the card's own `borderRadius:
12` (a very common, correct pattern — removing it would let sharp-
cornered content peek out past the rounded card edge). It was left
unchanged, since (a) the task's literal instruction named "the right
sidebar container," not this card, and (b) removing this specific
overflow:hidden risks a real visual regression (broken rounded-corner
clipping) for no requested benefit — the actual scroll region the task
names is the "suggestions card inner list div" (fixed below), which
manages its own maxHeight/overflow independently of this ancestor's
overflow:hidden in standard CSS (a child's own maxHeight+overflowY:
auto is respected regardless of an ancestor's overflow:hidden, as long
as the ancestor isn't itself height-constrained below the child's
capped height — which it isn't here, since the card has no explicit
height/maxHeight of its own).

What WAS changed, per the task's second, more concrete instruction
("Find the suggestions card inner list div. Make sure it has:
maxHeight: 'calc(100vh - 300px)', overflowY: 'auto', overflowX:
'hidden'"): the festival list div's style was updated from
`{ maxHeight: 400, overflowY: 'auto' }` to `{ maxHeight: 'calc(100vh -
300px)', overflowY: 'auto', overflowX: 'hidden' }`. This is a real,
concrete improvement regardless of the sidebar-container question
above: the previous hardcoded `400` px cap is now a viewport-relative
value, giving the list meaningfully more visible room on taller
screens (e.g. ~600px available on a 900px-tall viewport vs. the old
fixed 400px) while still capping and scrolling correctly on shorter
ones, and the added `overflowX: 'hidden'` prevents any stray
horizontal scrollbar from a wide emoji/name combination.

consequence of it, flagged per this session's standing practice of

three action buttons (Send Now / Approve / Add to Queue) were left
completely untouched — they still read `editorImageUrl` and send it
as-is:
  - Send Now -> POST /api/push/send-store { ..., imageUrl: editorImageUrl }
  - Approve / Add to Queue -> POST /api/queue/:shop/festival
    { ..., imageUrl: editorImageUrl }
This means an uploaded image now travels as a (potentially large,
hundreds of KB to a few MB) base64 string in the request body and, for
Approve/Add to Queue, gets stored verbatim in FestivalQueue.imageUrl
(a plain Mongoose String field — it will accept it, MongoDB's 16MB
document cap is very unlikely to be hit by one photo, but this is not
a true "image URL" any more — it's an inline blob, with no separate
hosting/CDN). This is a foreseeable, real side effect of FIX 2's own
literal design (converting file->data-URI client-side, matching
exactly what the task's given code does), not something this task's
scope asked to be solved (no backend upload/storage endpoint was
requested or added), and it was not silently worked around — send/
