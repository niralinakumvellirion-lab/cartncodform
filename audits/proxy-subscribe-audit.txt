SELF-AUDIT — proxy-subscribe

DEVIATION FROM LITERAL REQUEST
--------------------------------
Before implementing, read the full existing handler for
backend/routes/push.js POST /subscribe-customer (lines 114-179, as this
task instructed) and compared it against the literal proxy.js route given
in the prompt. The literal snippet was missing two pieces of behavior
present in the original:
  1. The same-cartToken dedup cleanup (deleteMany of other rows sharing
     cartToken but a different FCM token — prevents same-cart multi-row
     accumulation).
  2. The upsertProfile(...) identity-resolution call that feeds
     subscriptions into the profile/journey/attribution system.
Since this task also repoints ALL production subscribe traffic
(saveToken() and resyncCartTokenBeacon() in the liquid file) to this new
route, these omissions would have been a live functional regression, not
a parallel/unused path. Flagged to user via AskUserQuestion; user selected
"Add the route with full parity." Change below reflects that.

One additional deviation NOT flagged (informational only): unlike every
other route in proxy.js, the new /subscribe-customer route does not call
verifyProxySignature(req.query). This was left as given in the prompt and
not added, because the route it mirrors — backend/routes/push.js POST
/subscribe-customer — is also unauthenticated (confirmed in a prior
session turn), so this does not lower the actual security posture versus
today; it's simply inconsistent with this file's own established pattern
of guarding every other route with the App Proxy signature check.

FILE 1: backend/routes/proxy.js
---------------------------------
Added a new route, POST /subscribe-customer, immediately before
`module.exports = router;` (was the last line of the file). Body: the
literal route given in the prompt (shop/token validation, oldToken
