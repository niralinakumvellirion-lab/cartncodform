3. CONFIRM — Profile screen: identity, orders, signals, message history
================================================================================
frontend/app/admin/screens/Profile.jsx — props { shop, profileId, onBack }.
On mount: apiGet(`/api/profiles/${shop}/profiles/${profileId}`) -> { profile, signals }.
<Page title={email|phone|`Anonymous <id-6>`} backAction={{ content:'Customers',
  onAction: onBack }}>, with a critical <Banner> on load error.
<Layout>:
  - <Layout.Section variant="oneThird">:
      Card "Identity" — Stage Badge, one row per email, one per phone,
        "Push tokens" = identifiers.pushTokens.length, "Last seen" (en-IN date).
      Card "Orders" (in a Box paddingBlockStart="400") — Total orders,
        LTV (₹ en-IN), COD orders, Prepaid orders from profile.orders.*.
  - <Layout.Section>:
      Card "Active signals" — one bg-surface-secondary Box per signal:
        type (underscores -> spaces), strength Badge (critical >0.7 / warning
        >0.4 / info), each evidence line, "Expires <date>".
        Empty -> "No active signals."
      Card "Message history" (in a Box paddingBlockStart="400") —
        [...profile.messages].sort(sentAt desc), one Box per entry: type,
        "<channel> · <sentAt en-IN>", outcome Badge (converted=success /
        clicked=info / sent=default / else=warning). Empty -> "No messages sent yet."

DEVIATIONS:
  (a) `<Layout.Section oneThird variant="oneThird">` (spec) -> `variant="oneThird"`
      only (Polaris 13.9.5's Layout.Section reads `variant`, not the boolean;
      same finding as G1).
  (b) `sig.type.replace(...)` -> `sig.type?.replace(...) ?? 'signal'` (defensive;
      Signal.type is schema-required so this never fires in practice).
  (c) Badge `tone="default"` in the spec -> `tone={undefined}` (Polaris Badge
      has no 'default' tone value; undefined = the neutral default). Applied in
      Profile, Messages, CodOrders wherever the spec wrote 'default'.

6. CONFIRM — GET /api/profiles/:shop/messages route exists
================================================================================
backend/routes/profiles.js:
  + `const ScheduledJob = require('../models/ScheduledJob');`
  + router.get('/:shopDomain/messages', requireAuth, requireStoreOwner, ...)
    filter = { shopDomain, status: { $in: ['sent','skipped','failed','cancelled'] } }
    Promise.all([
      ScheduledJob.find(filter)
        .sort({ sentAt: -1, createdAt: -1 })         // spec: updatedAt -1 (absent field)
        .skip(page*limit).limit(limit)
        .select('profileId signalType channel payload status runAt reason cartToken sentAt createdAt updatedAt')
        .populate('profileId', 'identifiers stage'),
      ScheduledJob.countDocuments(filter),
    ]) -> { messages, total }
    limit default 50 / clamp 1..200 ; page default 0 / >= 0.
  requireStoreOwner enforces the token-shop vs path-shop IDOR check.

10. NOTICED BUT NOT TOUCHED  (out of scope for Phase G2)

  no timestamps). The /messages route and the Messages/Profile screens all

  ScheduledJob would be a clean fix and also help analyticsService (flagged
  since Phase B/E). Not done here.

  outcome is only ever 'sent' today (no PushClick -> 'clicked' wiring yet —
  Phase H). So the Profile message-history / Messages "outcome" badges will
  almost always read "sent". Same open item carried from Phase F.
- The Messages screen shows brain ScheduledJobs only meaningfully — legacy
  AutomationRule jobs (profileId null) appear as "Anon <cartToken-6>" with a
  blank Signal cell (falls back to `reason` which is '' for legacy jobs, then
  '—'). Acceptable; legacy scheduler retirement is a Phase C open item.
- CodOrders reuses GET /api/stores/:shop/orders and PATCH /api/cod/order/:id —
  both pre-existing. No dedicated COD list route was added.
- No pagination UI on Customers / Messages / COD (the routes support
  limit/page; the screens fetch page 0 only). Prototype has no pager either;
  add when a store exceeds ~50-200 rows.
- Customers still has no search / stage filter (prototype has both) — G1 open
  item, still open.
- Settings screen is still the bare `<Box>… coming soon` stub. The prototype's
  Settings (voice/caps/quiet-hours/channels) + Onboarding + "What to act on"
