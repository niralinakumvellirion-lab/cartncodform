7. RISKS AND OPEN QUESTIONS
================================================================================

7a. Would fail / jeopardise Shopify App Store review
  R1. PII in logs (§3a): customer email / name / phone printed to stdout
      (Render logs). Shopify's Protected Customer Data requirements expect PII
      minimisation in logs. Must be scrubbed before submission.
  R2. The dead `stores.js GET /` route (§3b): requireAuth-only, filters on a
      field that is always undefined post-auth-swap. A reviewer poking the API
      surface will find an endpoint that behaves undefinedly. Remove it.
  R3. shopify.app.toml only declares the `compliance` webhook subscription.
      carts/*, checkouts/*, orders/create, app_subscriptions/update,
      app/uninstalled must be registered (currently presumably at runtime on
      install). If runtime registration is flaky, GDPR/mandatory topics look
      fine but the product topics don't fire — verify on a fresh install.
  R4. `read_inventory` is NOT in access_scopes, and `products/update` is not a
      declared webhook — back_in_stock / price_drop signals can never work
      without a scope change + review re-approval. They are stubs today, so
      this is a "known future" not a blocker, but note it.
  R5. localStorage in the embedded admin (§3c): Safari / embedded-iframe
      storage partitioning can make it silently no-op; not a review blocker but
      a functional risk and a self-imposed-rule violation.

7b. Passes on the dev store, would fail / do nothing on a real store
  R6. THE SIGNAL ENGINE PRODUCES ZERO SIGNALS IN THE LIVE DB (§6). Everything
      downstream (brain, brain-scheduled sends, AI copy at send time, the
      Today "what to act on" card, Customers signal counts, Messages showing
      brain sends) is therefore inert. On a real store with traffic the
      ingest-time trigger would fire on carts/* — but the nightly recompute
      (the only thing that produces browse/high-intent/lapsing/etc.) is an
      in-process setTimeout that resets on every Render restart and never runs
      on a sleeping free dyno. Move it off the free tier AND/OR use a real
      scheduler (node-cron / an external ping).
  R7. Two schedulers run in parallel (legacy AutomationRule + brain). On a
      real store with an active rule, a cart could get both a legacy reminder
      and (once signals work) a brain message — double-messaging, and the
      legacy one uses the hard-coded 22:00-08:00 / 3-per-24h caps, not
      Store.caps. Retire the legacy path.
  R8. `LLM_API_KEY` unset -> every AI message is the same generic fallback
      line ("You left something behind" / "We saved your cart"). The whole
      "AI writes the message in your voice" value prop is off until the key
      (and LLM_MODEL=claude-sonnet-5) is set in Render.
  R9. Brain email sends: the poller's email branch looks up an AbandonedCustomer
      by cartToken to get an address. A brain email job for a profile whose
      email lives only in Profile.channels.email.address (no matching abandoned
      cart) will `skip` with "No customer email for this cart". Brain email is
      effectively non-functional for non-cart profiles.
  R10. Push suppression is over-aggressive (§Phase F caveat): with outcome
      never set to 'clicked', every brain-pushed profile is force-unsubscribed
      after maxUnopenedPush sends + 7 days, and only a storefront page_view
      brings it back. On a real store this will quietly shrink the push
      audience.
  R11. generateCopy's blocking fetch inside the 30s poll loop (§Phase E): a
      slow Anthropic response stalls the whole scheduled-job poller.

7c. Skipped, or interpreted differently from the plan
  R12. Phase C did NOT delete AutomationRule / the trigger enum (only the admin
       step editor). The backend legacy scheduler is fully intact.
  R13. Brain ranking is "highest strength wins", not the plan's
       EV = strength × baseValue × reachability × shopConversionRate. There are
       no per-signal base values or per-shop conversion rates anywhere.
  R14. Send-time re-validation re-checks only runAt, not "signal still true /
       didn't buy / still in stock" (plan Part 3).
  R15. Phase A did not turn AbandonedCustomer into a Profile view; it remains a
       parallel primary table read by 5+ call sites.
  R16. Phase E's file is services/aiService.js, not the CLAUDE.md-named
       utils/ai.js (cosmetic, single-location respected).
  R17. Phase G is missing the Insights screen entirely and the grouped
       "What to act on" screen — the two places the plan says dwell/scroll and
       per-signal economics get surfaced to the merchant.
  R18. Phase H never started (no prompt issued).
  R19. Storefront prompt events are logged via /api/events, not the
       /cart-activity beacon the phase prompt named (functionally fine, lands
       in StorefrontEvent either way).
  R20. Nightly jobs (signals, brain, pushStats reset) all hang off ONE
       self-rescheduling setTimeout at 02:00 server-local. If it throws or the
       process restarts near 02:00, a whole night is skipped silently.

    the free tier so the dyno doesn't sleep. Add a manual "recompute signals

    the scheduleCartAbandonJobs call in webhooks.js, and the `ref:'AutomationRule'`

    instead of the hard-coded 22-08 / 3-per-24h. One scheduler, one set of caps.

    outcome='clicked'; on an attributed order -> outcome='converted'. Without

    "[ai] cache hit" log lines and the cache hit rate).
