--- 2. WhatsApp ScheduledJob fields ---

Created by POST /api/whatsapp/:shop/send (whatsapp.js:382-395):
  channel: 'whatsapp'
  status:  'sent'           ← always immediately 'sent', never pending
  sentAt:  new Date()
  profileId, shopDomain, runAt, stepIndex
  purpose: 'followup' | 'order'
  origin: 'manual', sentBy: 'owner'
  — NO signalType, NO payload, NO reason, NO cartToken set at creation.

Then updated (whatsapp.js:423):
  messageText: message.slice(0, 1000)   ← final WhatsApp message text

ScheduledJob model (models/ScheduledJob.js):
  payload: Mixed (not set for WA)
  purpose: String (set for WA: 'followup'|'order')
  messageText: String (set for WA: the actual message body)

Status values for WA jobs: only 'sent' (created directly as sent).
Outcome: null initially; can become 'clicked' (attribution/click endpoint
  sets outcome='clicked' when visitor follows the ccf_job link) or
  'converted' (webhooks.js order handler sets outcome='converted' and
  recoveredRevenue when an order is placed after a click).

Attribution: ccf_src=whatsapp is appended to ctaUrl (whatsapp.js:398-400).
  The /api/attribution/click endpoint sets outcome='clicked' on the job.
  Conversion is tracked via webhooks. So outcome can be 'clicked' or
  'converted' for WhatsApp jobs just like for push/email.

--- 3. Festival WhatsApp broadcast tasks ---

FestivalQueue items with channel='whatsapp' are NEVER marked 'sent' by
the system. The processFestivalQueue poller query (server.js) explicitly
excludes whatsapp items (confirmed by addEngagement.test.js line 429-440:
"FestivalQueue.find filters out whatsapp — item not in dueItems list").

These items stay in 'draft' or 'approved' status — they appear as Dashboard
manual tasks for the merchant to act on. When a merchant manually sends
them in WhatsApp, the action is recorded as an individual ScheduledJob (via
POST /api/whatsapp/:shop/send) if they click from CustomerDetail, but the
FestivalQueue item itself is never updated to status='sent'.

Data available on FestivalQueue whatsapp items: title, body, scheduledAt,
festival (if any). But since they never reach status='sent' there is no
message actually sent to show. These items will be SKIPPED in this
implementation — nothing to show on the Messages page for them.

--- 4. Status chips and "Led to a sale" ---

getStatusConfig(status, outcome, revenue) maps:
  outcome='converted'   → "converted · ₹{revenue}" (green)
  outcome='clicked'     → "clicked" (gray)
  status='skipped'      → "skipped — bought first" (italic gray)
  status='failed'       → "failed" (red)
  status='pending'      → "scheduled" (yellow)
  outcome='opened'      → "opened" (gray)
  default               → status==='sent' ? 'delivered' : status (gray)

For WhatsApp: status='sent', outcome=null/undefined → "delivered" (WRONG).
Fix: override to "opened in WhatsApp" when channel=whatsapp and label=delivered.

If attribution exists (outcome='clicked'/'converted') → existing chips are
correct and apply to WhatsApp too.

"Led to a sale" filter: frontend client-side pass m.outcome==='converted'.
WhatsApp jobs can have outcome='converted' (via attribution), so they
correctly appear in this tab. Backend returns all channels for this tab
(no channel filter sent).
