QUERY ANALYSIS — confirmed NOT N+1
  The second find is issued ONCE per page load, against a $in of at most
  200 sessionIds and 200 customerIds. Tagging is done in-process via Set
  lookup. Total: 2 queries per request (unchanged from the original 2
  for find+countDocuments, now 3 counting the accepted query).

INDEX REPORT
  Added: (shopDomain, type, sessionId)
  Reasoning: the accepted query filters on all three fields; without this
  index MongoDB would scan all events for the shop+type and then filter
  by sessionId in memory.

  (shopDomain, type, customerId) — NOT added.
  Reason: ~70-80% of popup views are anonymous (no customerId). In the
  $or path, MongoDB can do an index intersection with separate indexes per
  branch, but the customerId branch is the minority. When sessionIds are
  present, the existing index already narrows the scan significantly. The
  marginal gain from a second index does not justify the write overhead on
  every push_prompt_accepted insert. Revisit if the proportion of
  identified visitors increases substantially.
