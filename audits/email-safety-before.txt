Q2 — Profile.suppressed reads and writes; what it blocks
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Where suppressed is WRITTEN:
  - services/pushHygiene.js:112–114: set suppressed=true on Profile after
    too many consecutive unopened push notifications (push-hygiene engine).
    Despite the name, this field was repurposed as a global block.
  - There is no existing "unsubscribe" endpoint that sets it from email.
    The only writes today come from the push-hygiene engine.

Where suppressed is READ (what it blocks):
  - services/brain.js:153: runBrainForProfile() returns null immediately →
    NO automation scheduled at all (push, email, WhatsApp) for that profile.
  - services/brain.js:342: excluded from "all profiles" batch run →
    ditto.
  - services/signalEngine.js:338,385: returns [] immediately → no signals
    detected, no ScheduledJob rows created.
  - routes/push.js/sendJourneyEmail:536: 400 error → no journey email.
  - routes/emailTemplates.js/buildEmailSegmentQuery:56: suppressed:{$ne:true}
    → excluded from template sends and broadcasts.
  - utils/emailBroadcast.js/buildEmailSegmentQuery:39: same.

CONCLUSION: suppressed blocks ALL automated channels — push, email, and
  WhatsApp automation — not just email. This is because brain.js and
  signalEngine.js are the scheduling layer for all three. Setting
  suppressed=true via the unsubscribe endpoint will also stop push and
  WhatsApp automations for that profile. This is not changed by this work;
  the Part A spec says "do not change what suppressed means elsewhere" and
  notes this in the audit instead.

Q3 — Public backend URL and signing secret
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Backend URL env var: BACKEND_URL
  Default: https://cartncodform-backend.onrender.com (.env.example:6)
  Used for unsubscribe URL: ${BACKEND_URL}/api/unsubscribe/${token}

Signing secret: SHOPIFY_API_SECRET
  This is the only stable shared secret in the env file suitable for HMAC
  signing. No dedicated JWT_SECRET or APP_SECRET exists. SHOPIFY_API_SECRET
  is already used for Shopify webhook HMAC verification (routes/webhooks.js)
  and is never exposed to customers.

Q4 — processFestivalQueue overlap guard
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

NO overlap guard exists. processFestivalQueue() (server.js:650):
  - Queries FestivalQueue.find({status:'approved', scheduledAt:{$lte:now}, ...}).limit(20)
  - Iterates and sends each item in a for loop (sequential, not atomic)
  - No running flag, no per-item claim field, no advisory lock
  - Poller fires every 30 seconds (server.js:818: setInterval(runPollerTick, 30*1000))

Risk scenario: an email broadcast to 90 recipients at ~0.5s/call (Resend API)
takes ~45 seconds. The next tick fires at 30s. Both ticks fetch the same
'approved' item from MongoDB, and both send to all 90 recipients.
