3. push_prompt_shown / push_prompt_accepted logging — HOW
================================================================================
DEVIATION FROM STEP 3/5 (endpoint): the spec says log these "via the
/apps/cartncodform/cart-activity beacon". That route (backend/routes/push.js
POST /cart-activity) ONLY stamps CustomerPushSubscription.lastEvent — it has
NEVER written a StorefrontEvent and takes no `meta` field. STEP 6's
/optin-stats reads StorefrontEvent. So the two prompt events are logged through
the liquid's EXISTING trackEvent() -> flushEvents() -> POST /api/events pipe,
which backend/routes/events.js writes straight to StorefrontEvent with
{ type, meta, sessionId, ts }. This lands them exactly where /optin-stats looks,
with meta = { trigger, productId } / { trigger, granted }.
Result: /cart-activity is UNCHANGED (honours STEP 5's "No other changes"), and
routes/events.js already accepts any `type` with no filter (line ~34:
`type: e.type || 'unknown'`), so nothing to remove there.

10. NOTICED BUT NOT TOUCHED  (out of scope for Phase D)
================================================================================
- STEP 3/5 assumed /cart-activity writes StorefrontEvent; it does not. Rather
  than change /cart-activity (STEP 5: "No other changes"), prompt events go via
  /api/events. If a future phase wants ALL cart-activity events in StorefrontEvent,
  that route needs its own change.
- The soft prompt's "Allow" path reuses saveToken()/registerSW()/getToken()
  which still target-by-cartToken on the backend. A profile-/pushToken-targeted
  send path is a Phase E/F concern (already flagged in the Phase C audit).
- RETURN VISIT stores raw productIds in localStorage 'ccf_viewed_products'
  unbounded-ish (capped at 200, slice(-200)). First-party storefront storage,
  per the handover rule "Storefront localStorage is fine".
- The DWELL timer and EXIT INTENT listener are registered even after the prompt
  has shown once (canPrompt() short-circuits inside showSoftPrompt, so they
  just no-op). Minor; not leaking (exit-intent listener removes itself on first
  qualifying move).
- No A/B or before/after opt-in-rate comparison is built — /optin-stats gives
  the raw shown/accepted/rate; the "measurably above baseline" judgement is the
  owner's to make from live data (handover "Done when").
- {% schema %} trim: if the owner wants to keep the old copy settings for a
  future re-use, they are gone from git history's working copy (still in the
  pre-Phase-D commit). Flagged as a deviation in §2.
- CodOrder.email has no format validation (matches how name/phone/address are
  declared — plain trimmed strings). A malformed email just won't produce a
  usable channels.email.address downstream.

11. OPEN QUESTIONS
================================================================================
1. Confirm routing prompt events through /api/events (not /cart-activity) is
   acceptable — it is the architecturally correct pipe, but diverges from the
   literal STEP 3/5 wording.
2. {% schema %} trim — OK to drop the 10 popup_* settings entirely, or keep
   them (inert) to preserve any merchant-customised values?
3. DWELL copy needs a product title. On themes where
   window.ShopifyAnalytics.meta.product is absent AND {{ product.title }} is
   empty (rare custom product templates), the copy falls back to
   "this product". Acceptable?
4. EXIT INTENT uses a raw document 'mousemove' listener (not passive-flagged
   for clientY reads). Negligible perf cost; leave as-is?
5. Should push_prompt_accepted with granted:false also set a longer-lived
   suppression than the session (e.g. localStorage for N days)? Currently a
   denied native prompt is browser-permanent anyway, and a dismissed soft
   prompt is session-only.
6. STEP 7 owner command: `shopify app deploy --allow-updates` — confirm the
   `--allow-updates` flag is what this Shopify CLI version expects (vs a plain
   `shopify app deploy` which prompts).
