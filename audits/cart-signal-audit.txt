     This is what actually links the event batch's sessionId/customerId/
     token into a Profile document's identifiers (via
     services/profileService.js's identity-resolution logic, which

     never extracts one from the request body).

So: identifiers used to link an incoming event to a profile = sessionId,
customerId, pushToken (called `token` in the request body). cartToken is
NEVER used or even read anywhere in this file's POST / handler.

SUMMARY - how this all connects (read-only synthesis, no code changed)
====================================================================
- cart_abandon (Part A) depends ENTIRELY on profile.identifiers.cartTokens
  being populated -- it never looks at sessionIds, and it never queries
  StorefrontEvent at all (it queries AbandonedCustomer instead).
- The generic event-ingest route, POST /api/events (Part B), is one of
  the main paths that calls upsertProfile() to build up a profile's
  identifiers -- but it ONLY ever supplies sessionId, customerId, and
  pushToken to that call. It never reads or forwards a cartToken, for
  ANY event type, including 'add_to_cart'.
- Profile.identifiers.cartTokens (Part C) is therefore populated by some
  OTHER ingest path than this one (e.g. the push-subscription routes,
  per earlier audits) -- not by the generic /api/events pipe that
  add_to_cart events flow through.
- Net effect: an add_to_cart event alone, ingested via POST /api/events,
  does not by itself cause profile.identifiers.cartTokens to gain an
  entry -- so cart_abandon cannot fire off of that ingestion path alone,
  regardless of how many add_to_cart events a profile has, unless a
  cartToken reached that profile via a different route.
