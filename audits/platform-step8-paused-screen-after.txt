EVERY PLACE THE MERCHANT FRONTEND CALLS THE BACKEND
════════════════════════════════════════════════════════════════════════════════

All merchant admin calls flow through frontend/lib/api.js. Two exported
helpers cover the entire admin codebase:

  apiGet(path)     — GET calls with session-token auth, 401-retry
  apiSend(path, method, body) — POST/PATCH/DELETE with session-token auth, 401-retry

EXCEPTION — three direct fetch() calls that bypass the helpers (needed because
they download binary blobs or use a fine-grained abort controller that the
helpers do not expose):

  File                                   Line   Purpose
  ─────────────────────────────────────  ─────  ───────────────────────────
  app/admin/screens/Customers.jsx        215    count API (count export matches)
  app/admin/screens/Customers.jsx        272    download all matching customers (.xlsx)
  app/admin/screens/CustomerDetail.jsx   2479   download single customer activity (.xlsx)

HOW EACH CALL NOW REACHES DETECTION

  apiGet   — !res.ok path: reads res.text(), parses as JSON, calls
             checkSuspended(res.status, bodyJson) before throwing.
           — 401-retry !retryRes.ok path: reads retryRes.json(), calls
             checkSuspended(retryRes.status, err) before throwing.

  apiSend  — !res.ok path: already reads res.json() into `data`; calls
             checkSuspended(res.status, data) before throwing.
           — 401-retry !retryRes.ok path: reads retryRes.json() into `err`;
             calls checkSuspended(retryRes.status, err) before throwing.

  Customers.jsx:215 (count)
           — !res.ok path already read res.json() into `body`;
             checkSuspended(res.status, body) added before setCountError.

  Customers.jsx:272 (bulk export)
           — !res.ok path already read res.json() into `body`;
             checkSuspended(res.status, body) added before setDlError.

  CustomerDetail.jsx:2479 (single export)
           — was `if (!res.ok) throw new Error('Export failed')`;
             changed to read res.json() into `body`, call
             checkSuspended(res.status, body), then throw.
             The res.blob() call is on the success path and is unaffected.

No other file directly calls fetch() against BACKEND_URL. Confirmed by
grepping all of frontend/app/admin for `fetch(` — only the three above appear.

checkSuspended — FUNCTION DESIGN AND TEST CASES
════════════════════════════════════════════════════════════════════════════════

Location: frontend/lib/api.js (exported function)

Algorithm:
  1. Return immediately if status !== 403
  2. Return if body is null, not an object, or an array
  3. Return if body.code !== 'STORE_SUSPENDED'
  4. Return if typeof window === 'undefined' (SSR context)
  5. Return if module-level _suspendedFired flag is true (idempotent)
  6. Set _suspendedFired = true
  7. window.dispatchEvent(new Event('ccf:store-suspended'))

The _suspendedFired flag is module-level so it survives hot-reloads in dev
but resets on a real page navigation (module is re-evaluated). No side
effect other than the dispatch.

Test file: backend/__tests__/checkSuspended.test.js
Runner:    Jest in backend/ (existing runner, no new config)
Note:      The function is redefined inline in the test file because
           frontend/lib/api.js uses ES module syntax (export function) and
           the backend Jest runs CommonJS. The test exercises the identical
           algorithm.

Test case                                          Result
─────────────────────────────────────────────────  ──────
403 + code=STORE_SUSPENDED                         PASS — dispatches once
Idempotent: called twice                           PASS — dispatches once
After reset, fires again                           PASS
403 + different code                               PASS — no dispatch
403 + no code field                                PASS — no dispatch
402 + code=STORE_SUSPENDED                         PASS — no dispatch
401 + code=STORE_SUSPENDED                         PASS — no dispatch

Non-JSON body (string)                             PASS — no dispatch
null body                                          PASS — no dispatch

SuspendedGate — DESIGN NOTES
════════════════════════════════════════════════════════════════════════════════

Location: frontend/app/admin/components/SuspendedGate.js
Used in:  frontend/app/admin/layout.js wrapping {children}

Behaviour:
  - Listens for 'ccf:store-suspended' on window (cleanup on unmount).
  - While not suspended: renders <>{children}</> — a React fragment with
    no DOM wrapper; layout is identical to before this change.
  - Once suspended: replaces full content with the paused card.

Paused card:
  - Centred in full viewport height (#F1F0EF background).
  - White card, border-radius: 12px, inline styles (Polaris not guaranteed
    to be initialised when the card appears).
  - Pause SVG icon (two vertical rectangles inside an indigo circle),
    aria-hidden="true".
  - role="alert" on the heading container.
  - h1 "Your account is paused", tabIndex={-1}, focused via useEffect when
    suspended becomes true — screen readers announce immediately.
  - No suspension reason, note, date or staff name shown.
  - "Contact support" — <a href="mailto:SUPPORT_EMAIL"> (styled as primary
    indigo button, 44px-equivalent touch target).
  - "Check again" — <button onClick={() => window.location.reload()}>
    (styled as secondary button).
  - Does NOT call window.shopify.* or any App Bridge API.

OTHER ERROR PATHS — UNCHANGED BEHAVIOUR
════════════════════════════════════════════════════════════════════════════════

  403 without code=STORE_SUSPENDED  — checkSuspended returns early; the
    existing throw/error-setter behaviour is unchanged.
  402 — not 403; checkSuspended returns early; caller behaviour unchanged.
  401 — handled by the 401-retry block before reaching checkSuspended;
    if the retry also 401s, it throws as before (no suspend dispatch).
  200, 201, other 2xx — res.ok is true; checkSuspended is never called.
  Network errors — throw from fetchWithTimeout; checkSuspended not called.
  Non-JSON body on error — JSON.parse failure caught; bodyJson stays {};
    body.code is undefined; checkSuspended returns early.

════════════════════════════════════════════════════════════════════════════════
WHAT CANNOT BE VERIFIED WITHOUT A BROWSER AND A SUSPENDED DEV STORE
════════════════════════════════════════════════════════════════════════════════

1. End-to-end flow — the merchant must make ANY API call (e.g. loading the
   dashboard) with the store suspended for the backend to return 403 +
   { code: 'STORE_SUSPENDED' }. Only then does the event fire and the gate
   appear. Cannot be simulated without a real suspended store.

2. Focus management — headingRef.current.focus() runs when suspended becomes
   true. Screen reader announcement via role="alert" depends on the browser's
   accessibility tree flushing correctly after the state change. Code-correct
   but unverified in an actual browser.

3. mailto: link — opens the user's default email client. Correct on desktop
   but may be a no-op on some mobile Shopify admin setups.

4. App Bridge coexistence — when the paused page appears, App Bridge is still
   loaded (the <script> tag is in the layout head). The paused page doesn't
   call window.shopify.*. The risk is App Bridge emitting errors about missing
   initialisation hooks now that its expected DOM is gone. This cannot be
   tested without a live embedded session.

5. Hot-module reload in dev — the module-level _suspendedFired flag persists
   across HMR because the module is not re-evaluated. If a developer suspends
   in dev and then unsuspends, reloading the page (via "Check again") resets
   the flag correctly. This is the intended behaviour.
