3. HOW TO ADD/REMOVE A STYLE (updated from the registry file's own
   header comment, restated here per the task's request)
====================================================================
ADD:
  1. frontend/app/admin/lib/popupStyles.js — one POPUP_STYLES entry
     (id/name/shortDescription/bestFor/layoutType/supportedFields/
     extraFields/defaultValues), add the id to STYLE_ORDER, and to
     MOBILE_ONLY_STYLE_IDS if it's device-restricted.
  2. frontend/app/admin/screens/Settings.jsx — one GALLERY_CARDS entry,
     one StyleCardPreview render branch (before the flash_sale check),
     and if it's mobile-only, no other change is needed — the gallery
     filter and the force-override-on-select logic already key off
     MOBILE_ONLY_STYLE_IDS generically.
  3. extensions/cartncodform-embed/assets/ccf-push.js — add the id to
     ccfResolveStyle()'s CCF_KNOWN_STYLE_IDS (and CCF_MOBILE_ONLY_STYLE_IDS
     if device-restricted), one render branch inside showSoftPrompt()
     (before the classic layout chain), and if it needs the
     'no unlocked-code room' banner treatment, add it to the
     wantsDiscount check the same way top_bar was added.
  4. backend/utils/popupStyles.js — add the id to STYLE_IDS (and
     MOBILE_ONLY_STYLE_IDS if applicable) and its STYLE_EXTRA_FIELDS
     entry.
  5. backend/models/Store.js — add the id to popup.styleId's enum and
     mobilePopup.styleId's enum.
  6. Add resolveStyleId tests for the new id (backend/__tests__/
     popupStyles.test.js already parametrizes over MOBILE_ONLY_STYLE_IDS,
     so a mobile-only addition is covered automatically by the existing
     test.each blocks — no new test code needed unless it's NOT
     mobile-only, or has extra fields worth asserting on directly).

REMOVE: delete the entry/branches everywhwere ADD touched — do NOT
  remove the id from either Store.js enum retroactively for shops that
  already saved it (breaks their save until they re-pick); leave the
  renderers' existing unknown-id fallback (already falls back to
  Classic) to handle it once the registry entry is gone.

5. ASSUMPTIONS
====================================================================
- "Mobile-only" is enforced by (a) hiding the cards from the Desktop
  tab's gallery and (b) resolveStyleId falling back for a desktop
  context regardless of how an id got into either styleId field — NOT
  by rejecting the enum value at the backend for popup.styleId (desktop
  field). A direct API write could still put a mobile-only id in
  popup.styleId; it would just never actually render there, on any of
  the three resolution points the task named. This was an explicit,
  discussed trade-off (Q2 in the Phase 1 proposal), not an oversight.
- Icon art for Bottom Sheet's no-image fallback reuses the existing
  'gift' icon (ccfIcon('gift', ...) / <Icon name="gift" .../>) rather
  than a new bespoke icon — no new SVG path was added in either file.
- Story Card's aspect-ratio (9/16, a tall "story" shape) and Full
  Screen's minInvocation via full-viewport `inset:0` both assume modern
  CSS support (aspect-ratio, env(safe-area-inset-*)) already implicitly
  assumed elsewhere in this codebase (the mobile-popup feature itself
  is scoped to <=600px devices, which are all modern enough).

6. KNOWN ISSUES
====================================================================
- Full Screen's close-X is 44x44 on the REAL storefront (ccf-push.js,
  unconditional, not compact-scaled) — this is what the task's touch-
  target requirement is actually about, and it's correct. The ADMIN's
  own interactive preview shows a 36x36 version inside its scaled-down
  phone-frame mockup (the same `compact` sizing convention every other
  close button in that preview already uses at smaller scale) — this
  is a preview-only illustration, not a real touch surface, so it was
  left as-is rather than special-cased to render literally 44px inside
  a ~200px-wide mockup.
- Full Screen's page_load suppression, as implemented, has a real
  practical reachability gap inherited from the trigger system's OWN
  existing constraints (not something this task introduced or was
  asked to fix): initIntentTriggers() returns immediately for ANY
  product-type page (`if (pageType === 'product') return;`), so
  dwell/return_visit never run on mobile at all today (matching the
  pre-existing comment in that function calling them "unreachable dead
  code"), and exit_intent is hard-gated to `window.innerWidth > 768`
  (desktop only) a few lines below. That leaves add_to_cart (wired
  separately from cart-add hooks) as the ONLY trigger realistically
  capable of showing Full Screen to a mobile visitor today. This
  satisfies the letter of the requirement ("never page_load... must
  require the existing intent triggers") but means Full Screen will,
  in practice, rarely fire automatically until/unless the trigger
  system's mobile-specific gaps are addressed separately — flagged
  here rather than silently shipping a style that looks broken in
  practice. Out of scope for this task to fix (the task named a single
  constraint on ONE style, not a trigger-system overhaul).
- supportedFields (all 7 styles, not just the 4 new ones) remains
  documentation-only — Settings.jsx never reads it to hide/show a
  field. Top Bar's own supportedFields excludes subtext/denyText/
  imageUrl, but the ADMIN'S generic Position SelectRow, for instance,
  still renders for every style regardless of supportedFields (a
  pre-existing gap for flash_sale/gift_reveal too, unrelated to this
  task, not newly introduced).
- ccf-push.js's new render branches were verified by `node --check`
  (syntax) and close manual comparison against the existing flash_sale/
  gift_reveal branch's own patterns (same helper functions, same
  escaping convention — textContent for every merchant string, never
  innerHTML with unescaped merchant input; the only innerHTML usage
  added, ccfIcon('gift', 40), is a hardcoded icon-markup lookup, not
  merchant-derived). They were NOT loaded in an actual browser against
  a real Shopify theme/storefront — no live dev store was available in
  this sandbox. Recommend a real-device check (phone width, actual
  Shopify preview) before shipping, per the deploy commands below.
