================================================================================

    upsertProfile(shop, {...ids}, {...updates})
      .catch((err) => console.error('[profile] upsert error:', err.message));

6. IMPLEMENTATION NOTES / DEVIATIONS FROM THE LITERAL SPEC
================================================================================
(a) Profile.js schema: implemented verbatim as given, including the
    `identifiers.customerId` scalar (all other identifier fields are arrays),
    `interests` as Map<String,Number>, `messages` sub-doc with outcome enum,
    and all 7 indexes (6 sparse identifier indexes + { shopDomain, updatedAt:-1 }).

(b) profileService.upsertProfile — algorithm matches steps 1–8:
    - $or query built only from non-null/non-empty identifiers (+ shopDomain).
      `cleanIdentifiers` trims, drops empties, lower-cases email.
    - 0 matches -> Profile.create(seed) then applyToProfile (so $inc/$set/$addToSet
      + stage + messagecap run through one code path).
    - 1 match -> $addToSet new identifier values, $set scalar customerId only if
      absent, apply updates, updatedAt.
    - N matches -> rank each by the highest-priority identifier it already holds
      (customerId=0 … pushToken=5), tie-break by createdAt asc (oldest wins);
      $addToSet all identifier arrays from losers into the winner, set winner's
      scalar customerId if it had none, concat+sort(desc by sentAt)+slice(20) the
      messages, delete losers, then re-apply this call's own ids+updates.
    - stage recomputed every call via nextStage(): customerId OR orders.count>0
      -> 'customer'; else email/phone -> 'identified'; else 'anonymous'. Never
      downgrades — STAGE_RANK {anonymous:0, identified:1, lapsed:2, customer:3},
      keep current if its rank >= candidate's. ('lapsed' is never *set* here — it
      is a Phase B/C nightly concern — but it is protected from downgrade.)
    - messages capped to 20 (newest first) after every write.
    - stage/messagecap applied in a second small findOneAndUpdate only when they
      actually change (keeps the common path to one write).

(c) DEVIATION — spec step 5c updates object had TWO `$inc` keys in one object
    literal (`{ $inc: {count,ltv}, ...(isCod ? {$inc:{codCount}} : {$inc:{prepaidCount}}) }`).
    JS collapses duplicate keys, so `orders.count`/`orders.ltv` would be lost.
    Fixed in the caller (webhooks.js handleOrderWebhook): a single merged
    `orderInc` object is built and passed once. splitUpdates() also defensively
    merges repeated operator keys if they ever arrive separately.

(d) DEVIATION — spec 5c/5b/5e reference local vars that don't exist verbatim
    (`payload`, `sessionId`). Used the real equivalents: `req.body` for the
    webhook payload, `doc.sessionId` for the cart handler's cart token,
    `normalizedCartToken` in /subscribe-customer. /cart-activity's destructure
    was widened to also read `ccfSessionId` and `cartToken` (the storefront
    beacon may not send them yet — Phase D reworks the storefront; until then
    that call resolves on pushToken alone, which is fine).

(e) `isCod` in handleOrderWebhook is a heuristic:
    order.payment_gateway_names[] + order.gateway, lower-cased, contains
    "cash on delivery" or "cod". May need tuning per gateway naming.
    `orderRevenue` = Number(revenueAmount) or 0 (reuses the existing
    revenueAmount computed for attribution).

(f) 5c call is placed AFTER the `if (cartToken) { … }` recovery block, so it
    runs for EVERY order (carted or not) — an order with no cart_token still
    bumps orders.count on a phone/email/customerId-matched profile.

(g) backfill step 4 (StorefrontEvent): the model's `sessionId` field holds a
    Shopify CART TOKEN (per its own comment), not a ccfSessionId. The spec said
    "upsertProfile with sessionId"; implemented as `cartToken: <that value>`
    (mapped to the cartTokens array) so it joins with AbandonedCustomer /
    ScheduledJob which key on cart token. customerId and FCM token from the
    grouped events are also passed. Grouping is one aggregate() call → one
    upsert per unique (shopDomain, sessionId).

  given an upsertProfile call. Spec step 5 lists only 5a–5e; the handover

  beacon but not the raw /api/events POST. If every StorefrontEvent write
  should touch a profile in real time (not just via backfill), events.js needs
  the same 3-line addition. Left out because it wasn't in the step list.
- checkouts/* webhooks share handleWebhook with carts/*, so 5b already covers
  checkout_abandon ingest — but there is no distinct checkout identity data
  beyond what carts give. Fine for now.
- No index migration / createIndexes call is run anywhere; Mongo builds the new
  Profile indexes lazily on first use. On a large existing collection the owner
  may want to build them explicitly.
- Merge does NOT deep-merge `orders`, `interests`, `channels`, or `activeHours`
  from losing profiles — only `identifiers.*` arrays + `messages` (per the
  literal spec). In practice losers are almost always anonymous shells with
  empty orders/interests, but a real-time merge of two profiles that each have
  order history would keep only the winner's counts. See open question 1.
- CLAUDE.md rule "Move the existing *_AUDIT.txt files to /audits/" — already
  done in commit de61791 (before this phase). Nothing to move.

8. OPEN QUESTIONS
================================================================================
1. Merge loss of orders/interests/channels from lower-priority profiles — should
   upsertProfile sum `orders.count/ltv/codCount/prepaidCount`, take max of
   `lastOrderAt`, and union `interests`/`activeHours` on merge? The spec says
   only identifiers + messages. Recommend adding orders-sum + channel-fill in
   Phase B when Signals start reading orders.
2. StorefrontEvent.sessionId semantics — it is named "sessionId" but stores a
   cart token. Backfill treats it as cartToken. If a stable ccfSessionId is
   later added to StorefrontEvent (Phase D storefront rework), backfill/ingest
   should map that to identifiers.sessionIds instead.
3. Should routes/events.js (raw /api/events ingest) also upsert a profile in
   real time, or is backfill + /cart-activity + webhooks enough? Not in the
   step list; easy to add.
4. `isCod` gateway heuristic — is there a canonical COD marker on the order
   payload for this shop's checkout (e.g. a fixed gateway name), so it can be
   an exact match instead of a substring test?
5. When does AbandonedCustomer get rewritten as `Profile` (stage 'carter')
   view — Phase A2, or folded into Phase B? No read path was changed here.
