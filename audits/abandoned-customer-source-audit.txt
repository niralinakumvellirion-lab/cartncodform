  backend/utils/shopify.js defines registerAllWebhooks(shop, accessToken,
  backendUrl), which loops over a hardcoded topic list --
    'carts/create', 'carts/update', 'checkouts/create', 'checkouts/update',
    'orders/create', 'app_subscriptions/update', 'app/uninstalled'
  -- and registers each one individually via the classic REST Admin API
  (POST https://{shop}/admin/api/{version}/webhooks.json), NOT the TOML
  mechanism. This function IS called, from backend/routes/auth.js line
  120, inside the OAuth callback:
    // Register webhooks (best-effort, non-blocking failures are logged).
    await registerAllWebhooks(shopDomain, accessToken, getBackendUrl(req));
  So these 5 topics are registered dynamically, per-shop, at
  install/reconnect time via a live Admin API call -- a DIFFERENT,
  legitimate mechanism from the declarative TOML subscriptions used for
  the GDPR topics. The TOML file being silent on these 5 topics is
  therefore not itself evidence they are unregistered -- but the
  comment "best-effort, non-blocking failures are logged" means a
  failed registerWebhook() call for any one topic is only ever logged
  (utils/shopify.js's registerWebhook(), on failure: "console.error(...
  Failed to register webhook ...)") and never retried or surfaced
  anywhere else (no stored flag, no admin-visible warning) -- so if this
  registration silently failed for this store at some point (e.g. an
  expired/invalid token at registration time, a scope mismatch, or the
  webhook already existing under stale settings), there would be no
  ongoing visible sign of it, and the only way to know would be a
  historical Render log line or checking Shopify's own webhook
  subscription list for the shop directly. Not verified further here --
  this is scope beyond what this audit-only task asked to check (it
  would require either digging through historical Render logs or a live
  Shopify Admin API call against the actual store, neither performed in
  this task).

SUMMARY (read-only synthesis, no code changed)
====================================================================
- AbandonedCustomer rows are created/updated from exactly one live
  request path: webhooks.js's handleWebhook() (carts/checkout webhooks),
  keyed by sessionId = the cart/checkout token from the Shopify payload.
  A second path (seedData.js) only ever runs manually for local dev
  fixtures and produced the 'seed-session-N' rows seen in the prior
  audit. A third site (handleOrderWebhook's updateMany) only recovers
  existing rows, never creates new ones.
- The 5 cart/checkout/order webhook topics are NOT declared in
  shopify.app.toml -- they rely entirely on the runtime
  registerAllWebhooks() REST call made during OAuth (routes/auth.js).
  That call's own failures are only logged, never retried or surfaced,
  so a silent registration failure for this specific store cannot be
  ruled out from the code alone -- would need direct verification
  against Shopify or historical logs, not done here.
- Given the previous task's finding that AbandonedCustomer only has 36
  total documents (several of them the seed fixtures) and that ZERO of
  the 2 email-profiles' 32 cartTokens matched any AbandonedCustomer row,
  the most likely explanations remain, now narrowed by this pass: either
  (a) carts/create and carts/update webhooks are not actually arriving
  for this store (registration failure, uninstalled/reinstalled without
  re-registering, or a HMAC/shop-domain mismatch silently rejecting them
  at the top of handleWebhook()), or (b) they ARE arriving but the token
  value Shopify sends in the webhook payload (payload.token /
  payload.cart_token / payload.id) does not actually match what the
  storefront's own /cart.js reports as cart.token for the same cart in
  this store's checkout flow. Neither hypothesis was tested in this
  task; both would require live/log verification beyond a code read.
