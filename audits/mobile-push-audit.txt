FIREBASE INIT (lines 10-38)
Guarded by FIREBASE_PROJECT_ID / FIREBASE_CLIENT_EMAIL /
FIREBASE_PRIVATE_KEY env vars. If any is missing, `firebaseReady`
stays false and BOTH exported functions short-circuit to a no-op

`{..., tokensFound:0}`) — logged, never thrown. This is a total-outage
condition affecting mobile AND desktop identically, not a mobile-
specific cause, but worth ruling out first since it would look exactly
like "nothing is being delivered."

sendPushToCustomers(shopDomain, title, body, url, imageUrl,
mobileOnly=false, cartToken=null, skipStaleCleanup=false) —
lines 89-269. This is the function that actually delivers to

--- How image URLs are passed to FCM ---
A single `imageUrl` parameter is fanned out into THREE places in the
same message object, identically in both the cartToken-scoped branch
(lines 149-171) and the broadcast-to-all-subs branch (lines 209-235):
  - data.imageUrl:            imageUrl || ''
  - data.icon:                imageUrl || '<hardcoded shopping-cart icon URL>'
  - webpush.notification.icon:  imageUrl || '<same hardcoded fallback>'
  - webpush.notification.image: imageUrl || undefined   <- NOTE: this
    one omits the key entirely when imageUrl is falsy (`undefined` in
    a JS object literal means the key is absent once JSON-serialized),
    whereas every other field above falls back to a real string. This
    is an inconsistency, not obviously a bug, but worth noting: `icon`
    always has SOME value (real image or the fallback icon); `image`
    can be entirely absent.
There is no per-recipient/per-device branching anywhere in this
function when building the message — every token in the `tokens`
array (or the single `[sub.token]` in the cartToken branch) receives
byte-for-byte the same `data`/`webpush` payload.

--- Whether mobile vs desktop tokens are handled differently ---
Only via the `mobileOnly` boolean parameter, which changes the MongoDB
QUERY used to select which CustomerPushSubscription rows to target
(line 103-105):
  if (mobileOnly) query.deviceType = { $in: ['mobile', 'unknown'] };
There is no equivalent "desktopOnly" filter anywhere — desktop rows
are only ever included as part of the unfiltered ("everyone") case
when mobileOnly is false. Once a set of tokens is selected, the FCM
MESSAGE ITSELF is constructed identically regardless of device type —
no `android`/`apns` payload block exists anywhere in this file; every
send goes out exclusively via FCM's `webpush` protocol. This is only
correct if every stored token is a genuine Web Push (browser Push
API / service worker) registration, not a native mobile app FCM
token — see Key Findings below.

--- Conditions that might cause mobile tokens to be skipped or fail
silently ---
(a) !firebaseReady (see above) — affects everyone, not mobile-specific.
(b) deviceType exact-string matching: `deviceType` is stored verbatim
    from whatever the storefront client sends (see push.js's
    /subscribe-customer route below — no validation, no enum), and
    `mobileOnly`'s filter does an EXACT match against the literal
    strings 'mobile' or 'unknown'. Any row whose deviceType was
    written as something else (different casing, 'phone', 'ios',
    'android', etc.) would silently fail to match a mobileOnly:true
    query. IMPORTANT: across all three files read for this audit, NO
    call site ever passes mobileOnly:true — every caller passes
    false or omits it (defaulting to false). This risk is therefore
    currently dormant, not an active cause of any present failure —
    flagged for completeness/future-proofing only.
(c) THE MOST CONCRETE BUG FOUND — the cartToken-scoped retry loop
    (lines 147-193). When a cartToken is supplied, this function:
      1. Finds ALL CustomerPushSubscription rows for that cart (or,
         if none, falls back to every cartToken the owning profile has
         ever had — lines 124-144), sorted most-recently-active first.
      2. Tries tokens ONE AT A TIME (lines 147-188). On a STALE token
         error, it prunes that token and tries the next. On ANY OTHER
         (non-stale) FCM error, it immediately `break`s out of the
         loop — no other token for that same customer is ever tried,
         even if older-but-still-valid tokens exist in `cartSubs`.
      3. After the loop (whether it broke early or simply ran out of
         rows), execution falls through to line 192-193:
           console.log(...'no valid token found'...);
           return { success: true, sent: 0, tokensFound: 0 };
         `success: true` even though a genuine send FAILURE may have
         just occurred on the most-recent token. `tokensFound: 0` is
         also wrong whenever cartSubs.length was actually > 0 — this
         return path hardcodes 0 regardless of how many rows were
         found/tried. No `error` field is set at all, so whatever the
         real FCM error code/message was (e.g. a malformed payload,
         a rate-limit error, a server error) is discarded entirely —
         only visible in the `console.error` at line 185, not in the
         returned result object callers actually act on.
    This is the SAME code path exercised by server.js's automated
    poller (see section 3) for every scheduled job that carries a
    cartToken — i.e., most brain.js-driven signal sends. See Key
    Findings for how this manifests downstream.
(d) skipStaleCleanup: when true (only ever passed as `true` by
    push.js's /send-customer route when there's no cartToken — see
    section 2), stale tokens found during a broadcast send are
    logged but NOT deleted (lines 252-259). Dead tokens (including
    mobile ones whose browser/PWA subscription has expired or been
    revoked) can accumulate indefinitely on that specific call path
    without ever being pruned — not a delivery failure per se, but a
    hygiene gap that could make "how many mobile subscribers do we
    actually have" numbers increasingly inaccurate over time.

--- Exact FCM payload structure (both branches, identical shape) ---

    data: {
      url: url || `https://${shopDomain}`,
      imageUrl: imageUrl || '',
      title: title,

      icon: imageUrl || '<fallback icon URL>',

    tokens: [...],   // or tokens: [sub.token] in the cartToken branch
  }
No top-level `notification` field, no `android` block, no `apns`
block — everything is carried inside `data` + `webpush`.

Key findings — what's most likely causing mobile delivery failure,
ranked by how directly each was verified in the code read for this
audit:

1. (Most concrete, verified bug) The cartToken-scoped retry loop in
   sendPushToCustomers() (pushNotification.js lines 147-193) tries
   only the single most-recently-active device token per customer and
   aborts entirely on the first non-stale FCM error, rather than
   trying any older-but-valid token for the same customer. This is
   the code path server.js's automated poller exercises for nearly
   every signal-driven send (it always supplies job.cartToken). The
   resulting ScheduledJob does get marked 'failed' (server.js's own
   `result.sent === 0` check catches it), but with the misleading
   generic reason "No active subscriber found" — the real FCM error
   code/message is discarded, never reaching the job record. If a
   merchant's mobile subscribers tend to be the most-recently-active
   token for their cart (a very plausible pattern — mobile browsers/
   PWAs churn tokens more than desktop), this would manifest as
   intermittent, hard-to-diagnose mobile non-delivery that LOOKS like
   "no subscriber" in the admin UI when it isn't.

2. (Structural, not a failure but likely the source of any
   "wrong/missing image on mobile" complaint) mobileImageUrl and
   desktopImageUrl are collapsed into one shared imageUrl (mobile
   preferred) before ever reaching FCM (push.js /send-store, line
   607) — there is no code path anywhere in the 3 files read that
   sends a different image to mobile-tagged vs desktop-tagged tokens.
   The two-image upload UI's promise and the single-image backend
   reality are mismatched.

3. (Unconfirmed but plausible, needs verification outside this
   audit's file scope) The entire FCM payload is built exclusively
   via the `webpush` block (pushNotification.js) with no top-level
   `notification`, `android`, or `apns` block anywhere. This is
   correct ONLY if every registered CustomerPushSubscription token is
   a genuine Web Push (browser/PWA) subscription. If any tokens are
   actually native mobile app FCM registrations, this payload shape
   would silently fail to display anything on those devices — native
   clients don't read `webpush.notification`. Could not confirm or
   rule this out from the files in scope for this audit; would
   require reading the storefront subscription/theme-embed code
   (extensions/cartncodform-embed) to verify what kind of token is
   actually being registered.

4. (Ruled dormant, not currently active) deviceType-based mobileOnly
   filtering has an exact-string-match risk (section 1(b)), but no
   call site anywhere in the 3 files read ever sets mobileOnly:true —
   so this cannot be an active cause of today's mobile delivery
   issues, only a latent risk if that parameter is ever wired up to a
   real caller in the future.

5. (Simplest explanation, rule out first) If FIREBASE_PROJECT_ID /
   FIREBASE_CLIENT_EMAIL / FIREBASE_PRIVATE_KEY are unset or invalid
   in the Render environment, EVERY push — mobile and desktop alike —
   silently no-ops. This wouldn't explain a mobile-SPECIFIC symptom
   (desktop would fail too), but is the cheapest thing to check first
   if the actual observed symptom is "no pushes at all" rather than
   "mobile specifically."
