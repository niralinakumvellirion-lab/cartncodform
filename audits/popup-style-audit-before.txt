2. EVERY POPUP TYPE AND WHERE EACH RENDERS
====================================================================
There are really only TWO visually distinct customer-facing "types"
today, plus one non-popup post-action element:

  a) MAIN SOFT-PROMPT POPUP — showSoftPrompt() (liquid ~line 640).
     - Rendered on non-product pages (home/collection/etc — gated by
       initIntentTriggers(), which explicitly `return`s on product
       pages), on a ~1.5s dwell timer (PAGE_LOAD trigger) for a visitor
       with no existing subscribe token.
     - Reads `popupConfig` or `mobilePopupConfig` (device-detected via
       `window.innerWidth <= 600`) and branches on `cfg.layout` to build
       one of 3 layouts (split / card / banner) via raw
       `document.createElement(...)` DOM construction (NOT a shared
       template string) into a `#ccf-push-prompt` element.
     - THIS SAME FUNCTION also serves the "discount-capture" case: an
       already-subscribed customer (`Notification.permission ===
       'granted'`) with any discount rule enabled gets the identical
       popup shown again (bypassing the normal permission gate) purely
       to collect an email for a bigger discount. It is NOT a separate
       visual design — same layout code, same `cfg`, just a different
       trigger condition and different fields shown inside it (the email
       input, via `ccfShowEmailField()`/`ccfBuildDiscountFields()`).
     - After a successful subscribe/discount, `renderDiscountCode()`
       (~line 519) replaces this same popup's content section IN PLACE
       with an "unlocked" state (code, copy-to-clipboard, auto-redirect)
       — still the same DOM element, not a new popup.

  b) PRODUCT-PAGE NUDGE — injectProductNudge() (liquid ~line 1464).
     - A SEPARATE, much simpler widget inserted directly after the
       product form / Buy button on product pages only (the main
       soft-prompt explicitly skips product pages).
     - Has NO layout choice and reads almost nothing from
       `popupConfig` — only `popupConfig.accentColor` for its accent;
       everything else (copy, structure, spacing) is hardcoded in the
       function. It is NOT currently styleable via the Popup
       Customization screen at all.
     - On a successful discount, this ALSO gets an in-place "unlocked"
       state (percentage + code + "Shop now" link), built by its own
       inline HTML, not by calling renderDiscountCode().

  c) PERSISTENT DISCOUNT BUY BUTTON — injectProductDiscountButton()
     (liquid ~line 483). Not a popup — a plain button inserted near the
     Buy button once a discount code already exists (from a previous
     visit/session, via sessionStorage). Mentioned for completeness
     since the task said "any others"; out of scope for "popup style" as
     it has no layout/appearance knobs of its own (a single hardcoded
     green button).

So for the purposes of "each popup type gets its own style selection"
(Phase 2C), there is realistically ONE styleable popup type today (the
soft-prompt / discount-capture popup, since they share all rendering
code) plus the product nudge as a second, currently-unstyled surface.
This is an important scoping question for Phase 2 — see item 4.

3. CURRENT DESIGN IN DETAIL
====================================================================
Layouts (cfg.layout, enum split | card | banner — Store.js popup
subdoc; mobilePopup only allows card | banner, default card):

  - SPLIT — two-column: image on one side, content (headline, subtext,
    email/discount fields, Allow/Deny buttons) on the other. Admin JSX
    branch ~Settings.jsx:1501; storefront branch inside showSoftPrompt().
  - CARD — single stacked card, image on top (if any), content below.
    This is the ONLY layout mobile ever uses by default.
  - BANNER — full-width bar, typically image+text inline with a compact
    CTA.

Both desktop and mobile have their OWN complete config object (`popup` /
`mobilePopup`), not a single config with a "mobile override" of a few
fields — each carries its own layout, headline, subtext, brandName,
image/imagePosition, colors, font, borderRadius, allow/denyText,
showBranding, textAlign, ctaStyle (mobile defaults `ctaStyle: 'pill'`
vs desktop's `'rounded'`). If mobilePopup's own fields are empty, the
storefront line `if (isMobile && !cfg.layout) cfg = popupConfig || {};`
falls back to the desktop config wholesale (not per-field).

Editable fields on the customizer screen today (Settings.jsx ~1078-1340,
one popRow per field): Layout (desktop tab only — mobile is fixed to
"Card" in the UI, matching the schema's mobile enum), Image (upload,
client-side canvas-resized to max 800px + JPEG-compressed to base64
before it ever reaches the request body, plus an Image focus /
imagePosition control), Headline, Subtext, Brand name, Allow button
text, Deny button text, Accent color, Background color, Text color,
Font, Border radius, Button style (`ctaStyle`: rounded/square/
pill/outlined/soft, rendered via `getCtaStyle()`), Position (only
meaningful together with `showOverlay`/overlay logic), Dark overlay
on/off toggle.

Schema fields that exist and are saved by the PATCH whitelist but are
NOT exposed by any control in the current UI (confirmed via grep — no
JSX references `activePopup.theme`, `.customTitle`, or `.overlayOpacity`
anywhere): `theme` (enum light/dark/custom), `customTitle`,
`overlayOpacity` (only the boolean `showOverlay` is wired up). These are
effectively dead/orphaned in the admin today; flagging since a new
"style" feature might want to either finally use them or explicitly
ignore/deprecate them.

Live preview: the customizer panel includes an inline preview
(Settings.jsx ~1480-1900) that is a COMPLETELY SEPARATE, hand-written
JSX re-implementation of the same split/card/banner rendering the
storefront's showSoftPrompt() does in vanilla JS DOM calls. The two are
not sharing any code or template — they are two independently
maintained visual implementations of "the same" popup. This is the
single most important fact for item 8 (sync strategy) below: today, any
visual tweak to one has to be manually re-implemented in the other, and
they can (and likely already do, in small ways) drift apart.

Discount fields: `ccfShowEmailField()` (true when emailDiscount or
bothDiscount is enabled, per the Discounts screen audited earlier this
session) controls whether an email `<input>` appears inside the popup —
split layout via the shared `ccfBuildDiscountFields()` helper, card
layout via its own inline-built input. The admin's live preview does NOT
currently render this email field at all (it previews the base
popup fields only) — task Phase 2 explicitly asks for "email field
visible in preview where applicable," which is new behavior, not a
sync-gap fix.

4. HOW "STYLE" SHOULD RELATE TO THE EXISTING `layout` FIELD
====================================================================
Options as framed by the task:
  a) style REPLACES layout
  b) style WRAPS layout (each style internally picks a layout)
  c) style sits BESIDE layout (both stay, independently selectable)

RECOMMENDATION: (b) — style wraps layout.

Reasoning:
  - `layout` (split/card/banner) is a structural/geometric concept
    (where does the image go, is it a bar or a box) that is already
    deeply wired through BOTH the admin preview and the storefront's
    DOM-building code, the mobile-vs-desktop schema (mobilePopup's enum
    is a SUBSET of popup's), and the backend's PATCH whitelist. Treating
    it as still-authoritative-but-now-derived keeps every existing
    stored document valid with zero migration: a style's registry entry
    just declares which `layout` value it renders as, and the existing
    `cfg.layout` reads throughout showSoftPrompt() keep working
    unmodified for the geometry, while the NEW style id decides which
    decorative treatment (fonts, borders, badges, imagery treatment,
    button chrome, whatever each reference design turns out to need) is
    layered on top.
  - Option (a), replacing layout outright, would require touching every
    existing `cfg.layout === 'split'|'card'|'banner'` branch in both
    files and would break the documented mobile-enum-is-a-subset-of-
    desktop-enum fallback logic (`if (isMobile && !cfg.layout) cfg =
    popupConfig`) for no real benefit — layout's job (2-col vs stacked
    vs bar) is orthogonal to "style" as evidenced by the reference-image
    task wording itself ("layoutType" is listed as one field the style
    registry stores, i.e. style HAS a layout, it doesn't obsolete it).
  - Option (c), fully independent axes (any style + any layout,
    cross-product), sounds flexible but is very unlikely to be
    what the reference images actually need — a "premium minimal" look
    and a "bold banner sale" look are not the same design with
    different image placement swapped in; they're genuinely different
    visual systems that each happen to use ONE particular layout well.
    A free cross-product multiplies the QA/parity surface (item 8) for
    little real merchant value, and none of the task's Phase 2 spec
    items (style registry has `layoutType` as ONE field per style, not a
    separate independent selector) suggest independent axes were
    intended.
  - "Classic" (id `classic`) = today's exact behavior, unchanged,
    mapping 1:1 to whatever `layout` the shop already has saved — this
    is what makes (b) a strictly additive change: an existing shop with
    no `style` field saved renders identically to before (task Phase 2D
    explicitly requires this), because Classic's registry entry doesn't
    change any existing code path, it just names the current one.

Consequence for Phase 2: the style registry's `layoutType` field is the
single source of truth for which of the 3 existing geometric layouts a
given style renders as; a style can technically reuse the SAME layout
another style uses (e.g. two different "card"-based styles with
different decoration), which is exactly the flexibility (b) is meant to
provide without (c)'s combinatorial risk.

6. SAVE/LOAD — ENDPOINTS, FIELDS, SCHEMA
====================================================================
Endpoints (repeated from item 1 for completeness):
  GET   /api/profiles/:shopDomain/popup        (admin, requireAuth)
  PATCH /api/profiles/:shopDomain/popup        (admin, requireAuth)
  GET   /apps/cartncodform/popup-config        (storefront, App Proxy)

PATCH whitelist (`POPUP_FIELDS`, routes/profiles.js): position, theme,
accentColor, bgColor, textColor, fontFamily, borderRadius, imageUrl,
imagePosition, allowText, denyText, customTitle, showBranding, layout,
headline, subtext, brandName, textAlign, ctaStyle, overlayOpacity,
showOverlay. The SAME list is reused for `mobilePopup.*` when the
request body includes a `mobilePopup` object — there is currently no
separate "style" or per-popup-type concept anywhere in this whitelist,
the Store schema, or the request/response shape; every field is a flat
property of ONE `popup` object (plus its `mobilePopup` sibling). Adding
a per-popup-type style selection (task Phase 2C "Style is selected per
popup type") is new schema/API surface, not something that reuses an
existing hook — see the "known issue for Phase 2 planning" note below.

Store.js schema (backend/models/Store.js):
  popup: { position, theme, accentColor, bgColor, textColor, fontFamily,
    borderRadius, imageUrl, imagePosition, allowText, denyText,
    customTitle, showBranding, layout, headline, subtext, brandName,
    textAlign, ctaStyle, overlayOpacity, showOverlay }
  mobilePopup: { layout (card|banner only), headline, subtext,
    brandName, imageUrl, imagePosition, accentColor, bgColor, textColor,
    fontFamily, borderRadius, allowText, denyText, showBranding,
    textAlign, ctaStyle, [truncated — same shape as popup minus
    position/theme/customTitle/overlayOpacity/showOverlay] }

Save flow: Settings.jsx's single `saveSettings()` (shared with every
other Settings field, not popup-specific) sends `voice/caps/
quietHours/timezone` to the settings PATCH and `{...popup, mobilePopup:
{...mobilePopup}}` (minus `imageUrl` when it hasn't changed this
session, per `popupImageChanged`/`mobileImageChanged`) to the popup
PATCH, in parallel via `Promise.all`. There is no separate "Save popup"
button — the customizer panel's changes are staged in React state and
only persisted on the screen's main Save click (the panel explicitly
says so: "Changes save with the main Save settings button").

NOTE FOR PHASE 2 PLANNING — a per-popup-type style concept (task's own
Phase 2C: "Style is selected per popup type") is genuinely new schema:
today there is exactly one `popup` + one `mobilePopup` config per shop,
with no notion of "type" at all (the two visually distinct surfaces from
item 2 — soft-prompt/discount-capture vs. product nudge — aren't even
separately configured today, only the nudge's accent color is derived
from the shared popup config). Phase 2's registry + "style id + extra
fields per shop, per popup type" (Phase 2D) will need a genuinely new
shape, most likely nesting style selection under each existing config
object (e.g. `popup.styleId` / `popup.styleFields`, `mobilePopup.styleId`
/ `mobilePopup.styleFields`) rather than a new top-level structure — this
keeps it additive/non-destructive per Phase 2D's requirement, and
naturally answers "per popup type" as "per existing config object,"
since desktop and mobile already are independently configured.

8. KEEPING ADMIN PREVIEW AND STOREFRONT POPUP IN SYNC
====================================================================
As established in item 3, today's split/card/banner rendering is TWO
independent hand-written implementations (JSX in Settings.jsx vs.
imperative DOM-building in the liquid file) with no shared code — this
is exactly the kind of drift risk the task is asking to avoid for the
NEW style feature.

RECOMMENDATION: a documented parity checklist per style, NOT a shared
markup/template approach — for this specific codebase, given real
constraints:

  - The storefront file is a Shopify theme app embed block: plain,
    dependency-free vanilla JS running in the customer's browser, no
    build step, no npm packages, no JSX. The admin is a Next.js/React
    app. There is no existing shared-code channel between them (no
    shared npm package, no codegen step, nothing) — introducing one
    (e.g. a shared JSON-driven template renderer both sides interpret)
    would be a substantial new piece of infrastructure, is explicitly
    flagged as "unrelated refactors" being out of scope, and is far more
    engineering than 4-6 new popup styles justify.
  - A genuinely shared TEMPLATE (e.g. both sides consuming one HTML/CSS
    string per style, admin via dangerouslySetInnerHTML, storefront via
    innerHTML) is technically possible and would remove drift risk
    entirely, but requires escaping merchant strings correctly on BOTH
    consumption sides and moving every existing hand-tuned per-layout
    detail (hover states, focus rings, responsive breakpoints, the
    existing admin-only "which layout looks selected" chrome that has no
    storefront equivalent) into one dialect both environments can
    render identically — high risk of visual regressions in the
    EXISTING 3 layouts for a feature whose ask is additive.
  - Given that: recommend each new style registry entry documents its
    own render recipe TWICE (an admin JSX render function + a storefront
    liquid/JS render function), governed by ONE shared, versioned
    "parity checklist" per style (documented directly in the registry
    file as a comment block, or in a short docs/popup-styles-parity.md):
    exact fields used, exact conditional rendering rules (e.g. email
    field visibility, image aspect/position), exact color/spacing
    tokens, and a screenshot-diff step as part of adding/changing a
    style (manually compare admin preview vs. a real storefront render
    before calling a style "done"). This mirrors how `layout` itself is
    already kept in sync today (by convention/discipline, not
    structurally) and is the lowest-risk, most consistent-with-existing-
    codebase-conventions option.
  - To reduce (not eliminate) drift risk further without a full shared-
    template rewrite: centralize the few things that ARE pure data
    (color/font/spacing DEFAULT values, and field lists like
    `supportedFields`) in the ONE style registry file itself (Phase 2A
    already asks for this), so at minimum the "what fields exist and
    what are their defaults" facts can't drift — only the actual pixel-
    level rendering code stays duplicated, exactly as `layout` is today.

9. PROPOSED STYLE SHORTLIST (Classic + 4 new)
====================================================================
IMPORTANT: every style below is an ORIGINAL design inspired by the
underlying structural/visual PATTERN in its reference group (layout
shape, typography weight, color contrast, element arrangement) — none
copies any brand's logo, product photography, exact copy, or exact
color values. Per the task's instruction, reference images will also
NOT be used as in-app thumbnails; Phase 2 card thumbnails must be
drawn/generated previews of this app's own rendering of each style.

One honest gap: none of the 15 references is a full-width BANNER. All
15 are either a boxed card/split panel or an organic full-bleed shape.
So this shortlist doesn't propose a new banner-wrapping style — Classic
continues to cover banner exactly as today, and a banner-based new
style would need its own separate reference material if wanted later.

---

1) CLASSIC (baseline, unchanged)
   Reference image(s): none — this names today's existing behavior.
   Wraps layout: whatever the shop already has saved (split/card/
   banner) — Classic does not force a layout.
   Extra fields: none (existing fields only).
   Behavior: renders EXACTLY as today, byte-for-byte (Phase 2/3
   requirement) — the reason (b) "style wraps layout" was recommended
   in item 4 is precisely so Classic can be a no-op.

2) "FLASH SALE" — dark, urgent, countdown-driven
   Reference image(s): #1 (14-popup-key-portal), #3 (Crown & Paw)
   Wraps layout: card
   Pattern taken (not copied): dark background, small decorative
   accent motif (dots/sparkles — an original simple pattern, not
   Crown & Paw's specific stars), bold high-contrast offer text, a
   live countdown as a first-class visual element, pill or rounded
   CTA.
   Extra fields: countdownEnabled (bool), countdownMinutes (number —
   duration from first view, or a fixed end time), badgeText (short
   optional eyebrow label, e.g. merchant-entered "LIMITED TIME");
   reuses existing accentColor/bgColor/ctaStyle for the dark palette
   and pill button rather than inventing new color fields.

3) "EDITORIAL" — elegant split, serif heading, countdown as digit
   blocks
   Reference image(s): #5 (Christopher Cloos)
   Wraps layout: split
   Pattern taken: light, airy split panel; small-caps/serif-leaning
   headline treatment; a thin divider rule under the heading; a
   countdown rendered as solid digit blocks rather than plain text;
   understated CTA color.
   Extra fields: countdownEnabled, dividerEnabled (bool, thin rule
   under headline), eyebrowText (short label above the headline, e.g.
   "MEMBERS ONLY" — same underlying concept as getresponse's badge,
   #8, folded in here rather than given its own style).

4) "SPOTLIGHT" — organic shape, image-as-background, no separate
   panel
   Reference image(s): #4 (Kinfield), #12 (Urban oval), #7 (meditation
   site, for the "text directly over photo" treatment)
   Wraps layout: card (rendered as an aggressively rounded card —
   effectively circular/oval — rather than a rectangular panel; see
   note below)
   Pattern taken: the merchant's uploaded image fills the ENTIRE
   popup shape as a background (not a side panel), heading/subtext/
   CTA sit directly on top of the image with a scrim/overlay behind
   the text for legibility, minimal chrome otherwise.
   Extra fields: shapeStyle (circle | oval | rounded-rect — how
   aggressively `borderRadius` is forced), overlayOpacity (reuses the
   EXISTING schema field, which today is saved but has no UI control —
   this style is a natural place to finally expose it), accentMotif
   (bool — a simple original thin-line decorative accent, not Kinfield's
   specific squiggle art).
   NOTE — this is the one style that stretches the "wraps an existing
   layout" model from item 4: `card` already supports an image (via
   `imageUrl`), but today that image sits ABOVE or BESIDE content, never
   BEHIND it as a full-bleed background with text overlaid. Implementing
   this needs one new rendering mode within `card`, not a new geometric
   layout — flagging this explicitly since it's more work than the other
   3 new styles, which mostly recombine existing rendering with new
   copy/color defaults.

5) "GIFT REVEAL" — playful, icon-driven, prominent code chip
   Reference image(s): #13 (mobile gift-box + code chip), #10 (Pipcorn,
   for the playful copy tone + input-badge micro-detail), #15
   (sddefault, for the stacked equal-weight two-button footer)
   Wraps layout: card
   Pattern taken: an optional simple original gift/present glyph (not
   Pop-up-Form-4's specific illustration) shown above the heading
   instead of a merchant photo when no image is set; a more prominent,
   pill-chip-styled treatment for the EXISTING post-subscribe "unlocked
   code" state (this app already has that state, via
   renderDiscountCode() — this style makes it visually louder, it
   doesn't add new subscribe/discount logic); a two-real-button footer
   (primary + secondary, both full-width pills) instead of
   button + text-link.
   Extra fields: giftIconEnabled (bool — show the built-in glyph when
   no imageUrl is set), secondaryButtonStyle (pill | text-link — which
   footer pattern to use), codeChipEmphasis (bool — louder styling on
   the existing unlocked-code display).
