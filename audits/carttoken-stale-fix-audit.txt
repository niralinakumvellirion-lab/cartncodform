DEVIATION FROM THE LITERAL TASK INSTRUCTIONS (verified, not guessed)
=========================================================================
The task's premise for Fix 2 was: "The function currently receives a
job object — check if it has access to profileId" and, if not,
"just log a warning and return as before."

Checked directly against the function's real signature (confirmed
again in this task before editing):
  async function sendPushToCustomers(shopDomain, title, body, url, imageUrl, mobileOnly = false, cartToken = null, skipStaleCleanup = false) {
sendPushToCustomers() does NOT receive a job object, and never has —
it takes 8 plain scalar parameters. There is no profileId anywhere in
its scope. The caller (backend/server.js's poller) has a `job` object,
but only ever forwards job.cartToken (a plain string) into this
function's `cartToken` parameter — never the job itself.

Taking the task's literal "if not available, log a warning and return
as before" branch would have left the exact bug this task exists to
fix completely unaddressed — the function would behave identically to
before in every case, since profileId is NEVER available under the
current, unchanged signature (and the task explicitly forbids changing
that signature). That would make Fix 2 a pure no-op.

Instead, implemented the SAME functional outcome — falling back to the
profile's other cartTokens when the given one has no live subscription
— without adding a profileId parameter: the given `cartToken` itself is
guaranteed to still be present in the correct profile's
identifiers.cartTokens array (that is literally why brain.js chose it
as job.cartToken — now carts[carts.length-1] after Fix 1, but the same
reasoning applied to the historical carts[0] jobs already in the
system). So the fallback re-derives the profile via:
  Profile.findOne({ shopDomain: shop, 'identifiers.cartTokens': cartToken })
instead of the given Profile.findById(profileId) — same destination
(the profile's full identifiers.cartTokens array), reached through an
identifier that IS actually available inside this function's existing,
unchanged signature.

Fallback only triggers when the INITIAL query returns zero rows
(cartSubs.length === 0), matching the task's literal trigger condition
("if the initial cartToken query returns 0 subscriptions") — a
cartToken that has subscriptions but all fail to actually deliver
(stale-but-present rows, or a non-stale FCM error) is NOT treated as a
0-subscription case and does not additionally trigger the fallback,
since the task specifically scoped the fallback to "0 subscriptions",
not "0 successful sends".

If the profile lookup itself finds nothing (no profile has this
cartToken at all) or the profile has no other cartTokens, a warning is
logged and the function proceeds exactly as it did before this fix
(falls through to the existing "no valid token found... skipping"
return) — this matches the spirit of the task's own "log a warning and
return as before" fallback-of-the-fallback, just reached via a
different (available) identifier instead of a genuinely unavailable
profileId.
