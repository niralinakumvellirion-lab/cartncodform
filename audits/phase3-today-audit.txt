PART A - EXACT CODE (mount fetch)
=========================================================================
  const [activity, setActivity] = useState(null);
  const [activityLoading, setActivityLoading] = useState(true);

  useEffect(() => {
    if (!shop) return;
    setActivityLoading(true);
    apiGet(`/api/activity?shop=${encodeURIComponent(shop)}`)
      .then(data => setActivity(data))
      .catch(() => setActivity(null))
      .finally(() => setActivityLoading(false));
  }, [shop]);

Matches the task's given code exactly, as its own separate useEffect
(not merged into the existing push-stats/signals/orders effect) —
kept independent so a slow/failing /api/activity call can never delay
or fail the existing Today content, and vice versa.

Note: the backend endpoint this calls (backend/routes/activity.js,
built in the Phase 2 task) does NOT read req.query.shop at all — it
derives the shop exclusively from the verified session token
(req.shopDomain), by design (see audits/phase2-activity-api-audit.txt,
security note on that endpoint). So the `?shop=...` in this fetch URL
is harmless but effectively unused server-side; apiGet() still needs
to attach the session token (Authorization header) for the request to
succeed at all, which it already does for every other call in this
file. No change was needed here since the call still works correctly —
just noting the param is a no-op on the backend, not a bug.

PART D - navigation pattern
=========================================================================
Checked for an existing `useRouter`/navigation hook import in this
file first, per the task's instruction: none was present. Per the
task's fallback instruction, checked Customers.jsx and Messages.jsx for
"the pattern used" — grepped both files for useRouter, router.push,
next/navigation, next/router, window.location.href, and <a href: ZERO
matches in either file. Neither screen navigates anywhere at all.
Broadened the search to the whole frontend/ tree: `useRouter` (from
next/navigation or next/router) is not imported ANYWHERE in this
codebase. The only real navigation mechanism that exists anywhere in
this app is Shopify's own NavMenu component (@shopify/app-bridge-react),
declared once per admin/*/page.js wrapper file (not in any screen
component) as plain <a href="/admin/...">, e.g.:
  <NavMenu>
    <a href="/admin" rel="today">Today</a>
    <a href="/admin/customers" rel="customers">Customers</a>
    ...
  </NavMenu>
This is Shopify Admin's own left-hand nav, rendered outside the iframe
by App Bridge — clicking one causes Shopify's embedded-app shell to
navigate the iframe itself, which is a different mechanism from a
same-document client-side route change.

Since no reusable pattern existed to "use the same pattern" per the
task's fallback instruction, introduced Next.js App Router's own
standard client-side navigation hook, `useRouter` from `next/navigation`
(this project's App Router version; `next/navigation`'s
`useSearchParams` is already used elsewhere in the codebase, e.g.
every admin/*/page.js wrapper file, so the module itself is already a
project dependency in active use — just not `useRouter` specifically
until now):
  import { useRouter } from 'next/navigation';
  ...
  const router = useRouter();
  const navigate = (path) => {
    const sep = path.includes('?') ? '&' : '?';
    router.push(`${path}${sep}shop=${encodeURIComponent(shop)}`);
  };


DEVIATION - navigate() carries `shop` forward explicitly; the task's
given onClick handlers did not
=========================================================================
The task's given code called `navigate('/admin/activity')` and
`navigate(\`/admin/activity?type=${key}\`)` with no shop parameter.
Every admin/*/page.js wrapper in this codebase (confirmed by reading
admin/page.js and admin/customers/page.js in full) derives the `shop`
prop passed into its screen component via
`useSearchParams().get('shop')` — there is no other mechanism in this
app for a screen to learn which shop it's rendering for. The existing
NavMenu <a href="/admin/customers"> links also don't carry `?shop=`
explicitly, but that's a DIFFERENT mechanism: Shopify's embedded-app
shell (outside the iframe) owns that navigation and is known to
reinject shop/host params when it reloads the iframe's src — this is
how Shopify embedded apps' NavMenu is documented to behave, and is
consistent with every screen in this app working correctly today
despite none of the NavMenu hrefs carrying shop explicitly.
`router.push()`, by contrast, is a same-document, client-side Next.js
route transition that happens entirely INSIDE the iframe, bypassing
Shopify's shell entirely — there is no reason to expect shop/host
reinjection to happen for it. Had `navigate('/admin/activity')` been
implemented exactly as given, a future /admin/activity/page.js built
the same way as every other page.js in this app (reading shop via
searchParams) would receive an empty shop string the moment a merchant
clicked "View all" or a tile from Today, breaking every API call the
destination page makes.
Since this is a concrete, verifiable, high-confidence failure mode
(not a stylistic guess) and the fix is a one-line addition local to
this file, `navigate()` now appends `shop` explicitly, handling both
cases (no existing query string vs. one already present, e.g. the
`?type=${key}` tile links).
