3. Why recent carts have MISSING productImageUrl but older ones have it
====================================================================
Direct evidence available from this investigation, connected here:

  - audits/webhooks-audit.txt (earlier task, same investigation)
    confirmed, via a LIVE call to Shopify's Admin API using this exact
    store's stored accessToken, that Shopify now rejects it outright:
    "Non-expiring access tokens are no longer accepted for the Admin
    API." This is not topic-specific (webhooks) -- it is a blanket
    rejection of that token for ANY Admin API call.

  - fetchProductImage() (section 2 above) makes its own, completely
    separate Admin API call using that SAME store.accessToken.

  - Since that function has no res.ok check (also section 2), a
    rejected-token response silently resolves to imageUrl = null,
    logged identically to "this product has no photo".

  - Mechanism A (the webhook payload's own line_items image data) is,
    per the code's own comment, not actually available for carts/*
    webhooks -- so in practice Mechanism B (the now-broken Admin API
    call) is the ONLY realistic source of a fresh productImageUrl for
    a cart-abandon row.

  - The two OLDER AbandonedCustomer rows checked in the immediately
    preceding task (sessionId hWNGYT5qafzRgR9yOLa9IaJQ and
    hWNGYSl977Ap3UC4X3PwpP1w) DO carry a real
    cdn.shopify.com image URL; the three NEWER rows (sessionId
    3e9af47bd1f3df3c83d63e09cad0b9e7, hWNGk4gcbJm3IHibIrQYJBHo,
    hWNGjzKaa5XjMsFIlC6WV3bw) do not.

Putting these together: the most likely explanation is that this
store's offline access token was still valid (accepted by Shopify) when
the older rows were created/updated -- fetchProductImage() succeeded
and wrote a real image URL onto them. At some point since, Shopify
began rejecting this same token (confirmed still rejected as of this
session), and every AbandonedCustomer row created or updated from that
point forward has had fetchProductImage() silently fail (no res.ok
check surfaces this) -- leaving productImageUrl unset for all of them,
which is exactly the MISSING pattern seen on the 3 more recent rows.
This is a plausible, evidence-backed explanation, not something
directly re-verified with a fresh live test in this task (that would
require deliberately triggering a new carts/create webhook and watching
it fail, which was not done here -- audit only).

DOES THE HANDLER MAKE A SHOPIFY ADMIN API CALL TO FETCH PRODUCT IMAGES?
====================================================================
Yes -- fetchProductImage() (section 2), called from inside
handleWebhook() whenever a store record and a productId are both
available (lines 216-221).

Token used: store.accessToken (line 219) -- loaded via
`const store = await Store.findOne({ shopDomain });` (line 204) a few
lines above. This is the plain, classic OAuth offline access token
stored on the Store document -- NOT store.onlineAccessToken (the
Token-Exchange-derived online token that backend/routes/discounts.js's
generateDiscount() was changed to prefer, in an earlier phase of this
same overall investigation/fix history). fetchProductImage() has no
awareness of onlineAccessToken at all -- it only ever receives and uses
whatever `accessToken` its caller passes in, and this caller always
passes store.accessToken specifically.

Is it the same offline token that was rejected earlier? Yes -- it is
the exact same field, Store.accessToken, on the exact same Store
document, confirmed directly rejected by Shopify's Admin API in
audits/webhooks-audit.txt via a live call. fetchProductImage() would be
expected to fail for the same underlying reason, for as long as that
token remains invalid, though this was not independently re-tested
live in this task (see note above).
