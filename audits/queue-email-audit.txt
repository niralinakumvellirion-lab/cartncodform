1. What query it uses to find profiles
====================================================================
  Profile.find({ _id: { $in: profileIds } })
-- a single batch lookup by `_id`, no `shopDomain` filter (not needed:
`profileIds` was already derived only from the CURRENT page's job
rows, which were themselves already scoped by `shopDomain: shop` in
the earlier ScheduledJob.find() query, so every _id here already
belongs to this shop). `profileIds` (lines 30-33) is built by mapping
every job in the current page to its `profileId`, dropping any
falsy/missing one (`.filter(Boolean)` -- jobs with no profileId, e.g.
legacy rule-based jobs, are excluded here), and stringifying each
(`.map(String)`) so they can be matched against Profile's `_id` (an
ObjectId) via Mongoose's usual string-to-ObjectId cast in a query.

3. How it maps email to each job
====================================================================
Two-step map/lookup, not a per-job query:
  1. `profileMap` (lines 39-44) is built ONCE from the small
     `profiles` result set: for each profile, its resolved email
     (see section 4 below) is stored keyed by `p._id.toString()`.
  2. `enriched` (lines 46-49) maps every job in the current page to a
     new object spreading the job's own fields (`...j`) plus one added
     `email` field, looked up via `profileMap[j.profileId?.toString()]`
     -- falling back to `null` if that key isn't present in the map at
     all (covers both "job has no profileId" and "job's profileId
     didn't match any profile", e.g. a stale/deleted profile
     reference).
This is a classic batch-enrichment pattern (one query for all jobs'
profiles, then an in-memory map lookup per job) rather than N+1
separate Profile queries per job -- efficient for the paginated list
(max 20 jobs per page).

4. What fallback is used when email is null
====================================================================
Two-level fallback, applied per-profile inside profileMap's
construction (lines 41-43), NOT per-job:
  p.channels?.email?.address || p.identifiers?.emails?.[0] || null
  1. First choice: `channels.email.address` (the single "current"
     email address field).
  2. If that's falsy: `identifiers.emails[0]` (the first entry in the
     accumulating emails array).
  3. If BOTH are falsy: the literal `null`.
This exact 2-field fallback order (channels.email.address first, then
identifiers.emails[0]) matches the same precedence already established
elsewhere in this codebase for resolving "a profile's email" (see
backend/server.js:430-431, backend/routes/push.js:398-399, and the
test backend/__tests__/sendJourneyEmail.test.js, all noted in earlier
audits this session) -- consistent, not a one-off choice specific to
this file.
Then, separately, at the per-JOB level (line 48):
  profileMap[j.profileId?.toString()] || null
-- if the job's profileId doesn't resolve to any key in profileMap at
all (no profileId on the job, or no matching profile found), the
job's `email` field is `null` too. So the final `email` value on an
enriched job is `null` in three distinct cases: (a) the job has no
profileId, (b) the job's profileId didn't match any Profile document,
or (c) it matched a Profile that itself has neither
channels.email.address nor any identifiers.emails entries. The API
response gives no way to distinguish which of these three occurred --
the frontend (QueueScreen.jsx, built in an earlier task this session)
displays all three identically as "Anonymous", per its own
`job.email || 'Anonymous'` fallback.
