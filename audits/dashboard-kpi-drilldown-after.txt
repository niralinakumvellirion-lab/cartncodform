=== PART 1: Fix the 4 already-broken attributed links ===

Problem: activity/page.js dropped ?type= from searchParams entirely; ActivityScreen
  defaulted activeType to null and filter to '7d' unconditionally, so a Dashboard
  click always landed on "All types, last 7 days" regardless of what was clicked.

Fix:
- activity/page.js: reads type, from, to from searchParams; passes as initialType,
  initialFrom, initialTo to ActivityScreen.
- ActivityScreen.jsx: seeds activeType = initialType || null; if initialFrom+initialTo
  are both present, starts in 'custom' filter mode with customFrom/customTo sliced to
  .slice(0,10) for the type="date" inputs (day granularity — same pre-existing limit).
  Otherwise defaults to '7d' as before.
- DashboardScreen.jsx: attributed-tile onClick now appends
  &from=<encodeURIComponent(kpiFrom)>&to=<encodeURIComponent(kpiTo)> to every
  /admin/activity?type=<key> link, using a single getDateRange(dateFilter) call shared
  across all tiles.

No backend change — /api/activity already accepts eventType, from, to.

=== PART 2: Push Sent / Emails Sent -> Messages ===

Backend (backend/routes/profiles.js — GET /:shopDomain/messages):
- Added channel param: 'push' or 'email' narrows filter.channel; any other value ignored.
- Added status param: narrows filter.status to exactly that value (e.g. 'sent');
  default stays {$in:['sent','skipped','failed','cancelled']} so a plain screen visit
  is unchanged.
- Added from/to params: adds filter.sentAt = {$gte, $lte} ONLY when from or to is
  present. Doing this unconditionally would silently drop skipped/failed/cancelled rows
  from the default view (those rows may have no sentAt); the additive-only approach
  avoids that regression.

Client-side vs server-side channel filter decision:
  The existing Messages.jsx Push/Email tabs filtered client-side on whatever single
  page of <=50 already-fetched rows. That undercounts whenever the channel split
  across pages (e.g. 40 push + 15 email = 55 total, push tab would show only 35
  because limit=50 returned a mixed first page). Moved to server-side: filter=push
  or filter=email now triggers a refetch with channel=push|email. 'converted' tab
  stays client-side (no backend outcome filter; out of scope). This is a correctness
  fix, not just plumbing.

Frontend:
- messages/page.js: reads channel, status, from, to from searchParams; passes as
  initialChannel, initialStatus, initialFrom, initialTo to MessagesScreen.
- Messages.jsx: seeds filter state from initialChannel (push|email or 'all');
  statusParam, fromParam, toParam are read-only initial values threaded into the load()
  useCallback dep array; all four go into the fetch query string.
- DashboardScreen.jsx tiles: Push Sent -> /admin/messages?channel=push&status=sent&from&to;
  Emails Sent -> /admin/messages?channel=email&status=sent&from&to.

=== PART 3: Emails Captured / Push Subscribers -> Customers ===

Field existence check (channels.push.subscribedAt):
  Confirmed present. Every genuine opt-in write path sets it:
    - routes/push.js:177 (FCM subscribe endpoint)
    - routes/proxy.js:547 (storefront proxy)
  One exception: services/pushHygiene.js:163 (clearPushSuppression) sets
  subscribed:true WITHOUT touching subscribedAt. This is correct — it's a
  re-activation after suppression, not a new opt-in, so the original subscribedAt
  should stand.

pushSubscribers tile count fix (today-stats handler):
  Was: Profile.countDocuments({shopDomain, 'channels.push.subscribed': true})
       — all-time count, silently ignores the Dashboard's date range selector.
  Now: adds 'channels.push.subscribedAt': {$gte: from, $lte: to}
       so the tile answers "subscribed within the selected range" like every
       other tile in the today-stats response.

Backend (backend/routes/profiles.js — GET /:shopDomain/profiles):
- Added from/to params: parsed to rangeFrom/rangeTo Date objects (null if absent).
- email_captured filter: adds {$exists: true, ...(rangeFrom? $gte), ...(rangeTo? $lte)}.
  Without from/to: just {$exists: true} — same as before.
- push_subscribed filter: NEW filter value. Sets channels.push.subscribed: true;
  if rangeFrom or rangeTo: adds channels.push.subscribedAt range. Without from/to:
  no date filter (shows all subscribers — consistent with full-tab view intent).
- Existing has_cart / bought_once / repeat_buyer / going_quiet branches untouched.

Frontend:
- customers/page.js: reads filter, from, to from searchParams; passes as
  initialFilter, initialFrom, initialTo to CustomersScreen.
- Customers.jsx: seeds filter state from initialFilter if it matches FILTER_TABS
  (otherwise falls back to 'everyone'); fromParam/toParam are read-only initial
  values in the load() dep array.
- DashboardScreen.jsx tiles: Push Subscribers -> /admin/customers?filter=push_subscribed&from&to;
  Emails Captured -> /admin/customers?filter=email_captured&from&to.

=== PART 4: Popups Shown -> slide-out panel ===

Backend: New endpoint GET /api/profiles/:shopDomain/popups-shown
  - StorefrontEvent rows of type 'push_prompt_shown' within from/to, paginated.
  - Returns {events: [{ts, path, customerId}], total, page, limit}.
  - customerId returned as stored, ONLY when the event already carries one — no
    Profile lookup step. Most rows have customerId=null (event fires before opt-in).
  - StorefrontEvent was already required at the top of profiles.js (used by today-stats).
  - requireAuth + requireStoreOwner; scoped by shopDomain param.

Frontend: PopupsShownPanel component (module-level, inside DashboardScreen.jsx)
  - Fixed-position slide-out overlay with backdrop.
  - role="dialog", aria-modal, aria-label="Popups Shown".
  - Escape key closes it (useEffect listener).
  - Fetches GET /api/profiles/:shop/popups-shown?from&to&page&limit on open.
  - Displays per-row: formatted timestamp, path (or "unknown page"), customer ID if present.
  - Prev/Next pagination.
  - Empty state: "No popups shown in this range."
  - Opened by Popups Shown KPI tile onClick -> setPopupsPanelOpen(true).

=== PART 5: New Subscribers Today -> scroll + highlight ===
