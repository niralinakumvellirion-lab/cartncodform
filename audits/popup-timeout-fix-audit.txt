  // Races a fetch against a plain timer so a cold-starting backend can't
  // block the popup/discount config load (and, in turn, initIntentTriggers())
  // for as long as the browser's own fetch would otherwise wait.
  function fetchWithTimeout(url, ms) {
    var timeout = new Promise(function(resolve) {
      setTimeout(resolve, ms || 3000, null);
    });
    return Promise.race([fetch(url), timeout]);
  }

BEHAVIOR NOTE (observed, not a deviation -- matches what the task
already called out as safe)
=========================================================================
When the 3s timer wins the race, fetchWithTimeout() resolves with
`null` (not a Response object). The very next line in both functions,
`r.ok ? r.json() : null`, then evaluates `null.ok` -- this throws a
TypeError, which is caught by each function's existing
`.catch(function () { /* keep defaults */ })` at the end of the chain.
So a timeout still results in "keep defaults" exactly as the task
intended, just via the catch block rather than the `r.ok` false
branch. Functionally equivalent to the task's stated expectation
("resolve with null (use defaults) and let initIntentTriggers() run
immediately") -- initIntentTriggers() is gated on Promise.all()
settling (not on any particular resolved value), and both promises
here always resolve (never reject) by design, so this still unblocks
initIntentTriggers() within the 3s cap regardless of which path
(r.ok-false vs. thrown-and-caught) is taken.

A genuinely slow-but-eventually-successful fetch (e.g. one that
returns after 3.5s) is NOT aborted by this change -- Promise.race()
does not cancel the losing fetch, it just ignores its result once the
timer promise has already resolved the race. The abandoned fetch
still completes in the background (its response is simply never used
by fetchPopupConfig()/fetchDiscountConfig() once they've already
resolved via the timeout path) -- no AbortController was introduced,
matching the task's exact given helper code, which does not use one.
