AUDIT: queue-drag-not-working
File: frontend/app/admin/queue/QueueScreen.jsx (commit 52a9300)
Date: 2026-10-14

=== ROOT CAUSE ===

Two confirmed code bugs; one additional issue that requires browser verification.

PRIMARY (Check #3 — React setState during dragstart):
  DayDetailsPanel, line 717-720:
    onDragStart={isDraggable ? e => {
      e.dataTransfer.effectAllowed = 'move';
      if (onCardDragStart) onCardDragStart(item);  // ← calls setDragItem(item)
    } : undefined}

  Planning list, lines 2292-2295:
    onDragStart={planIsDraggable ? e => {
      e.dataTransfer.effectAllowed = 'move';
      setDragItem(item);  // ← direct call
    } : undefined}

  In Next.js 14 (React 18 createRoot), dragstart is a "discrete" user-input
  event. React flushes all state updates synchronously at the end of the
  event handler, WITHIN the same browser event dispatch cycle (before the
  browser finishes processing dragstart). This means:

    1. onDragStart handler fires
    2. setDragItem(item) queued
    3. Handler returns to React
    4. React flushes: QueueScreen re-renders → DayDetailsPanel re-renders
       → card style changes: opacity 1 → 0.4 (via isBeingDragged = true)
       → transition: 'opacity 0.15s' fires
    5. Browser finishes dragstart (reads DOM for ghost image)

  Step 4 happens BEFORE step 5. The DOM is mutated — opacity changed,
  a CSS transition started — during the dragstart event. Chrome cancels
  the drag (or produces a broken ghost) when the drag source element's
  DOM is mutated during dragstart before the browser commits to the drag.

  This is the documented React + Chrome drag-and-drop failure pattern.
  Every React DnD tutorial warns against it.

SECONDARY (Check #4 — missing dataTransfer.setData):
  Neither onDragStart handler calls e.dataTransfer.setData(). Firefox
  requires at least one setData() call in dragstart; without it, Firefox
  silently cancels the drag and never fires dragover or drop on any target.
  Chrome does not require setData, but calling it is required for full
  cross-browser support.

  Calendar cell structure (lines 471-508):

  This button covers the ENTIRE cell. During a drag, pointer events hit
  the button, not the cell div. dragover/drop fire on the button, then
  bubble to the cell div where the handlers live.

  React 18 uses event delegation (listeners on root). When dragover fires
  on the button and bubbles to root, React calls the div's onDragOver via
  its synthetic event system. e.preventDefault() IS called on the native
  event (React proxies it). The browser should allow the drop.

  onDrop on the div also fires (drop bubbles from button → div). ✓

  However: some browser/version combinations require e.preventDefault()
  to be called at the ACTUAL target element (the button), not just in a
  bubbling ancestor. If that is the case in the user's browser, drop
  never fires and the cursor permanently shows no-drop.

  CANNOT CONFIRM without a browser test. Low probability but non-zero.

=== RECOMMENDED FIX ===

The smallest fix for the primary root cause (defers DOM mutation until
after the browser has committed to the drag):

  In DayDetailsPanel onDragStart (line 717):
    onDragStart={isDraggable ? e => {
      e.dataTransfer.effectAllowed = 'move';
      e.dataTransfer.setData('text/plain', item._id);  // add: Firefox fix
      requestAnimationFrame(() => {                     // add: defer mutation
        if (onCardDragStart) onCardDragStart(item);
      });
    } : undefined}

  In planning list onDragStart (line 2292):
    onDragStart={planIsDraggable ? e => {
      e.dataTransfer.effectAllowed = 'move';
      e.dataTransfer.setData('text/plain', item._id);  // add: Firefox fix
      requestAnimationFrame(() => {                     // add: defer mutation
        setDragItem(item);
      });
    } : undefined}

  requestAnimationFrame fires AFTER the browser has captured the drag
  ghost image and committed to the drag operation. The card opacity then
  changes to 0.4 on the first animation frame after drag start, which is
  the correct visual feedback without cancelling the drag.

  If the ccf-day-cell-btn (Check 5) proves to be a problem in browser
  testing, add this to the button JSX:
    onDragOver={e => { if (dragItem) e.preventDefault(); }}

  This ensures e.preventDefault() is called on the actual event target
  (the button), satisfying any browser that requires target-level
  preventDefault rather than ancestor-level.
