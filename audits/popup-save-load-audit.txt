What it produces: `compressed` is a base64 DATA URI string in the form
`data:image/jpeg;base64,<base64 text>` -- the browser's Canvas
`toDataURL('image/jpeg', 0.7)` call JPEG-encodes the canvas contents
(already resized so neither dimension exceeds 800px, aspect ratio
preserved) at quality 0.7 (on Canvas's 0-1 scale), then base64-encodes
the resulting binary JPEG bytes, and prefixes the MIME-type header.
This full string is what gets stored into activePopup.imageUrl and,
eventually, sent in the popup PATCH body (section 2) and persisted as
the `popup.imageUrl` or `mobilePopup.imageUrl` field in MongoDB.

Size estimate (width x height x bytes-per-pixel / compression, as
asked) -- worst case for this code path is a source image whose
SHORTER side is already >= 800px too, so both output dimensions land
at the 800px cap (a portrait or landscape source only caps the longer
side, producing a smaller canvas on the other axis, so 800x800 is the
upper bound this code can ever produce, not the typical case):

  Pixel count (worst case): 800 x 800 = 640,000 pixels
  Raw (uncompressed) bitmap equivalent: 640,000 px x 3 bytes/px (RGB)
    = 1,920,000 bytes (~1.83 MB) -- this is NOT what gets sent; it is
    the baseline JPEG compression works from.
  JPEG at quality ~0.7 (a "medium-high" quality setting) typically
  yields somewhere around 0.1-0.3 compressed bytes per source pixel
  for ordinary photographic content (product photos, lifestyle
  images) -- this is an empirical range from how JPEG's DCT/quantization
  behaves at that quality level, not a value this codebase configures
  or guarantees.
    Low end:  640,000 x 0.10 = ~64,000 bytes  (~62 KB) compressed JPEG
    Mid:      640,000 x 0.15 = ~96,000 bytes  (~94 KB) compressed JPEG
    High end: 640,000 x 0.30 = ~192,000 bytes (~188 KB) compressed JPEG
  Base64 encoding inflates binary size by ~4/3 (33%), plus the
  `data:image/jpeg;base64,` prefix (~23 bytes, negligible):
    Low end:  ~64,000  x 1.33 = ~85 KB  base64 text
    Mid:      ~96,000  x 1.33 = ~128 KB base64 text
    High end: ~192,000 x 1.33 = ~255 KB base64 text

So a realistic estimate for a typical 800x800 JPEG at quality 0.7,
stored as this code's base64 data URI, is roughly 85 KB to 255 KB of
text, with something around 100-150 KB being a reasonable "typical
photo" midpoint. A simpler/flatter image (solid colors, less detail --
e.g. a graphic or logo rather than a photo) compresses far better than
this range; a very high-detail/noisy photo can run higher. This is an
estimate based on general JPEG compression behavior, not a value
measured against an actual file in this session.

5. After save succeeds - does it reload popup config from backend, or
   just keep local state?
====================================================================
It does NOT reload from the backend. Per the full saveSettings()
function shown in section 2, the only things that happen after the
`await Promise.all([...])` succeeds are:
  166	      setSuccess(true);
  167	      setPopupImageChanged(false);
  168	      setMobileImageChanged(false);
No apiGet call, no re-fetch of /api/profiles/:shop/popup, and no other
state setter touches `popup` or `mobilePopup` here -- they simply keep
whatever value was already in local state (the same value that was
just PATCHed to the backend, since popup/mobilePopup are the source
the PATCH body itself was built from). `setSuccess(true)` only toggles
a success banner (grepped every use of the `success` state in this
file -- it appears at declaration (line 65) and at 2 render sites
(lines 595 and 1874, both `{success && (...)}` conditional banners) --
it is never used as a dependency of any effect, so it cannot trigger a
reload as a side effect either).

This is safe/correct as long as the PATCH succeeded and the local
state accurately reflects what was sent (which it does, since the
PATCH body is built directly from `popup`/`mobilePopup`/`popupBody`,
themselves derived from local state) -- there is no scenario in the
current code where the backend's stored value could end up different
from what local state believes was just saved, EXCEPT for the
asymmetry already flagged in section 2 / audits/settings-image-skip-
audit.txt: `popup.imageUrl` is sometimes omitted from the outgoing
PATCH (when unchanged), but that's fine here too, because when it's
omitted, local `popup.imageUrl` also still holds the correct
(unchanged) value the backend already had -- nothing diverges.
