3. STEP 5 ("REDIRECTING") — A DESIGN NOTE, NOT A BUG
====================================================================
In ccf-push.js, renderDiscountCode() builds ONE html block (icon, "N% OFF
Unlocked!", "Expires in N days", the code chip, and the pulsing "Applying
your discount automatically..." line) and swaps it into #ccf-content-
section in a single synchronous call; a 2-second setTimeout then performs
the real navigation. There is no second, visually distinct DOM state
between "just unlocked" and "about to redirect" in the real
implementation — the button's brief 'gift'/"Redirecting..." label
(set immediately before the swap) is created and destroyed inside that
same synchronous call, before a browser could ever paint it, and is
therefore never actually visible to a real customer either.

Given the task's explicit request for 5 distinguishable steps including a
named "Redirecting" one, the preview renders the SAME UnlockedView for
both 'unlocked' and 'redirecting', with one addition: 'redirecting' shows
a small labeled badge ("REDIRECTING (SIMULATED — NO REAL NAVIGATION)")
above the content. This is explicitly a preview-only annotation, not a
second real DOM state ccf-push.js has — flagged here rather than silently
presented as if it were pixel-identical to something in production.

5. PREVIEW-VS-STOREFRONT DIFFERENCES FOUND AND FIXED
====================================================================
The OLD admin preview (replaced by this change) was a simplified,
NOT-pixel-accurate mock, not a real reimplementation of ccf-push.js.
Differences found while rebuilding it against ccf-push.js as source of
truth, and fixed:

  1. Split layout's image/content ratio was 40%/60% in the old preview;
     ccf-push.js's real desktop split is 45%/55%. Fixed.
  2. Card layout's "no image" state showed nothing in the old preview;
     ccf-push.js shows a bouncing bag icon centered in the gradient.
     Fixed (split's own "no image" gradient correctly stays icon-less,
     matching ccf-push.js — only card gets the bag icon).
  3. Card layout never showed the green "🏷️ {discount offer text}" badge
     in the old preview at all. Fixed — shown when a discount is enabled,
     using the real per-action offer text (ccfDiscountOfferText()
     equivalent: emailDiscount.offerText or the auto "Add your email to
     get N% off" line when the email field shows, else pushDiscount
     .offerText or "You get N% off as a subscriber").
  4. Split layout never showed ANY discount UI in the old preview. Fixed
     — now shows the same generic offerHeadline text + email input
     ccfBuildDiscountFields() adds after Deny, reading the ACTUAL
     DiscountConfig.offerHeadline field (a value this screen wasn't even
     fetching before this change — added to the discountRules fetch).
  5. Banner layout's old preview didn't distinguish it from the other
     layouts' discount handling; it had no email/discount UI to begin
     with, which happened to already match reality (banner never shows a

6. REAL BUG FOUND AND FIXED WHILE BUILDING THIS
====================================================================
Initial implementation computed previewWantsDiscount purely from
discountRules (push.enabled || email.enabled), without the banner
exception. That would have let the step bar show "Unlocked"/"Redirecting"
tabs, and auto-advance actually reach them, for a Classic popup set to
Banner layout with a discount configured — even though ccf-push.js's own
`layout !== 'banner' && ccfDiscountEnabled()` guard means a real banner
popup NEVER offers a discount at all. Fixed by computing an
activeStyleId/layout-aware previewEffectiveLayout at the top of the
component and gating previewWantsDiscount on `previewEffectiveLayout !==
'banner'` — this is the single source of truth the step machine, the step
bar, AND ClassicPreview's own (now redundant-but-harmless) internal
banner check all agree with.

7. STEP BAR JUMP / REPLAY / RESET-ON-CHANGE
====================================================================
- Step bar: a real button per visible step (Unlocked/Redirecting hidden
  when previewWantsDiscount is false), role="tablist"/role="tab" +
  aria-selected, onClick calls setPreviewStep(id) directly — jumps
  immediately to any step regardless of current state or whether Allow
  was ever clicked, per the explicit "without replaying" requirement.
- Replay: a separate button, sets previewStep back to 'prompt' and clears
  the simulated email field.
- Reset-on-change: a stable JSON-serialized key (device, activeStyleId,
  activeStyleFields, and whichever of popup/mobilePopup is the config
  actually being previewed) is compared each render via a ref; the
  step/email only reset when that key's STRING VALUE actually changes —
  so editing any customizer field (headline, colors, image, extra style
  fields, switching styles, switching the device tab) resets to Prompt,
  but re-renders caused by unrelated state (e.g. the simulated email
  input itself, or the step bar) do not loop or reset each other.
