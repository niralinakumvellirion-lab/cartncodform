CRITICAL FINDING — the given /api/queue/festival route would have
403'd on every single request
====================================================================
Part E's given route was:
  router.post('/festival', requireAuth, requireStoreOwner, async (req, res) => {...})

backend/middleware/requireOwner.js's requireStoreOwner (read in full
to confirm) does, unconditionally:
  if (req.shopDomain !== req.params.shopDomain) {
    return res.status(403).json({ error: 'Not authorized for this store' });
  }

A route path of plain `/festival` has no `:shopDomain` segment, so
`req.params.shopDomain` is always `undefined` -- which never equals
a real shop domain string. Every single request to this endpoint,
from any authenticated shop, would have received a 403 "Not
authorized for this store" -- the Approve and Add to Queue buttons
would have been completely non-functional, always failing with the
generic "Failed to approve"/nothing-happens alert the frontend shows
on any thrown error. This is exactly why every OTHER route already in
backend/routes/queue.js uses the `/:shopDomain/...` path shape (GET
/:shopDomain, POST /:shopDomain/:jobId/send-now, POST
/:shopDomain/:jobId/cancel) -- this new route was the one exception,
and would have been broken from the moment it shipped.

FIX: changed the route path to `/:shopDomain/festival`, matching
this file's own established convention, and updated both frontend
call sites (Approve, Add to Queue) to
`` `/api/queue/${encodeURIComponent(shop)}/festival` `` accordingly,
also matching how every other apiGet/apiSend call in this same file
already addresses shop-scoped backend routes. Dropped the `shop`
field from the request body in both calls since the backend handler
never read `req.body.shop` in the first place (it already correctly
used the verified `req.shopDomain` from the session token, same IDOR-
safe pattern as every other route in this file) -- it was purely
dead weight once shop travels via the URL path instead.

This is not a scope expansion: Part E explicitly asked this task to
WRITE this exact route in this exact file. Writing it so it actually
works, rather than writing it exactly as given knowing it would 403
on every call, is the same standing practice this session has applied
to every previous backend route given by a task (see e.g.
audits/customers-journey-merge-build-audit.txt for an equivalent
:profileId-filter gap in a different route).
