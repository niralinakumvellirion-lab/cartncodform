PART A - backend/services/realtimeTrigger.js
=========================================================================
Created exactly as given, byte-for-byte. Reviewed carefully against
the real generateCopy(store, signalType, product, channel) signature
(verified in the immediately preceding Phase-1-realtime task) before
implementing — unlike that earlier task's given code, THIS task's
`generateCopy(store, signalType, '', channel)` call is correctly
shaped: `store` is `{shopDomain, voice: {}}` (has the `.shopDomain`/
`.voice` the function reads), `signalType` is the plain string
argument (not wrapped in an object), `''` as the product arg is
falsy exactly like `null` would be (every internal `product &&
product.x` check in generateCopy() short-circuits the same way for
both), and `channel` ('push' or 'email') is actually passed this
time. No fix was needed here.

NOTE - verified the missing signal double-check is covered by an
EXISTING mechanism, not a gap this task needed to close.
maybeScheduleRealtime() never itself confirms a `cart_abandon`/
`checkout_abandon` Signal document actually exists/fired for the
profile — it schedules purely on the CALLER's say-so (Part B decides
to call it based on the raw storefront event type just recorded, e.g.
any add_to_cart -> assume cart_abandon is relevant). This means a
customer who adds to cart and then completes checkout within seconds
would still get a job created (with `runAt` in the future, per the
configured delay). Checked whether anything else in this codebase
protects against that job firing anyway: yes — backend/routes/
webhooks.js's order webhook handler already cancels ANY pending
ScheduledJob matching the shop's cartToken/customerId the moment an
order is placed (`ScheduledJob.updateMany({shopDomain, status:
'pending', $or: cancelOr}, {status:'cancelled', error:'order
placed'})`), regardless of how that job was created — brain-scheduled,
legacy-rule, or (now) realtime-triggered. Since maybeScheduleRealtime()
sets `cartToken` on the job it creates (from the profile's own
identifiers), a converting customer's realtime-triggered job is
cancelled by this SAME existing mechanism, exactly like a normal
brain-scheduled one would be. No additional signal-verification logic
was added to realtimeTrigger.js as a result — it wasn't needed.

PART C - backend/services/brain.js
=========================================================================
Read the full file first, as instructed. Found a structural mismatch
between the task's literal Part C snippets and the real code that
required adapting the implementation, not just the variable names:

DEVIATION 1 (the significant one) - the task's 3 snippets ("load
AutomationConfig at the start of runBrainForShop()", "add enabledSignals
check where signalType is checked", "add delay where runAt is
computed") all read as if they belong to ONE function. They don't:
runBrainForShop(shopDomain) is a thin per-SHOP orchestrator — it only
loads the shop's profile ids and batches calls to a COMPLETELY SEPARATE
function, runBrainForProfile(profileId, shopDomain), which is where
ALL of the real per-signal ranking, the `winner.type` check, and the
`computeRunAt()` call actually live. Implementing the given snippets
literally inside runBrainForShop() alone would be impossible (there is
no `winner`/`runAt` in that function's scope at all) and would leave
runBrainForProfile() — called independently by the nightly poller loop
AND, per backend/__tests__/brain.test.js and weightsService.test.js,
directly by tests — with no automation-config awareness whatsoever.
Fixed by loading `cfg` ONCE in runBrainForShop() (matching the task's
own framing of "at the start of the function" — this is also the more
efficient design, avoiding a redundant per-profile AutomationConfig
lookup for every profile in the same shop's batch) and THREADING it
through as a new, OPTIONAL third parameter:
  async function runBrainForProfile(profileId, shopDomain, cfg = null) { ... }
  ...
  runBrainForProfile(id, shop, cfg)   // inside runBrainForShop()'s batch loop
Checked every call site of runBrainForProfile() before making this
change (grepped the whole backend/ tree): all 19 are in
__tests__/brain.test.js and __tests__/weightsService.test.js, every
one calling it with exactly 2 arguments (`runBrainForProfile('p1',
SHOP)`) — the new 3rd parameter defaulting to `null` is fully
backward-compatible with every existing call site, and every new
`cfg?.x` check added below is written to no-op cleanly when `cfg` is
null (confirmed: 151/151 tests still pass unchanged).

DEVIATION 2 (a real bug, not just structural) - the given delay-floor
snippet reassigns `runAt`:
  if (runAt < new Date(Date.now() + delayMs)) {
    runAt = new Date(Date.now() + delayMs);
  }
but the existing code declared `const runAt = computeRunAt(...);`.
Reassigning a `const` binding throws `TypeError: Assignment to
constant variable` — and since `cartAbandonDelay`/`checkoutAbandonDelay`
default to 60 minutes (a fairly long floor) while `computeRunAt()`'s
own fallback (no personal/shop hour history) schedules for "the next
non-quiet hour from now" (often much sooner than 60 minutes out), this
branch would be reached routinely, not as a rare edge case — this was
a near-guaranteed runtime crash the moment ANY shop had automation
config with a real delay value AND a signal ranked without enough send-
time history to push computeRunAt() past that delay on its own.
Changed `const runAt` to `let runAt`, matching the given code's own
(correct) intended behavior for everything else.

Where each Part C snippet actually landed inside runBrainForProfile():
  - enabledSignals check: inside the existing per-signal ranking loop
    (`for (const { signal: s } of ranked) { ... }`), right after the
    existing SignalConfig-based `continue`, before the `tooSoon`
    cooldown check — an independent, additional skip condition, not a
    replacement for the existing SignalConfig mechanism.
  - delay floor: immediately after `let runAt = computeRunAt(...)`,
    using `winner.type` (already resolved by that point in the
    function) to look up the right delay field, exactly as the given
    snippet specified.
