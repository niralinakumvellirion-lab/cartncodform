2. What API call(s) it makes -- endpoint, method, payload
====================================================================
TWO sequential (awaited, not parallel) apiSend() calls per click:

  Call 1: PATCH /api/profiles/{shop}/settings
    Payload: { voice, caps, quietHours, timezone } -- the 4 pieces of
    top-level React state this screen holds for those settings.

  Call 2: PATCH /api/profiles/{shop}/popup
    Payload: { ...popup, mobilePopup } -- the desktop popup config
    object spread at the top level, plus the entire mobilePopup object
    nested under a `mobilePopup` key.

Both go through frontend/lib/api.js's apiSend() (not re-read in full
for this task, but its shape is already established from earlier
sessions: attaches the App Bridge session token as a Bearer header,
retries once on a 401 after a 500ms wait, otherwise no retry and no
explicit client-side request timeout -- it relies on the browser's own
fetch() default behavior, which has no built-in timeout at all).

Because these two calls are sequentially awaited (not
Promise.all'd), the SECOND request (popup) never starts until the
FIRST (settings) has fully resolved -- if the settings PATCH hangs or
is slow, the popup PATCH (and therefore the whole save, and the
`success`/`saving` state) is blocked behind it.

3. How it handles loading state and errors
====================================================================
- `saving` (boolean state) is set true at the very start of
  saveSettings() and false in a `finally` block -- so it always clears
  regardless of success or failure. While true, both Save buttons
  render disabled, gray, with text "Saving..." (line 557 / 1811 use the
  ellipsis character, ...).
- `error` (string state) is cleared at the start of every save attempt
  and set from `e.message || 'Save failed'` in the catch block -- so
  only the LATEST attempt's error is ever shown; a stale error from a
  previous failed save is cleared as soon as a new save begins, even
  before the new one has resolved.
- `success` (boolean state) is set true only after BOTH apiSend() calls
  resolve without throwing; it is explicitly reset to false at the
  start of every new save attempt. There is no auto-dismiss timer for
  the "Saved" message anywhere in this file -- once shown, it stays
  visible until the user triggers another save (unlike, for comparison,
  other screens' `setTimeout` + `setSendResult('')` patterns seen in
  earlier files this session, e.g. Journey.jsx's sendResult). This
  screen's success banner has no such timeout.
- If the FIRST call (settings) throws, the catch block fires
  immediately and the SECOND call (popup) is never attempted at all --
  a failure in the settings save silently prevents the popup save from
  running, with no separate error message distinguishing which of the
  two actually failed. The user only ever sees one generic error
  string, never knowing whether their popup changes were saved or not
  in that scenario.

4. How long it waits before timeout
====================================================================
No explicit timeout exists ANYWHERE in this flow -- not in
saveSettings() itself (no setTimeout/AbortController/Promise.race
wrapping either apiSend() call), and not in apiSend() (frontend/lib/api.js,
per its established behavior from earlier reads this session):
plain fetch() calls with no `signal`/timeout option set at all. The

response at all, this UI would show "Saving..." indefinitely, with no
