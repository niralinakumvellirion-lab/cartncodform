FIX B1 — phone identity split

Approach taken:
  cleanIdentifiers(identifiers, defaultCountry) now normalises the phone field
  to E.164 via normalizePhone(val, defaultCountry) before storing it.
  Falls back to the raw trimmed value when normalisation fails (invalid/test numbers).

  defaultCountry is threaded from upsertProfile(options.defaultCountry, default 'IN')
  into cleanIdentifiers; NOT hard-coded inside cleanIdentifiers so the default site
  is easy to grep for and change per-store in the future.

  Backward compat: upsertProfile computes phoneVariants (a de-duped Set) before
  calling buildQuery:
    1. ids.phone (normalised E.164)
    2. rawPhone if it differs from ids.phone (caller-side raw, e.g. proxy.js COD)
    3. getNationalNumber(ids.phone) — the national number stripped from E.164
       (e.g. "9876543210" from "+919876543210"), for profiles created before
       this fix that stored the bare national number from the COD form.

  buildQuery uses $in: phoneVariants when phoneVariants.length > 1, falling back
  to a plain exact match for single-variant lookups.

  getNationalNumber() added to backend/utils/phone.js using the same
  parsePhoneNumber from libphonenumber-js already imported there.

  No callers were changed to pass raw phone — they continue to pass whatever they
  have. Both pre-normalized (discounts.js WA path) and un-normalized (proxy.js
  COD path) phone values are handled centrally.

Scope confirmed correct:
  discounts.js action='whatsapp' at line 117: phone: normalized — unchanged.
    phoneVariants will be ['+919876543210', '9876543210'] via getNationalNumber.
  proxy.js /cod-order at line 456: phone: String(phone).trim() — unchanged.
    rawPhone='9876543210', ids.phone='+919876543210' after cleanIdentifiers.
    phoneVariants will be ['+919876543210', '9876543210'] via both rawPhone and
    getNationalNumber (deduplicated).
  Neither caller modified — backward compat achieved centrally.
