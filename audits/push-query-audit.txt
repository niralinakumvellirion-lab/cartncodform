If `CustomerPushSubscription.find({ shopDomain, cartToken })` returns
ZERO rows, `cartSubs` is an empty array, the `for` loop body never
executes even once, and execution falls straight through to line 137:
  return { success: true, sent: 0, tokensFound: 0 };
-- note `success: true` even though NOTHING was sent. This return value
then reaches the poller in backend/server.js, which checks:
  if (!result.success || result.sent === 0) { ... status: 'failed' ... }
Since `result.sent === 0` is true (even though success is also true),
the job is still marked 'failed', with error defaulting to
"No active subscriber found" (result.error is undefined here, so the
fallback string is used) -- this is the exact error string seen on
every failed job in every previous audit in this investigation.

So: a cartToken with no matching CustomerPushSubscription row does NOT
throw, does NOT retry with a different identifier, and does NOT
consult the profile for any OTHER cartToken/pushToken it might have --
it deterministically returns sent:0 for that one cartToken and the
caller marks the job failed.

The value written to job.cartToken is `carts[0]` -- the FIRST element
of profile.identifiers.cartTokens, where `carts` is the profile's ENTIRE
cartTokens array, taken as-is with no filtering, no recency check, and
no cross-reference against CustomerPushSubscription to confirm that
cartToken is still live.

profile.identifiers.cartTokens is built by $addToSet (see
backend/services/profileService.js, not re-read in full here but
already traced in prior audits this session) -- values are appended
over the profile's ENTIRE lifetime and never removed, so the array's
insertion order is oldest-first. carts[0] is therefore the OLDEST
cartToken this profile has ever accumulated, not the most recent or
currently-active one.

cartToken on file) onto the job, and CustomerPushSubscription rows only
ever track a subscriber's CURRENT cartToken (each row's cartToken field
gets overwritten on every resync -- see resyncCartTokenBeacon() /

almost always have no live subscription left pointing at it, even
though the SAME customer (same profile, same physical device/pushToken)
is still actively subscribed under a newer cartToken value further
along in that same array.

SUMMARY (read-only synthesis, no code changed)
====================================================================
This directly explains the repeated "No active subscriber found"
failures traced across this entire investigation thread:
  1. brain.js schedules a job using profile.identifiers.cartTokens[0]
     -- the OLDEST cartToken ever seen for that profile, not the
     current one.
  2. sendPushToCustomers(), when given a cartToken, looks up
     CustomerPushSubscription by that EXACT cartToken value only -- no
     fallback to the profile's other cartTokens, its pushTokens, or its
     profileId.
  3. CustomerPushSubscription rows track only the CURRENT cartToken per
     device (overwritten on each resync), so an old cartToken like
     carts[0] typically has no row left pointing at it, even when that
     same customer/device is demonstrably still subscribed (confirmed
     directly in the immediately preceding task: a manual send using
     the customer's LATEST cartToken succeeded instantly).
  4. Net result: the job silently returns sent:0 (still reported as
     success:true internally) and the poller marks it 'failed' with
     the generic "No active subscriber found" message -- which reads as
     if the customer has no push subscription at all, when in fact they
     do; the job simply targeted a stale identifier.

Not fixed here (audit only, per task scope). A fix would need to change
either what brain.js writes to job.cartToken (e.g. the LAST/most recent
cartToken, or a value cross-checked against
CustomerPushSubscription/pushTokens at schedule time or at send time),
or change sendPushToCustomers() to fall back to the profile's other
identifiers when the given cartToken has no match -- neither was
implemented in this task.
