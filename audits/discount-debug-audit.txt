IMPORTANT ROUTING NOTE (read first — affects how to read sections 2 & 3)
----------------------------------------------------------------------------
The storefront calls `fetch('/apps/cartncodform/generate-discount?shop=...')`
(App Proxy path). That exact route — `POST /generate-discount` — is defined
in backend/routes/proxy.js (line 149), NOT backend/routes/discounts.js.
discounts.js exposes a DIFFERENT, secondary route at `POST
/api/discounts/:shopDomain/generate` (line 297) — same underlying logic,
different path, not the one the storefront actually hits.
Both routes call the exact same shared `generateDiscount(shopDomain, body)`
function, which lives in discounts.js and is exported for reuse:
  proxy.js:      const { generateDiscount, defaultConfig } = require('./discounts');
  discounts.js:  module.exports.generateDiscount = generateDiscount;
So "the POST /generate-discount route handler" requested in step 2 is shown
below from proxy.js (the one actually called), with discounts.js's own
`generateDiscount()` — the real logic — shown as the task's step 2 asked.

--- Email/phone form submit handling (the Allow button's click handler,
    lines 742-838 above) — summary of what happens after the customer
    types email/phone and clicks Allow ---
  1. Reads #ccf-email-input / #ccf-phone-input values (trimmed).
  2. Disables the button, shows "⏳ Setting up...".
  3. Branch A — Notification.permission === 'granted' already (discount-
     capture path, existing subscriber): skips requestPermission()
     entirely, derives `capAction` from which of email/phone were filled
     ('push'|'email'|'phone'|'both'), POSTs straight to
     /apps/cartncodform/generate-discount, then calls finishDiscount(d,
     capAction) on response.
  4. Branch B — normal new-subscriber flow: calls
     Notification.requestPermission() -> if granted, registerSW() ->
     getToken() -> saveToken() -> setupForegroundMessages() -> derives
     `action` from email/phone -> POSTs to /apps/cartncodform/
     generate-discount -> finishDiscount(d, action).
  5. finishDiscount() calls handleDiscount() (module scope) which calls
     renderDiscountCode() to swap in the code UI and schedule the
     redirect.
  6. Any fetch/registerSW/getToken/saveToken rejection calls resetButton()
     (Branch B) so the customer can retry — the popup does NOT silently
     close on error.

  OBSERVATION (not a bug being fixed here — audit only): saveToken()
  (see below) returns `Promise.resolve({success:true})` immediately,
  without waiting for its internal fetch chain to resolve. So in Branch
  B, `.then(function() { setupForegroundMessages(); })` — and everything
  after it, including the generate-discount POST — proceeds as soon as
  saveToken() is *called*, not once the backend has actually confirmed
  the subscription was saved. The subscribe-customer POST and the
  generate-discount POST race each other; they are not sequenced.

Every call to generateDiscount() (regardless of entry route) logs, in
this order:
  1. (conditionally) '[discounts] online token expired for', shop
     — only if store.onlineAccessToken exists AND
     store.onlineTokenExpiresAt has passed.
  2. UNCONDITIONALLY: '[discounts] using token type:', 'online'|'offline'
     — this is the exact line referenced in the task ("We saw earlier:
     [discounts] using token type: offline").
  3. One of, depending on outcome:
     - '[discounts] GraphQL error: ' + gqlCode  (top-level GraphQL error,
       e.g. ACCESS_DENIED)
     - '[discounts] discountCodeBasicCreate userErrors:', message
       (field-level rejection — bad input/limits)
     - '[discounts] discountCodeBasicCreate returned no
       codeDiscountNode.id' (mutation "succeeded" with no error but also
       no node — treated as failure)
     - (nothing extra — success path returns the code with no further log)
  4. If the request never reaches Shopify (network/fetch failure):
     '[discounts] Shopify API error:', err.message
  proxy.js itself only logs on its own failure path:
     '[proxy] POST /generate-discount error:', err.message
     (this fires only if generateDiscount() ITSELF throws — it currently
     never throws, it always returns a {code, error} object — so this
     proxy.js catch block is effectively dead code under normal
     operation; the only way to hit it would be an unexpected exception
     outside generateDiscount()'s own try/catch, e.g. in
     verifyProxySignature() or JSON serialization of a malformed body).
