 113  /**
 114   * Requires requireStoreOwner to have run first (sets req.store).
 115   * Blocks access unless the store's plan is 'pro'.
 116   */
 117  function requirePaidPlan(req, res, next) {
 118    if (!req.store) {
 119      return res.status(500).json({ error: 'requirePaidPlan must run after requireStoreOwner' });
 120    }
 121    if (req.store.plan !== 'pro') {
 122      return res.status(402).json({
 123        error: 'This feature requires the Pro plan',
 124        upgradeRequired: true,
 125      });
 126    }
 127    next();
 128  }
 129
 130  module.exports = { requireAuth, requireStoreOwner, requirePaidPlan };

For context — the two middlewares it depends on (same file):

  requireStoreOwner (94–111): loads Store.findOne({ shopDomain: req.shopDomain })
    -> 404 'Store not found' if none;
    -> 403 'Not authorized for this store' if req.shopDomain !== req.params.shopDomain (IDOR);
    -> sets req.store = store; next().
    (500 'Authorization check failed' on a thrown error.)

  requireAuth (10–86): verifies the Shopify App Bridge session token, sets
    req.shopDomain. Does NOT set req.store or req.userEmail.

  => requirePaidPlan chain order MUST be: requireAuth -> requireStoreOwner ->
     requirePaidPlan. requireStoreOwner needs req.params.shopDomain, so the
     route it guards must have a :shopDomain path param.

Plan check: `req.store.plan !== 'pro'` -> 402 { error, upgradeRequired: true }.

6. OBSERVATIONS FOR PHASE 7 PLANNING
================================================================================
  A. requirePaidPlan is fully implemented, exported, and unit-tested
     (backend/__tests__/requireOwner.test.js) but WIRED TO NOTHING — no route
     in backend/routes/ references it (grep: 0 matches). Nothing is currently
     plan-gated on the server.

  B. The billing lifecycle already works end to end via auth.js:
     install (/callback) -> plan detected; /upgrade -> Shopify confirmation
     URL; /billing/callback -> plan flipped to 'pro'. There is NO
     app_subscriptions/update webhook handler wired to keep Store.plan in sync
     when a merchant cancels/downgrades outside the app — worth checking
     routes/webhooks.js in Phase 7 (shopify.app.toml lists no
     app_subscriptions/update subscription either; only compliance topics are
     in the toml, other topics may be registered at runtime).

  C. Store schema is billing-ready (plan / subscriptionId / subscriptionStatus
     / planUpdatedAt). No trial metadata persisted — trialDays=7 is only sent
     to Shopify at createSubscription time; the backend can't independently
     tell "in trial" vs "paid" without re-querying Shopify (getActiveSubscription
     returns status/test but not trial state).

  D. Frontend has neither an upgrade CTA nor an onboarding flow. A Phase 7
     that adds plan gating will need: (i) the admin page to read the store's
     plan (new field on an existing stores API response, or a new endpoint),
     (ii) an upgrade button that navigates the merchant to
     `${BACKEND_URL}/api/auth/upgrade?shop=<shop>` (top-level redirect, not
     fetch — it 302s to Shopify), (iii) handling of the 402
     { upgradeRequired: true } response shape from any newly gated API call.

  E. requireStoreOwner requires req.params.shopDomain. Most current API routes
     (push.js, cod.js PATCH, automation.js) authorize via a manual
     `req.shopDomain !== <body/param>` check and do NOT use requireStoreOwner,
     so they also don't set req.store. Any route that adds requirePaidPlan
     must first adopt the requireAuth -> requireStoreOwner chain (and thus a
     :shopDomain path param), or requirePaidPlan needs a variant that loads
     the store itself.
