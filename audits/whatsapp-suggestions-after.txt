HOW PUSH/EMAIL SUGGESTIONS WORK (SUMMARY)
------------------------------------------
Both live entirely in CustomerDetail.jsx. Customer signals (topSignal.type,
topProducts, cartTokens, orders.count, lastSeenAt) come from the already-
fetched journey endpoint. Collapsible panel shows category-tabbed suggestion
cards; clicking a card pre-fills the text fields and the existing send button
then sends. No extra API call for suggestions.

WHAT I MIRRORED
---------------
Exact same pattern: ranking logic + card data at module scope, suggestion
cards above the send button, click = "select" rather than immediate send,
WhatsApp-green (#25D366) accent for selected state, "Recommended" tag on
[0]. Extracted to a `WaComposer` component (mirrors NotificationComposer /
EmailComposer structure). Used `aria-pressed` on suggestion buttons for
accessibility. No new API call for suggestions.

RISKS / COMPLIANCE NOTE
-----------------------
- cart_reminder, welcome_offer, win_back, product_followup are
  promotional/marketing messages. They correctly gate on `canFollowup`
  (consent required). Server re-checks this.
- cod_confirmation, order_thank_you are transactional / non-promotional.
  They correctly gate on `canOrder` (phone only, no consent required).
  Server re-checks this.
- The 'say_hello' fallback on the frontend has purpose='followup' — the
  WaComposer will call sendWhatsapp with template: 'say_hello'. The
  backend will return 400 "Unknown template: say_hello". This is
  intentional: the fallback is a UI hint only. When clicked it fails
  gracefully through the existing waSendError banner. A follow-up can
  either add 'say_hello' to WA_TEMPLATES or change the fallback to send
  with no template (plain followup). Risk: low (consent already checked
  by canFollowup; backend will refuse if say_hello is sent).
- No PII logged. No console.log of profile fields.
