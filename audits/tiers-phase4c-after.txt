── Output schema ─────────────────────────────────────────────

  Return type: CartLinesDiscountsGenerateRunResult

  Old shape:
    { discountApplicationStrategy: 'MAXIMUM', discounts: [{...}] }

  New shape:
    { operations: [{ productDiscountsAdd: { candidates, selectionStrategy } }] }

  Documented example (https://shopify.dev/docs/api/functions/2026-10/discount, excerpt):
  {
    "operations": [
      {
        "productDiscountsAdd": {
          "candidates": [
            {
              "message": "20% OFF PRODUCT",
              "targets": [
                { "cartLine": { "id": "gid://shopify/CartLine/0" } }
              ],
              "value": { "percentage": { "value": "20.0" } }
            }
          ],
          "selectionStrategy": "FIRST"
        }
      }
    ]
  }

  Key field: targets now use cartLine.id (cart line GID), NOT productVariant.id.
  selectionStrategy for product discounts: FIRST or ALL (MAXIMUM is order-discount only).

── Input query changes ───────────────────────────────────────

  Old: discountNode { metafield(namespace: "...", key: "...") { value } }
  New: discount { metafield(namespace: "...", key: "...") { jsonValue } }

  - Root key changes from discountNode → discount
  - Value field changes from value (JSON string) → jsonValue (already-parsed object)
  - cart.lines must include id (the cart line GID) for the targets

  Inferred from page input types (confirmed: the input field is cart.lines.id):
  query RunInput {
    cart {
      lines {
        id         ← NEW (needed for targets)
        quantity
        merchandise { __typename ... on ProductVariant { id product { id } } }
      }
    }
    discount {
      metafield(namespace: "cartncodform", key: "function-configuration") {
        jsonValue  ← replaces value (string) with a parsed JSON value
      }
    }
  }

── discountAutomaticAppCreate / Update changes ───────────────

  From build guide: "The discount's discountClasses field determines which
  Function targets will be executed during checkout."

  discountClasses: [PRODUCT, ORDER, SHIPPING] shown in build guide example.
  Our function only applies product discounts → using discountClasses: ['PRODUCT'].

── apiType from shopifyFunctions Admin API query ─────────────

  OLD filter (removed): n.apiType === 'product_discounts'
  NEW behavior: title-only lookup — n.title === 'Quantity Tier Discount'

  REASON: The exact apiType value for the new cart.lines.discounts.generate.run
  target was NOT stated in any fetched documentation page. The page frontmatter
  lists api_type: functions and api_name: discount — these are page metadata,
  not the shopifyFunctions query response field. Rather than guess, the apiType
  filter was removed; title-only lookup is safe since the title is unique.
  If the title ever changes, both approaches would break equally.

── Root cause analysis ──────────────────────────────────────

  The Shopify CLI (v4.9.0) detects which package manager to use by looking for
  a lock file in the app root (yarn.lock, pnpm-lock.yaml, package-lock.json).
  D:\cartncodform\ has NO package.json or lock file at the root level. The CLI
  cannot detect npm/yarn/pnpm and falls back to the literal string "unknown" as
  the package manager name, then tries to run "unknown install" — a command
  that does not exist.

  This is a TWO-part cause:
  A. Root-level: no package.json at D:\cartncodform\ → CLI can't detect PM.
     (This is a project structure issue — the project has backend/ and frontend/
     as separate npm projects but no app-level root package.json.)
  B. Extension-level: extensions/quantity-tier-discount/ had no node_modules or
     package-lock.json before this phase (npm install was never run there).

── Fix applied in the repo ──────────────────────────────────

  Extension-level fix (in repo — committed):
    Ran npm install in extensions/quantity-tier-discount/.
    Created: extensions/quantity-tier-discount/package-lock.json
    Created: extensions/quantity-tier-discount/node_modules/ (esbuild)

  After fix: npm run build (esbuild step) runs successfully:
    > node esbuild.config.mjs
    EXIT: 0
    Output: extensions/quantity-tier-discount/dist/index.js (ESM bundle)

  Root-level fix needed on your machine:
    The CLI still fails with "unknown install" because D:\cartncodform\ has
    no package.json. To allow shopify app build to complete the Install step,
    create a minimal root package.json:

      cd D:\cartncodform
      echo {} > package.json
      (or: npm init -y)

    After that, the CLI will detect npm (from package-lock.json in extension).
    The javy compilation step may still fail if shopify-specific tools are not
    in PATH — that is a separate environment issue, not a repo issue.

    Alternatively, upgrade the CLI:
      npm install -g @shopify/cli@latest   (upgrades to 4.9.4 or later)

STEP 5 — Liquid metafield syntax
═══════════════════════════════════════════════════════════

── Research findings ─────────────────────────────────────────

  Page fetched: https://shopify.dev/docs/apps/build/online-store/theme-app-extensions/configuration
  Result: The page shows two reserved-prefix patterns:

    Product metafields via block settings:
      block.settings.product.metafields["$app:custom"].my_key.value

    Metaobjects via shop object:
      shop.metaobjects["$app:custom"]["my_handle"].my_key.value

  Neither of these is: shop.metafields.$app.key (dot notation with $ prefix)
  Neither documents: shop.metafields["$app"]["key"] (bracket notation for namespace)

  Page fetched: https://shopify.dev/docs/api/liquid/objects/metafield
  Result: Only shows dot notation resource.metafields.namespace.key.
  No example with $app. No bracket notation for namespaces.

  Community forums (https://community.shopify.com/... multiple threads):
  Field reports suggest shop.metafields['$app:namespace']['key'].value using
  a colon-separated format. But:
    1. These are community posts, not official documentation.
    2. The format $app:namespace implies the $app PREFIX plus a custom namespace
       SUFFIX — not just $app alone as the full namespace.
    3. Metafields written with namespace='$app' (no suffix) may be resolved to
       the app's full namespace at write time and may not be readable via
       $app alone in Liquid.
    4. Metafields must have a PUBLIC_READ storefront access definition to be
       readable in Liquid — our metafield has no definition (written without one).

── Decision ─────────────────────────────────────────────────

  Cannot confirm a documented Liquid syntax for reading a shop-level metafield
  in the bare $app namespace inside a theme app extension block. The app proxy
  fetch (/apps/cartncodform/discount-config) is the primary and confirmed path.

  The ccf-tiers.js already falls back to the App Proxy when no inline config
  element is found. Removing the Liquid metafield read makes App Proxy the
  exclusive config path — simpler and confirmed to work.

── Changes made ─────────────────────────────────────────────

  extensions/cartncodform-embed/blocks/quantity-tiers.liquid:
    REMOVED:
      {%- liquid
        assign qt_mf = shop.metafields.$app.quantity_tiers
        ... (8 lines of metafield read + enabled check)
      -%}
      {%- if qt_config != nil -%}
        <script type="application/json" id="ccf-qt-config">...</script>
      {%- endif -%}

    RESULT: Block renders only the #ccf-qt-root div (no inline config).
    ccf-tiers.js always fetches config from App Proxy on load.

    Comment added in the Liquid explaining why the metafield read was removed.

  No changes to ccf-tiers.js — the App Proxy fallback was already in place.

STEP 6 — Backend Admin GraphQL api_version (REPORT ONLY)
═══════════════════════════════════════════════════════════

  File: backend/utils/shopify.js, line 9
  Constant: const API_VERSION = '2025-01';

  Supported window per https://shopify.dev/docs/api/usage/versioning:
    "Each stable version is supported for a minimum of 12 months."
    Current supported stable versions: 2026-01, 2026-04, 2026-07, 2026-10
    Listed as unsupported: 2025-04 (accessible until April 16, 2026 UTC),
                           2025-07 (accessible until ~July 2026),
                           2025-10 (accessible until ~October 2026)
    2025-01 is NOT listed at all — it is past its accessible-until date
    (would have been ~January 16, 2026 UTC).

  VERDICT: 2025-01 is OUTSIDE the supported window as of October 2026.
  Shopify "falls forward" — Admin API calls using 2025-01 are served by
  the oldest accessible stable version (currently 2026-01).
  Calls still succeed but may include schema changes not accounted for in code.

  NO CODE CHANGE in this phase (report only per spec).
  RECOMMENDATION: Update API_VERSION to '2026-10' in backend/utils/shopify.js
  in a future phase to stay on a supported version.
