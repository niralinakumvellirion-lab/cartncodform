  Sends the full `draft` object from EmailTemplates.jsx.
  EDITABLE_FIELDS (emailTemplates.js:23-27):

  All 21 design fields are saved. After save, the route returns the full
  updated template document; the editor updates savedDraft + draft to match.

=== STEP 1b — How the editor renders its own preview ===

Client-side, real-time. PreviewStage (emailStudio/PreviewStage.jsx:130-141):
  design = designFromTemplate(draft, store, { placeholder: !draft.imageUrl })
  out    = renderEmail(design)   → { css, body } fragment
  Wrapped in makeDoc() → adds DOCTYPE + Google Fonts link + <style id="s">

Uses frontend/app/admin/lib/emailEngine.js (which is emailEngine.js copied).
NO HTTP call — the preview is purely from in-memory draft state.

=== STEP 1c — GET /:id/preview vs editor preview: field mapping ===

Both use designFromTemplate() from the SAME emailEngine.js (file is shared).
All 21 EDITABLE_FIELDS map correctly in both paths.

KEY DIFFERENCE — placeholder value (emailTemplates.js:351 vs editor):

  /:id/preview  → designFromTemplate(template, store, { placeholder: !template.imageUrl })
                  → placeholder: true when the template has no imageUrl
                  → renders a placeholder image box ("photo appears here")

  /:id/send     → designFromTemplate(template, store, { placeholder: false })
                  → placeholder: false always
                  → never renders a placeholder box

  Editor preview → designFromTemplate(draft, store, { placeholder: !draft.imageUrl })
                  → same as /:id/preview — shows placeholder for no-image templates

Result: for templates WITHOUT a photo, /:id/preview shows a placeholder image
box that the actual sent email does NOT contain.
Documented in emailParity.test.js:120-124 (existing assertions intentionally
confirm the divergence).

=== STEP 1d — /:id/send vs /:id/preview render path ===

/:id/preview (emailTemplates.js:351-352):
  design = designFromTemplate(template, store, { placeholder: !template.imageUrl })
  html   = renderEmailDocument(design)

/:id/send (emailTemplates.js:529-530):
  design = designFromTemplate(template, store, { placeholder: false })
  html   = renderEmailDocument(design)

Same function, same stored fields, ONE DIFFERENCE:
  placeholder = !template.imageUrl (preview) vs placeholder = false (send)

For a template with no imageUrl:
  preview HTML contains a placeholder image block
  sent email does NOT
→ preview ≠ sent email for no-image templates (affects layout + visual appearance)

=== STEP 1e — Caching analysis ===

apiGet() (frontend/lib/api.js:47): fetch(url, { cache: 'no-store', ... })
  → browser HTTP cache bypassed on every call ✓

No SWR, react-query, module-level cache, ETag, or Vercel cache on these routes.

STALE TEMPLATE LIST (CustomerDetail.jsx EmailComposer lines 1714-1719):
  useEffect(() => {
    apiGet(`/api/email-templates?shop=...`)
      .then(d => setTemplates(d?.templates || []))
  }, [shop]);

  Runs ONCE when EmailComposer mounts (shop prop never changes on a customer
  detail page). NOT re-run when:
    - emailMode switches to 'template'
    - window regains focus / tab becomes visible
    - user navigates back to customer detail without causing remount

  If EmailComposer stays mounted while the user edits a template in another tab
  or window (or while the Next.js router cache restores the customer page),
  the `templates` state is stale.

  Consequence: handleSelectTemplate(t) calls onPreviewSubjectChange(t.subject)
  using stale t.subject → preview HEADER shows old subject; iframe body from
  /:id/preview shows NEW subject (fresh DB read). Mismatch.

  The /:id/preview HTML IS fetched fresh each time (no-store + fresh DB read) ✓.

=== STEP 1f — Root causes (plain English) ===

ROOT CAUSE 1 (render mismatch):
  GET /:id/preview uses placeholder:true for no-image templates.
  POST /:id/send uses placeholder:false always.
  A no-image template preview shows a placeholder box that the actual email
  does not contain. Customer detail preview ≠ what the customer receives.

ROOT CAUSE 2 (stale list):
  The template list is fetched once on EmailComposer mount and never refreshed.
  Editing a template in the Email Templates screen and returning to Customer
  detail shows the old subject/name in the template card and passes the old
  subject to the preview header. The iframe HTML is correct (fresh fetch), but
  the header subject shown above the iframe is stale.
