CHANGE 2 — popup config load flow (READ CAREFULLY, NO CHANGE MADE)
=========================================================================
The task's premise was that popup config might be fetched separately
from voice/caps settings (e.g. on tab-open, or in a second sequential
request), and asked to move it into one parallel Promise.all if so.

Read Settings.jsx's actual data-loading flow (the single useEffect that
depends on `shop`, lines 79-118) before making any change. It already
does exactly what CHANGE 2 asks for:

  useEffect(() => {
    if (!shop) return;
    let cancelled = false;
    Promise.allSettled([
      apiGet(`/api/profiles/${encodeURIComponent(shop)}/settings`),
      apiGet(`/api/profiles/${encodeURIComponent(shop)}/signal-configs`),
      apiGet(`/api/profiles/${encodeURIComponent(shop)}/popup`),
      apiGet(`/api/profiles/${encodeURIComponent(shop)}/push-stats`),
      apiGet(`/api/profiles/${encodeURIComponent(shop)}/profiles?limit=1`),
      apiGet(`/api/discounts/${encodeURIComponent(shop)}/config`),
    ]).then(([s, c, pop, ps, prof, disc]) => {
      if (cancelled) return;
      ...
      if (s.status === 'fulfilled') { setVoice(...); setCaps(...); ... }
      ...
      if (pop.status === 'fulfilled') {
        setPopup(pop.value?.popup || {});
        setMobilePopup(pop.value?.mobilePopup || {});
      }
      ...
    });
    return () => { cancelled = true; };
  }, [shop]);

Findings:
- There is exactly ONE data-loading effect in this file, gated only on
  `shop` becoming available -- it runs once on mount (and again if
  `shop` itself changes), not when a "popup tab" is opened.
- `/api/profiles/:shop/popup` (line 85 in the array) is already inside
  the SAME `Promise.allSettled([...])` array as
  `/api/profiles/:shop/settings` (line 83) and 4 other endpoints
  (signal-configs, push-stats, profiles, discounts config) -- all 6
  requests fire together, in parallel, in a single effect run. There is
  no separate/later/sequential fetch for popup config anywhere else in
  the file (grepped for every `apiGet(` and every `useEffect(` call in
  the file -- only 2 useEffects exist total: one for the
  isMobileView resize listener (lines 72-77), and this one).
- `showPopupCustomizer` (the state that toggles which panel is
  rendered -- the popup customizer vs. the voice/frequency cards) is a
  purely client-side render switch (`setShowPopupCustomizer(true)` on
  a button click, lines 638/667) -- it does not trigger any fetch.
  popup/mobilePopup state is already populated from the initial mount
  load by the time a merchant could click into the customizer panel,
  regardless of whether they do so immediately or after some delay.
- Promise.allSettled (rather than Promise.all) is actually a slightly
  stronger guarantee here than what the task asked for: it means a
  slow/failing request on ANY one of the 6 endpoints (e.g. discounts
  config) does not prevent the other 5 -- including popup -- from
  still resolving and updating state as soon as THEY finish, since
  each result is inspected individually via `.status === 'fulfilled'`
  after the whole batch settles. (Note: because it's `.then()` on the
  whole array rather than handling each promise's own `.then()`
  independently, all 6 results are still applied together only once
  every one of them has either resolved or rejected -- so a single
  very slow request among the 6 still delays when ALL of the resulting
  state updates apply, popup included. This is a possible future
  optimization -- attaching state updates to each individual apiGet's
  own `.then()` instead of waiting on the whole batch -- but it was not
  in scope here: the task only asked whether popup was fetched
  SEPARATELY from settings, which it is not, and whether it could be
  loaded in ONE parallel Promise.all, which it already is.)
