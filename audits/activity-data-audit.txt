Declared at line 171: `const [activity, setActivity] = useState(null);`

After a SUCCESSFUL fetch, `setActivity(actData)` (line 196) sets it
directly to the parsed JSON body of GET /api/activity's response —
i.e. whatever backend/routes/activity.js's handler returns as-is (see

object shaped like:

    checkout_start: <number>, purchase: <number> }
(exactly the 4 keys ACTIVITY_STATS reads from, always present with a

After a FAILED fetch (any rejection from either of the two
Promise.all calls), `.catch()` (lines 199-203) sets BOTH `activity`
and `notifStats` to `null` — not just the one that actually failed;
a failure in the today-stats call also blanks out `activity`, and
vice versa, since they're awaited together via Promise.all rather
than Promise.allSettled. While `activity` is null,
`activity?.summary?.[key] ?? 0` safely renders 0 (via the `?? 0`
fallback) once `notifLoading` becomes false again, rather than
crashing or showing 'undefined' — but this means a real fetch error
is visually indistinguishable from "genuinely zero activity events"
in the Activity column (both render as 0/'—' depending on loading
state) — there is no separate visible error indicator for THIS
fetch specifically (contrast with the OTHER `error` state used
lower in the file, line 543, which belongs to a different effect —
see section 4 of this audit's context and section 4 below).

BONUS — backend/routes/activity.js GET / handler, full behavior for
"what it returns for summary"
====================================================================

Full handler already quoted in relevant parts above; the summary-
specific logic (lines 36-53):

    // Get counts per event type
    const counts = await AttributedEvent.aggregate([
      { $match: { shopDomain: shop, ts: { $gte: from, $lte: to } } },
      { $group: { _id: '$eventType', count: { $sum: 1 },
                  profiles: { $addToSet: '$profileId' } } }
    ]);

    // Format counts
    const summary = {
      revisit: 0,
      add_to_cart: 0,
      checkout_start: 0,
      purchase: 0,
    };
    counts.forEach(c => {
      if (summary[c._id] !== undefined) {
        summary[c._id] = c.count;
      }
    });

`summary` is ALWAYS initialized with exactly these 4 keys, each
defaulted to 0, regardless of what's actually in the database (this
is exactly why ACTIVITY_STATS's `?? 0` fallback in the frontend is
rarely/never actually needed for a SUCCESSFUL response — the backend
already guarantees all 4 keys exist with a numeric value; the `?? 0`
only matters for a null/malformed `activity` object, i.e. the failed-
fetch case described in section 3).

The aggregate query groups ALL matching AttributedEvent documents
(scoped by `shopDomain` + the `ts` date range — NOT filtered by
`eventType` at this aggregate stage, even though `baseQuery` above it
at lines 29-33 DOES conditionally add an `eventType` filter) by
`eventType`, counting occurrences and collecting a `profiles` set
(distinct profileId values) per group — though `profiles` is never
actually read/used anywhere after this aggregate call; only `.count`
is consulted in the `counts.forEach` loop. Each aggregate result's
`_id` (the eventType string) is used to look up a matching key on the
`summary` object; if it matches one of the 4 predefined keys, that
key's value is overwritten with the real count. Any `eventType` in
the data that ISN'T one of these 4 (revisit / add_to_cart /
checkout_start / purchase) is silently ignored — counted by the
aggregate, but never surfacing anywhere in the response, since
`summary[c._id] !== undefined` is false for any other key name.

Note: the `eventType` query param (`req.query.eventType`, lines 26,
33) only affects the SEPARATE `users` list query below (baseQuery,
used at line 56 for `AttributedEvent.find(baseQuery)...`) — it does
NOT affect the `summary` aggregate at all (that aggregate's own
`$match` only filters by shopDomain + date range, lines 36-38,
independent of `baseQuery`/`eventType`). So `summary` in the JSON
response is always the FULL breakdown across all 4 event types for
the date range, even when a caller passes `?eventType=purchase` —
only the `users` array (the per-event detail list) gets filtered by
eventType, not the counts.

Full response shape (lines 88-93):
  {
    from,      // the resolved Date object used for the query lower bound
    to,        // the resolved Date object used for the query upper bound
    summary,   // { revisit, add_to_cart, checkout_start, purchase } — always all 4 keys, numeric
    users,     // array of { eventType, email, sessionId, jobId, meta, ts } — up to 200, newest first, optionally eventType-filtered
    total,     // users.length (NOT a total count of all matching events — see below)
  }

Note: `total` is `users.length`, i.e. capped at the same 200-row
limit as the `users` array itself (line 58: `.limit(200)`) — if more
than 200 AttributedEvent rows exist in the date range, `total` under-
reports the true total; it is NOT a separate `countDocuments()` call
against the full matching set. This is a different, more limited
"total" than what `summary`'s per-type counts represent (those come
from the unlimited aggregate, not the capped find().limit(200)).
