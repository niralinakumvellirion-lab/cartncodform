CONFIRM RESPONSIVE BEHAVIOUR DOWN TO 600px
-----------------------------------------------
- Page container: side padding already reduces (20px -> 12px) under the
  existing `isMobileView` breakpoint (768px, JS-based, unchanged from
  before this task) — still applies at 600px since 600 < 768.
- Tab switcher and month-nav row: use flex-wrap / no fixed widths, so
  they reflow rather than overflow at 600px.
- Calendar grid: `repeat(7, 1fr)` was already fluid; unchanged.
- Planning List rows: flex-based, thumbnail/badges are flexShrink:0 while
  the title/meta column is flex:1 with `overflow:hidden` +
  `textOverflow:ellipsis`, so long titles truncate rather than break the
  row at narrow widths (same pattern the file already used elsewhere).
- Edit modal: `width:'100%', maxWidth:560` with the backdrop's own
  `padding:20` means the modal itself already shrinks to fit a 600px (or
  narrower) viewport with margin to spare. The ImageUploadPair grid
  specifically: added a `.ccf-upload-pair-grid` className inside
  ImageUploadPair.jsx (internal-only — see next section) and a one-time
  `<style>` injection in QueueScreen (same idempotent-injection pattern
  DashboardScreen already uses for its own keyframes) with
  `@media (max-width: 600px) { .ccf-upload-pair-grid { grid-template-
  columns: 1fr !important; } }`, so the mobile/desktop upload boxes stack
  vertically under exactly the 600px threshold the task specified, rather
  than staying cramped at `1fr 1fr` the way ImageUploadPair's own inline
  styles alone would force.

CONFIRM IMAGEUPLOADPAIR'S API IS UNCHANGED
-----------------------------------------------
The component's exported signature is still exactly
`ImageUploadPair({ mobileImageUrl, desktopImageUrl, onMobileChange,
onDesktopChange })` — no prop added, removed, or renamed. Both call
sites (DashboardScreen.jsx's editor and QueueScreen.jsx's new edit
modal) pass the same 4 props they already did; neither needed any
change. The only edit to ImageUploadPair.jsx was adding a
`className="ccf-upload-pair-grid"` to its OWN internal upload-boxes
`<div>` — an implementation detail invisible to any consumer, not part
of the props contract, added specifically so an external CSS media query
could target that div (since inline styles can't do media queries on
their own, and a `className` selector with `!important` is the minimal
way to override an inline `style` from outside without changing how the
component is called). This does mean DashboardScreen's own edit modal
also now stacks its image pair under 600px as a side effect of sharing
the component — flagging this explicitly since it does touch a file
DashboardScreen also imports, even though it's a non-breaking, purely
responsive enhancement, not a regression, and DashboardScreen's own
modal already needs to work at the same iframe widths.
