3. CONFIRM — EV formula uses signalRates × channelRates from ShopWeights
================================================================================
brain.js runBrainForProfile, ranking step:
    const base = BASE_VALUE[s.type] != null ? BASE_VALUE[s.type] : 0.5;
    const sigRate  = rateFromMap(signalRates, s.type);              // ShopWeights.signalRates
    const chanRate = channelRates[estChannel]?.rate ?? 1.0;         // ShopWeights.channelRates
    const ev = Number(s.strength) * base * sigRate * chanRate;
  signalRates / channelRates come from
  `(await ShopWeights.findOne({ shopDomain: shop })) || {}`.
  Signals are ranked `.sort((a,b) => b.ev - a.ev)` — highest EV first — then the
  existing enabled/6h-cooldown filter picks the top survivor. Test 8 proves a
  weak+high-rate signal (browse_abandon EV 0.064) beats a strong+low-rate one
  (cart_abandon EV 0.045).
  DEVIATION: `chanRate` uses `estChannel` = selectChannel(type, null, profile)
  — the BASE-preference channel, computed WITHOUT the per-signal SignalConfig
  (config isn't loaded until the filter pass). So if a signal has a
  channelOverride that flips push<->email, its EV uses the wrong channel's
  rate. Ranking heuristic only; the actual send channel is still resolved
  correctly with the real config after a winner is chosen.

6. CONFIRM — neutral rate 1.0 used when the sample is too small
================================================================================
weightsService.js thresholds:
  MIN_SIGNAL_SENDS  = 10   -> signalRates[type].rate = 1.0 when sends < 10
  MIN_CHANNEL_SENDS = 10   -> channelRates[push|email].rate = 1.0 when sends < 10
  MIN_HOUR_SENDS    = 5    -> hourRates[hour].rate = 1.0 when sends < 5
  rate (when sampled) = (clicks + conversions) / sends   [signal, channel]
                      = conversions / sends              [hour, where
                        conversions counts clicked+converted]
Tests 1 (5 sends -> 1.0), 6 (3 sends -> 1.0) assert this directly; test 2
(10 sends -> 0.5) and test 5 (10 sends -> 0.5 / 0.1) assert the sampled path.
On the read side, rateFromMap() and the channelRates access both default to
1.0 when a key/entry is absent, so a shop with NO ShopWeights doc at all ranks
identically to pre-Phase-H.

9. DEVIATIONS FROM THE LITERAL SPEC (all deliberate)
================================================================================
(a) EV chanRate uses the base-preference channel estimate (selectChannel with
    null config), not the per-signal channelOverride (config not yet loaded at
    ranking time). Heuristic-only; the real send channel is unaffected. (§3)
(b) hourRates influences send time only among WELL-SAMPLED buckets (sends >= 5).
    The spec said "highest hourRates rate"; taken literally, an under-sampled
    hour (rate 1.0) would always beat a well-sampled real hour (rate ~0.1),
    which is backwards. Restricted to sends >= 5 so only learned hours compete.
(c) hourRates in weightsService keys off `job.sentAt` and falls back to
    `job.runAt` when a job was skipped before it was ever claimed (no sentAt).
    Spec said `sentAt.getHours()`; used `.getUTCHours()` per the spec's own
    "in UTC" note.
(d) STEP 6 named "the Phase-C2 nightly gate" — the branch base (main @ 0511518)
    already has it, so computeWeights was chained straight into the gate's
    per-shop `.then()` (runNightlySignals -> runBrainForShop -> computeWeights).
    No adaptation was needed.
(e) brain.test.js was edited (+3 lines: mock ShopWeights, return null) — a test
    change, required so the pre-existing brain tests don't hit a real mongoose
    model now that brain.js require()s ShopWeights.
(f) ShopWeights Map fields use `of: new mongoose.Schema({...},{_id:false})`
    rather than an inline `of: { ... }` — the inline form does not reliably
    give per-key defaults on a Map in Mongoose 8.

10. NOTICED BUT NOT TOUCHED  (out of scope for Phase H)
================================================================================
- The outcome WRITE path (C2: attribution click / order convert) is in the
  base, but no shop has accumulated enough clicks/conversions yet, so
  computeWeights currently produces all-1.0 rates and the brain effectively
  ranks by `strength × BASE_VALUE` until real data crosses the thresholds.
  Intended cold-start behaviour. (Open question #1.)
- computeWeights loads up to 90 days of ScheduledJob rows per shop with no cap
  / streaming. Fine at current volume (21 jobs in the live DB); a busy shop
  could return tens of thousands. Consider an aggregate() pipeline instead.
- BASE_VALUE is a hard-coded constant in brain.js, not configurable per shop.
  The plan's Part 3 formula also has `shopConversionRate` — that role is now
  filled by `signalRates[type].rate`. There is still no per-shop `baseValue`
  override.
- No Today-screen UI reads /weights yet (STEP 7 says "eventually"). The route
  exists and returns `{ weights }`.
- The nightly gate (whichever form) still runs signals+brain+weights
  sequentially per shop; a slow shop delays the next. Fine for one design
  partner.
- ShopWeights has no TTL / cleanup; one small doc per shop, grows with
  signal-type variety only.
- weightsService counts a 'failed'/'skipped' job as a "send" in the
  denominator (status IN ['sent','failed','skipped'] per the spec). A shop
  with many no-subscriber failures will see depressed rates. Arguably correct
  (a message that couldn't be delivered has 0 conversions) but worth noting.
