A. backend/routes/whatsapp.js
------------------------------------------------------------

NEW ROUTE: GET /:shopDomain/pending?limit=
  • requireAuth + requireStoreOwner.
  • Default limit=8, max=50, min=1 (clamped in-handler).
  • Finds opted-in profiles (consentedAt exists + !null, optedOutAt null),
    sorted channels.whatsapp.consentedAt DESC.
  • Calls ScheduledJob.distinct('profileId') for the whatsapp channel —
    all-time, not range-limited — to find ever-contacted profiles.
  • Filters to uncontacted, slices to limit.
  • Returns { total, items: [{ profileId, name, email, phone, consentedAt }] }.
  • name derived from email local-part (first segment before ._+, title-cased).
  • 500 on error.

C. AUDIT: activity.js + today-stats — channel filter correctness
------------------------------------------------------------

backend/routes/activity.js (GET /api/activity):
  • Aggregates ALL AttributedEvent by eventType, no channel filter.
  • WhatsApp-attributed events (ccf_src=whatsapp) WILL appear in counts.
  • FINDING: this is intentional — the Activity screen shows cross-channel
    engagement. No existing push/email card is broken; the route has no
    per-channel display. Counts correctly include WA-attributed revisits,
    carts, purchases. NO CHANGE NEEDED.

backend/routes/profiles.js today-stats (GET /api/profiles/:shop/today-stats):
  • pushSent: ScheduledJob.countDocuments({ channel: 'push', ... }) — ✅ explicitly filtered.
  • emailSent: messages.channel: 'email' subdoc filter — ✅ explicitly filtered.
  • emailCaptured: channels.email.capturedAt date range — ✅ profile-field, unaffected.
  • pushSubscribers: channels.push.subscribed + subscribedAt date range — ✅ unaffected.
  • NO WA jobs appear in any existing today-stats number. NO CHANGE NEEDED.

Total recovered revenue (stats?.revenueRecovered):
  • Comes from the yesterday-stats panel, which reads a legacy stats object
    with no per-channel breakdown. WhatsApp has no ScheduledJob with
    status:'pending' (all created as 'sent'), so it cannot affect any
    poller-based revenue calculation. Any WA-attributed purchase event
    would correctly add to cross-channel recovered revenue — this is the
    desired behaviour. NO CHANGE NEEDED.

orders/create attribution:
  • Reads ccf_job query param → looks up ScheduledJob by _id, reads channel.
    WA jobs exist as channel:'whatsapp' status:'sent', so attribution
    correctly records the channel. Pre-existing push/email attribution
    queries are unaffected. NO CHANGE NEEDED.

D. frontend/app/admin/screens/customerShared.jsx
------------------------------------------------------------

Added at top: 'use client' directive, useState/useCallback import,
apiSend import.

NEW EXPORT: useWhatsapp()
  Returns { sendWhatsapp, waError, waFallbackUrl, clearWaError }.

  sendWhatsapp({ shopDomain, profileId, purpose }):
    1. window.open('about:blank', '_blank') SYNCHRONOUSLY (pop-up blocker
       compliance — must be in the call stack of the click handler).
    2. w.opener = null if w exists (security: breaks opener reference).
    3. POST /api/whatsapp/:shopDomain/send with profileId + purpose.
    4. On success: w.location.href = data.url (navigates blank tab to wa.me).
    5. On API error: w.close(), setWaError(message).
    6. If window blocked (w is null): setWaFallbackUrl(data.url) — caller
       renders an "Open WhatsApp" link.
