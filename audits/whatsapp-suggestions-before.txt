PART 2 — HOW THE WHATSAPP TAB SENDS TODAY
===================================================================

Route: POST /api/whatsapp/:shopDomain/send
File:  backend/routes/whatsapp.js:125–205
Body:  { profileId, purpose?: 'followup' | 'order' }
       purpose defaults to 'followup' (line 129)

Does it accept custom text? NO.
Message text is built 100% server-side from two fixed template functions:

  waFollowupMessage(firstName, storeDomain, ctaUrl)  — lines 29–35
    "Hi {firstName}! You left something in your cart at {storeName}.
    Complete your order here: {ctaUrl}
    Reply STOP to opt out."

  waOrderMessage(firstName, storeDomain, ctaUrl)  — lines 38–45
    "Hi {firstName}! This is {storeName}.
    We wanted to reach out about your order. Find details here: {ctaUrl}
    Reply STOP to opt out."

Store link + ccf_job added at line 191–192:
  storeLink = `https://${shop}?ccf_src=whatsapp&ccf_job=${job._id}`
  Passed as the ctaUrl arg to both template functions.

Purpose rules (consent / non-promotional):
  'followup':
    - requires channels.whatsapp.consentedAt (consent) + not opted out
    - phone from channels.whatsapp.phone only (already normalised to E.164)
    - promotional / marketing — requires consent
    lines 143–150, 161–165
  'order':
    - refuses if opted out; no consent required (non-promotional)
    - phone resolved via resolveOrderPhone() which searches:
        channels.whatsapp.phone → identifiers.phones[] →
        CodOrder rows → AbandonedCustomer rows  (lines 57–104)
    lines 152–156, 166–170

Returns: { url, jobId, purpose }
  url = `https://wa.me/{digits}?text={encodedMessage}`

Frontend sendWhatsapp hook (customerShared.jsx:200–235):
  Opens blank tab synchronously, calls POST /send, sets tab.location to
  the returned url. If popup blocked, sets waFallbackUrl.

WhatsApp tab UI (CustomerDetail.jsx:1173–1272):
  No suggestion block. Two plain buttons only:
  - "WhatsApp" (followup) — shown when waProfile.canFollowup (line 1192)
  - "Order message" / "WhatsApp (order message)" — shown when
    waProfile.canOrder (line 1209)
  No text inputs, no previews, no category tabs.

WHAT NEEDS A BACKEND ADDITION:
  None. All signals needed for suggestion ranking are already present in
  `customer` (from the journey endpoint), which is fetched before the WA
  tab is shown. The ranking function can run client-side from `customer`
  + `waProfile` exactly as Push/Email suggestions do.

  The one thing that requires a backend change is supporting distinct
  message copy per template: POST /send currently only supports two fixed
  messages (followup / order). We must add an optional `template` field
  whitelisted to 6 keys. Each maps to one of the two purposes. The server
  re-checks eligibility (purpose-level consent/phone) before building the
  message, so no security regression.

SUMMARY OF GAPS VS. PUSH/EMAIL
===================================================================
1. No suggestion block in the WA tab UI.
2. POST /send only accepts purpose (2 options), not a named template
   — cannot produce 6 distinct message types from the client.
3. waProfile endpoint does not return cart/order/last-seen data, but
   that's fine because `customer` already has it all.
