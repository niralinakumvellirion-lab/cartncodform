2. The sort order used - ascending or descending by date
====================================================================
The customer/journey LIST ITSELF is NOT sorted by date at all, on
either the frontend or the backend. Journey.jsx never calls `.sort()`
on `customers` or `filteredCustomers` anywhere in the file (the only
`.sort()` calls in Journey.jsx operate on a DIFFERENT, per-customer
list -- see the NOTE below). The backend's getJourneyData() (traced in
full in section 4) sorts the underlying Signal documents by
`strength: -1` -- i.e. by signal STRENGTH, descending (strongest
signal first), not by any date/timestamp field. So: the customer rows
in the main Journey list are ordered strongest-signal-first, not
newest-first or oldest-first.

NOTE -- two OTHER lists in this same screen ARE date-sorted, but
neither is "the customer/journey list" the question is asking about:
  - Each customer's "Recent activity" timeline (rendered in the right-
    hand detail panel when a customer is selected, from
    `selectedCustomer.recentEvents`) is populated by the backend via
    `StorefrontEvent.find(...).sort({ ts: -1 })` (backend/routes/
    events.js line 443) -- DESCENDING by ts (newest event first). This
    is a per-customer EVENT list, not the customer list itself.
  - `topProducts` (the "Most interested in" section) is sorted by view
    `count` descending (events.js line 470, `.sort((a, b) => b.count -
    a.count)`) -- not a date sort either.

This is the ONLY sort that determines the order of the customer list
itself: `Signal.find(...).sort({ strength: -1 })` -- descending by
`strength` (a 0-1 float on the Signal model), capped to the 200
strongest signals shop-wide. The function's own doc comment (lines
393-396) explains why this specific sort matters beyond just display
order: "Grouping relies on Signal.find(...).sort({ strength: -1 }):
the FIRST signal seen per profile in that sorted list is guaranteed to
already be that profile's strongest, so profileMap[pid] is only ever
created once per profile" -- i.e., the strength-descending sort is
load-bearing for the grouping algorithm itself (lines 409-422), not
just cosmetic ordering.

After that grouping step, profiles are paginated via plain array
slicing (NOT a second MongoDB query/sort):
  424	  const profileIds = Object.keys(profileMap);
  425	  const pageIds = profileIds.slice(page * limit, (page + 1) * limit);
Since `profileMap` is built by iterating the strength-sorted `signals`
array in order, and each profile's FIRST appearance in that iteration
becomes its entry in `profileMap` (a plain JS object), the resulting
`Object.keys(profileMap)` preserves that same strength-descending
insertion order (per the ECMAScript spec's guarantee that plain-object
string keys iterate in insertion order) -- so the pagination slice
also ends up strongest-first, without a second explicit sort.
