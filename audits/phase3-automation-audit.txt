DEVIATION - PATCH's wholesale `$set: req.body` on nested objects is
safe ONLY because the frontend always sends both nested objects
complete
=========================================================================
backend/routes/automation.js's PATCH handler applies `{ $set: req.body
}` directly — for a top-level scalar field (enabled, brainRunHour,
etc.) this is fine, but for the 2 NESTED object fields
(enabledSignals, realtimeTriggers), MongoDB's $set REPLACES THE WHOLE
SUBDOCUMENT with whatever object the caller sent under that key — any
key the subdocument previously had that ISN'T in the new object is
lost, not merged. This is the exact same class of bug traced and fixed
in an earlier task this session (audits/mobile-popup-merge-audit.txt,
the popup.email/mobilePopup PATCH handler) — but here, since the
task's given Part B code was presented as complete and did not ask for
a per-field dot-notation merge, and per-field merging server-side is a
bigger structural change than this task's scope covers, the FRONTEND
was the piece I controlled: AutomationScreen.jsx's saveConfig() always
sends the COMPLETE current enabledSignals (all 12 keys) and
realtimeTriggers (both keys) objects in every PATCH call, never a
partial diff of just the one toggle the merchant clicked — since this
screen has a single "Save automation settings" button for the whole
form (Section 6), not per-toggle auto-save, this is also the natural,
correct way to build it regardless of the backend's behavior. Net
effect: no data loss occurs from how THIS screen actually uses the
endpoint, but the endpoint itself would still silently drop sibling
keys if some future caller ever sent a partial nested update — flagged
here for visibility, not fixed, since fixing the backend route wasn't
asked for and the given Part B code was presented as final.

Also deliberately excluded `_id`/`shopDomain`/`createdAt`/`updatedAt`/
`__v` from the PATCH body construction (the GET response, which
becomes local `config` state, includes all of these) — sending `_id`
back through `$set` risks MongoDB's "Performing an update on the path
'_id' would modify the immutable field '_id'" error (behavior can
vary by MongoDB version even when the value is unchanged), and
`shopDomain`/timestamps/`__v` simply aren't meant to be merchant-
editable. saveConfig() builds an explicit object naming only the 10
real mutable fields.


PART C - backend/server.js: nightly gate + master switch
=========================================================================
Read the existing nightly gate code in full first, as instructed,
before changing anything. The original gate:
  const target2am = new Date(`${todayStr}T02:00:00`);
  const alreadyRanToday = s.lastSignalRunAt && s.lastSignalRunAt >= target2am;
  if (nowD >= target2am && !alreadyRanToday) { ...claim, run, reset stats... }

Changed to load each shop's AutomationConfig BEFORE computing the gate
threshold (since the threshold itself must now depend on the
configured hour/minute, not a hardcoded "02:00"):
  const autoConfig = await AutomationConfig.findOne(
    { shopDomain: s.shopDomain },
    'brainRunHour brainRunMinute enabled'
  ).lean();
  const runHour = autoConfig?.brainRunHour ?? 2;
  const runMinute = autoConfig?.brainRunMinute ?? 0;
  const automationEnabled = autoConfig ? autoConfig.enabled !== false : true;
  const hh = String(runHour).padStart(2, '0');
  const mm = String(runMinute).padStart(2, '0');
  const targetTime = new Date(`${todayStr}T${hh}:${mm}:00`);
  const alreadyRanToday = s.lastSignalRunAt && s.lastSignalRunAt >= targetTime;
A shop with no AutomationConfig row yet (never visited the Automation
screen) falls back to hour=2/minute=0/enabled=true — the exact same
defaults the schema itself declares — so this change is a complete
no-op for every existing shop until a merchant actually saves
something, exactly matching Part C's own given fallback instruction.

DEVIATION 1 - the master `enabled` switch was also wired into this
gate, not just brainRunHour/brainRunMinute.
Part C's own literal template only sketched loading brainRunHour/
brainRunMinute ("Use AutomationConfig.brainRunHour/brainRunMinute...
Fall back to default hour=2, minute=0 if no config exists") — it never
explicitly said to also check `enabled` here. But Part E's own Section
1 spec gives this switch a specific, load-bearing description: "When
off, no automated notifications will be sent. Manual sends from
Journey screen still work." If the nightly gate ignored `enabled`
entirely, that toggle would be a complete no-op in the running system
— a merchant could switch "Automation enabled" off and every nightly
signal/brain run would continue exactly as before, directly
contradicting the UI's own stated behavior. Wired it in:
  if (automationEnabled) {
    runNightlySignals(s.shopDomain)
      .then(() => runBrainForShop(s.shopDomain))
      .then(() => computeWeights(s.shopDomain))
      .catch((err) => console.error('[signals] nightly error:', err.message));
  } else {
    console.log(`[signals] automation disabled for ${s.shopDomain} — skipping nightly run`);
  }
Manual sends (Journey screen's send-journey/send-journey-email, Today
screen's send-now, Queue screen's send-now) all go through entirely
separate endpoints that never touch AutomationConfig at all — none of
them were modified by this task, so "Manual sends... still work" is
already true by construction, matching the UI's own description
exactly without any further change needed there.
`lastSignalRunAt` is still claimed/updated even when automationEnabled
is false, so a disabled shop is correctly marked "checked for today"
and isn't re-evaluated on every subsequent 30s tick for the rest of
that day — only the actual runNightlySignals/runBrainForShop/
computeWeights chain is skipped. The 7-day push-stats reset
(unrelated data hygiene, not itself part of "automation") still runs
regardless of the enabled flag.

NOTE - pre-existing timezone-interpretation nuance, observed but not
touched.
The gate builds `targetTime` from a bare `` `${todayStr}T${hh}:${mm}:00`
`` string with no timezone designator — per the ECMAScript spec, a
date-time string with no explicit zone offset is parsed in the JS
engine's LOCAL time (Render's server environment, likely UTC), not
necessarily the store's configured `timezone` field that `todayStr`
itself was computed in. This subtlety already existed in the ORIGINAL
"T02:00:00" code before this task and is unrelated to what this task
asked for (making the HOUR/MINUTE configurable, not fixing how the
resulting string gets interpreted) — preserved exactly, not touched,
but flagged here for visibility since a careful reader configuring a
non-UTC-aligned run time should know this pre-existing behavior still
applies.

NOTE - minor added per-tick cost.
Computing `targetTime` now requires one extra AutomationConfig.findOne
per shop per 30-second poller tick (previously `target2am` needed no
DB lookup beyond the already-batched Store.find). This lookup is
efficiently indexed (AutomationConfig.shopDomain has `unique: true`,
which creates an index), and this app is explicitly scoped to a small-
to-medium shop count per CLAUDE.md ("small Indian D2C stores"), so no
caching/pre-check optimization was added — flagged as a known,
accepted minor cost rather than silently left unmentioned.
