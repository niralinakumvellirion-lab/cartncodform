TWO REAL BUGS FOUND IN THE GIVEN StageBadge CODE, FIXED
====================================================================
1. `const orders = customer.orders || 0;` then `if (orders > 1)` /
   `else if (orders === 1)`. A profile's `orders` field is an OBJECT
   ({ count, ltv }) in this codebase, never a plain number —
   confirmed throughout this very file's pre-existing code
   (p.orders?.count, p.orders?.ltv, used in numerous places both
   before and after this change). `orders > 1` on an object coerces
   via the default Object.prototype.toString -> "[object Object]" ->
   NaN, so both comparisons would ALWAYS evaluate false. Every
   customer, regardless of actual order count, would have fallen
   through past "Repeat buyer" and "Bought once" straight to "Has
   cart"/"Visitor" — the two most important stage labels in the whole
   badge would never have appeared for ANY customer. Fixed to read
   `customer.orders?.count || 0`.

2. `label = customer.stage === 'lapsing' ? 'Going quiet' : 'Visitor';`
   This file's own STAGE_CONFIG object (left in place, now otherwise
   unused — see below) and every other stage check anywhere in this
   codebase use the profile-stage value 'lapsed', not 'lapsing'.
   'lapsing' is a SIGNAL TYPE elsewhere in this app (Signal.type
   values include cart_abandon/lapsing/winback/etc. — a completely
   different enum from Profile.stage). A real profile.stage field
   would never equal 'lapsing', so the "Going quiet" branch could
   never have fired — every non-buying, cart-less profile would show
   "Visitor" even when genuinely lapsed. Fixed to check
   `customer.stage === 'lapsed'`.

Both fixes are called out with an inline comment directly above
StageBadge in the file itself, pointing back to this audit.

OTHER GAPS FOUND AND HOW THEY WERE HANDLED
====================================================================

3. The given CUSTOMER column snippet used
   `customer.email || customer.identifiers?.emails?.[0] || 'Anonymous'`
   for the name text, and only email for the avatar initial. Profile
   objects in this codebase never have a top-level `.email` field (so
   `customer.email` is always undefined — harmless, just a dead first
   check), but more importantly the given snippet DROPS the phone
   fallback and the "Anonymous shopper · #12345" unique-suffix
   fallback the existing code already had (`displayName`, computed
   from `p.identifiers?.emails?.[0] || p.identifiers?.phones?.[0] ||
   'Anonymous shopper · #<last5 of _id>'`). Following the given
   snippet literally would have made every phone-only or fully
   anonymous profile display the same bare word "Anonymous" with no
   way to tell them apart in the list. Kept using the existing
   `displayName` variable for the row's name text (preserving the
   phone + unique-id fallback chain), and used the given avatar-initial
   logic (email-only, falling back to '?') unchanged for the circle
   glyph specifically, since a phone-number digit as an "initial"
   would look odd and the task's own snippet only ever intended a
   letter there.

4. The given CUSTOMER column snippet's "seen X days ago" line used
   `customer.lastSeenDays ?? '—'` — no such field (`lastSeenDays`)
   exists anywhere on a profile object; the actual field is
   `lastSeenAt` (a timestamp), and the file already computes a proper
   relative-time string from it via `getRelativeTime()` (e.g. "5m
   ago", "3h ago", "yesterday", "12 days ago"). Since
   `customer.lastSeenDays` is always undefined, the literal given
   code would have shown "seen — days ago" under every single row,
   permanently, regardless of actual activity. Reused the file's
   existing `lastSeen` variable (already computed via getRelativeTime
   earlier in the row) instead, and — matching the existing,
   pre-change convention in this same file — only render the "seen
   ..." line at all when lastSeenAt is present, rather than showing a
   permanent "seen — days ago" placeholder for profiles with no
   recorded activity.

5. "MOST INTERESTED IN column: Show product title truncated to 20
   chars." No per-product data is available for every row in this
   screen's own list fetch (GET /api/profiles/:shop/profiles + GET
   /api/profiles/:shop/signals) — a customer's topProducts only gets
   fetched once their Journey panel is opened (a separate, per-click
   apiGet). The only "most interested in" value actually available
   for all rows up front is the pre-existing `topInterest` (from
   p.interests). Applied the requested 20-char truncation to that
   existing value instead of a nonexistent "product title" field,
   restyled to the requested fontSize 12/color #374151, and kept
   the signal-type sub-label (which the task's Change 3 description
   didn't mention removing) underneath it when a signal exists.
