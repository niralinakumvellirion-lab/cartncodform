4. apiSend() IN frontend/lib/api.js -- HOW IT BUILDS THE URL
====================================================================
BACKEND_URL is defined at the top of this file (line 2-3):

  export const BACKEND_URL =
    process.env.NEXT_PUBLIC_BACKEND_URL || 'http://localhost:4000';

So BACKEND_URL resolves to the NEXT_PUBLIC_BACKEND_URL environment
variable if it is set at build time (this is how Next.js exposes
client-side env vars -- it gets inlined into the bundle during
`next build`), falling back to 'http://localhost:4000' if that env
var is not set.

apiSend() itself (lines 100-139) builds the request URL like this
(line 101):

  export async function apiSend(path, method, body) {
    const url = `${BACKEND_URL}${path}`;
    ...
    const res = await fetchWithTimeout(url, {
      method,
      headers,
      body: JSON.stringify(body),
    }, method);
    ...
  }

YES -- it prepends BACKEND_URL directly onto the given path via
simple string template concatenation: `${BACKEND_URL}${path}`. There
is no separate base-path normalization, no leading-slash handling
beyond what the caller already supplies, and no other transformation
of the URL. (apiGet(), the sibling helper just above it at line 40-41,
builds its URL the identical way: `const url = \`${BACKEND_URL}${path}\`;`.)

Putting it together for the Send Now button in the editor modal, the
actual request URL at runtime is:

  `${BACKEND_URL}/api/push/send-store`

which resolves to (depending on environment):
  - production (Vercel): whatever NEXT_PUBLIC_BACKEND_URL is set to
    in the Vercel project's environment variables (expected to be the
    Render backend's URL, e.g. something like
    https://<render-service>.onrender.com/api/push/send-store) --

    out of scope for a read-only source-code audit.
  - local dev with NEXT_PUBLIC_BACKEND_URL unset: falls back to
    http://localhost:4000/api/push/send-store
