2. EXISTING-DOCUMENT SAFETY (Store.js enum removal)
---------------------------------------------------
Question: can removing the enum value reject a stored document that already has it?
Findings:
  - Reads never validate. Store.findOne() of a document with popup.styleId = 'full_takeover'
    loads normally.
  - PATCH /api/profiles/:shop/popup writes with Store.updateOne({$set}) and no runValidators
    (profiles.js documents this), so enum validation does not run on that write.
  - The one runValidators use in the backend (routes/automation.js findOneAndUpdate) does not
    touch popup/mobilePopup paths, so it cannot trip on the stale value.
  - Mongoose save() validates only modified paths, so an untouched stale styleId would not fail.
  So a shop that saved full_takeover can still load and re-save without a validation error.
What I did anyway:
  - Renderers already treat unknown ids as classic: admin getStyle() falls back to classic,
    resolveStyleId() returns classic, and ccf-push.js ccfResolveStyle() falls back to classic
    for ids not in CCF_KNOWN_STYLE_IDS.
  - Before this change, a PATCH carrying the old id would be silently dropped by isValidStyleId,
    leaving the stale value in the database forever. Now the route normalizes it to 'classic'
    (popup.styleId and mobilePopup.styleId), so it is overwritten on the shop's next save.
  - No data migration was run. Shops that never re-save keep the stale value in Mongo but render
    as Classic on the storefront and admin.
Behavior change for affected shops: a shop whose mobile style was Full Screen now renders
Classic on mobile (this is the requested fallback).
