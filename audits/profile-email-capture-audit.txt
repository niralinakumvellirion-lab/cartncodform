3. Is there any timestamp on when email was added?
====================================================================
No per-field timestamp exists for the email address specifically. The
only timestamps anywhere on the Profile document are document-level,
not field-level:
  67	  createdAt: { type: Date, default: Date.now },
  68	  updatedAt: { type: Date, default: Date.now },
These are plain schema-default fields -- NOT Mongoose's built-in
`{ timestamps: true }` schema option (which would auto-manage both on
every save). Confirmed by reading backend/services/profileService.js
(section below): updatedAt IS explicitly reset to `new Date()` on
every write that goes through applyToProfile() (used by every
upsertProfile() call, including the email-capture path from
discounts.js) -- so updatedAt DOES get refreshed at email-capture
time. However, updatedAt reflects "this profile was last written to
for ANY reason", not "this is when the email specifically was added"
-- any later, unrelated update (a new push token, a new order, a
signal-driven message log entry, etc.) will move updatedAt forward
again, permanently overwriting any trace of when the email itself was
actually captured.
createdAt is set once, at Profile.create() time (profileService.js
line 181), and only coincides with "when the email was added" if the
profile did not already exist before the email-capture call -- if the
same visitor already had a profile (e.g. from an earlier push
subscription or storefront session) before ever giving an email,
createdAt reflects that earlier, unrelated first-seen moment instead.
Net answer: no reliable timestamp of when an email was specifically
added exists anywhere in this schema or its current write paths.

NOTE -- 'popup' is not a valid value for channels.email.source's
declared schema enum:
=========================================================================
Profile.js's schema (section 1 above) declares:
  source: { type: String, enum: ['cod', 'form', 'checkout'] }
'popup' is not in that list. This write still succeeds and is not
silently corrected to some other value -- confirmed by reading how
upsertProfile()/applyToProfile() actually applies the `updates` object
in profileService.js: it goes through
`Profile.findOneAndUpdate({...}, update, { new: true })` (line 144)
with no `runValidators: true` option. Mongoose does NOT run schema
validators (including enum checks) on findOneAndUpdate/update-family
calls unless runValidators is explicitly passed -- validators only run
automatically on .save()/.create(). So this write bypasses the enum
constraint entirely: a real Profile document can end up with
channels.email.source === 'popup' in the live database even though the
schema's own declared enum says only 'cod'/'form'/'checkout' are
allowed. This is a genuine mismatch between the schema's stated
contract and what the actual code paths write -- not something this
audit was asked to fix (read-only task), flagged here since it was
directly observed while tracing this exact code path.

Mechanics for `channels.email.address`/`channels.email.source`
specifically:
  1. splitUpdates() (lines 49-60) splits the raw `updates` object the
     caller passed in (e.g. discounts.js's
     `{ 'channels.email.address': email, 'channels.email.source':
     'popup', lastSeenAt: new Date() }`) into a plain dot-notation
     `set` bag (any key not starting with `$`) and a separate
     `operators` bag (any key starting with `$`, e.g. a caller-supplied
     `$inc`). Since discounts.js's call passes plain dot-notation keys
     (no `$`-prefixed operators), both `channels.email.address` and
     `channels.email.source` land in `set` verbatim, unchanged.
  2. applyToProfile() merges that `set` bag directly into
     `update.$set` (line 132), alongside `updatedAt: new Date()` --
     so the final Mongo command ends up containing
     `$set: { 'channels.email.address': <email>, 'channels.email.
     source': 'popup', lastSeenAt: <now>, updatedAt: <now> }`.
  3. This whole `update` object is applied via a single
     `Profile.findOneAndUpdate({ _id, shopDomain }, update, { new:
     true })` call (line 144) -- a plain MongoDB $set on the given
     dot-notation paths, with NO transformation, validation
     (runValidators not set, per the NOTE above), or normalization
     applied to either value by profileService.js itself. Whatever
     string the CALLER passes for channels.email.address or
     channels.email.source is written to MongoDB exactly as given.

Separately (NOT the same field): the EMAIL VALUE the caller passes as
part of the `identifiers` argument (`{ email: ... }`, the FIRST
parameter to upsertProfile(), used for identity resolution) goes
through a completely different path -- cleanIdentifiers() (lines
35-46) trims it and lowercases it (`if (key === 'email') val =
val.toLowerCase();`, line 42) before it's used to search for/create a
profile and, via addToSetForIds() (lines 117-124), $addToSet'd onto
identifiers.emails[]. This lowercasing/trimming does NOT carry over to
channels.email.address, which is a totally separate value supplied by
the caller through the second (`updates`) argument and written
verbatim as shown above -- so identifiers.emails[] and
channels.email.address can end up holding differently-cased (or
otherwise differently-formatted) representations of what was intended
to be the same email address, since they are populated via two
independent code paths with different normalization rules.
