--- How is the date filter implemented? ---
Client-side only, no server involvement beyond what params are sent
in the fetch URLs:
  - `dateFilter` state (default '7d'), set by 4 pill buttons (Today /
    Yesterday / Last 7 days / Last 30 days -- DATE_FILTERS, lines
    91-96) rendered in "SECTION 1 — Date filter bar" (lines 284-313).
  - `getDateRange(f)` (module-scope function, lines 132-143) converts
    the selected key into concrete `{ from, to }` ISO-string
    boundaries entirely in the browser (new Date() math, no API call)
    -- 'today' = midnight today to now; 'yesterday' = midnight
    yesterday to 23:59:59.999 yesterday; '7d'/'30d' = N days back
    (current time-of-day) to now.
  - Those `from`/`to` strings are then passed as query params on both
    fetch URLs in the combined effect (section above) -- the actual
    date filtering happens server-side, inside the /api/activity and
    /api/profiles/:shop/today-stats handlers (the latter shown in
    full in section 2 below), which apply them as MongoDB
    `$gte`/`$lte` range queries.
  - Changing `dateFilter` re-runs the combined effect (it's a
    dependency), which re-fetches both endpoints with the new range.
    There is no debounce -- each button click fires an immediate
    fetch (acceptable here since only 4 discrete buttons exist, not a
    free-text input).

--- What data does it currently return? ---
A flat JSON object with exactly 5 integer counts, all computed fresh
on every request (no caching layer) via 5 parallel Mongo
queries/aggregations:
  - pushSent: ScheduledJob rows for this shop with channel:'push',
    status:'sent', sentAt within [from, to].
  - emailsSent: count of Profile.messages subdocuments (across every
    profile in the shop) with channel:'email' and sentAt within
    [from, to] (via $unwind + $match + $count).
  - popupsShown: StorefrontEvent rows of type 'push_prompt_shown'
    within [from, to].
  - emailsCaptured: Profile documents whose channels.email.capturedAt
    falls within [from, to] (this field was added in an earlier task
    this session, audits/email-capturedat-audit.txt).
  - pushSubscribers: Profile documents with channels.push.subscribed
    === true -- NOT date-ranged (queried without any ts/sentAt/
    capturedAt filter at all, so this one is always an ALL-TIME total,
    regardless of the from/to the caller passed -- the only one of the
    5 stats that ignores the date filter entirely, by design per its
    own inline comment "Total push subscribers (all time)").
`from`/`to` default to now minus 7 days / now when the query params
are omitted. No pagination, no per-row detail -- purely aggregate
counts, matching what Today.jsx's 5 stat tiles need (section 1 above).

324	/**
325	 * POST /api/push/send-journey
326	 * Body: { profileId, title, body, url }
327	 * Sends a one-off push to a single customer from the Journey screen.
328	 *
329	 * There is no :shopDomain in this route's path, so requireStoreOwner (which
330	 * compares req.shopDomain to req.params.shopDomain) doesn't apply here — the
331	 * route uses requireAuth only and scopes the Profile lookup by the verified
332	 * shopDomain from the session token itself (never a client-supplied value),
333	 * which is what actually prevents one shop from pushing to another shop's
334	 * customer via a guessed/leaked profileId.
335	 */
336	async function sendJourneyPush(shopDomain, { profileId, title, body, url }) {
337	  const Profile = require('../models/Profile');
338
339	  if (!profileId || !title || !body) {
340	    return { status: 400, payload: { error: 'profileId, title and body are required' } };
341	  }
342
343	  const shop = String(shopDomain || '').trim().toLowerCase();
344	  const profile = await Profile.findOne({ _id: profileId, shopDomain: shop });
345
346	  if (!profile || !profile.channels?.push?.subscribed) {
347	    return { status: 400, payload: { error: 'No push subscription' } };
348	  }

351	  const result = await sendPushToCustomers(

353	  );
354
355	  if (!result.success) {
356	    return { status: 500, payload: { success: false, error: result.error } };

358	  return { status: 200, payload: result };

--- What does it accept and do? ---
Accepts (POST body): { profileId, title, body, url }. All 3 of
profileId/title/body are required (400 if any is missing); `url` is
optional (passed straight through to sendPushToCustomers(), which
itself defaults to `https://${shopDomain}` when falsy -- per
pushNotification.js's own fallback, not reproduced here since this
task only asked for push.js's handler).

Behavior:
  1. Looks up the target Profile by `_id` AND `shopDomain` together
     (the shopDomain comes from the VERIFIED session token,
     `req.shopDomain`, not from the request body -- this is the IDOR
     protection the doc comment describes, since this route has no
     `:shopDomain` path segment for requireStoreOwner to check
     against).
  2. Rejects (400 "No push subscription") if no profile matches OR
     the matched profile's channels.push.subscribed is not true --
     i.e. even a profileId that legitimately belongs to a DIFFERENT
     shop, or a real profile that simply isn't push-subscribed, both
     produce the same 400.
  3. Takes the profile's first cartToken (identifiers.cartTokens[0],
     if any) to pass to sendPushToCustomers() as its targeting
     cartToken.
  4. Calls sendPushToCustomers(shop, title, body, url, null, false,
     cartToken) -- imageUrl hardcoded to null (no image support on
     this send path) and mobileOnly hardcoded to false.
  5. Returns 500 with `{success:false, error}` if the send itself
     fails (result.success falsy); otherwise 200 with the raw result
     object from sendPushToCustomers() (whatever shape that function
     returns -- e.g. {success, sent, tokensFound, ...} per earlier
     audits this session, audits/push-query-audit.txt).
Notably: this handler does NOT call recordProfileMessage() (the
helper server.js's poller uses to log a message onto
Profile.messages after a brain-scheduled send) -- a journey-composer
push sent through this endpoint does not appear to get logged into
the customer's own message history the same way an automated/brain
send does. Not confirmed further since tracing recordProfileMessage's
other call sites was outside this task's scope; noted as an
observation from reading this handler in full.

Notes: `{ timestamps: true }` (line 42) means Mongoose auto-manages
`createdAt`/`updatedAt` on every save -- this is the field the
today-stats endpoint's own comment (section 2) explicitly avoids using
for "push sent" counting, in favor of the separately-managed `sentAt`
(set once, manually, only at actual send time -- never touched by
Mongoose's automatic timestamp machinery). Two partial unique indexes
enforce de-duplication rules (one for legacy rule-based jobs keyed by
cartToken+stepIndex, one for brain-scheduled jobs keyed by
profileId+signalType) -- both scoped to `status` via
partialFilterExpression so a cancelled/failed/skipped job doesn't
block a fresh one from being created for the same target.
