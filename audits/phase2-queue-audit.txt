DEVIATION 1 - stats row sourced via 4 parallel calls to the SAME list
endpoint, since no aggregate counts endpoint exists
=========================================================================
Part D's spec says: "STATS ROW (4 small cards): Pending | Sent |
Failed | Cancelled — Show counts from total query." But Part A's given
GET /:shopDomain/queue endpoint (presented as the complete, final
backend deliverable for this task — no other backend file/endpoint was
named anywhere in this task) only ever returns ONE `total`, scoped to
whatever single `status` value the CALLER requested (`all`, `pending`,
`sent`, etc.) — there is no field anywhere in its response that breaks
total down by all 4/5 statuses simultaneously. A stats row showing 4
different counts AT ONCE cannot be built from one call to this
endpoint.
Implemented by calling the same endpoint 4 times in parallel (once per
status: pending/sent/failed/cancelled), reading only `.total` from
each response and discarding the (also-fetched, profile-enriched) job
rows each call returns. This works and stays entirely within the given
backend contract, but is genuinely wasteful — each of the 4 calls also
does the full job-list query, the `.skip/.limit(20)` pagination work,
and a second Profile.find() enrichment JOIN, none of which the stats
row uses. A more efficient fix would be a small aggregate (e.g. a
`$group` by status, or a dedicated `/api/queue/:shop/stats` endpoint)
added to the backend — out of scope here since Part A's code was given
as complete and this task's file list never mentioned adding to or
changing it further. Flagging this as a known inefficiency for a
future task to address, not a bug in what was built.

DEVIATION 2 - status filter resets page to 0 on change
=========================================================================
Not explicitly named in the task's fetch-logic spec ("Fetch on mount +
when statusFilter or page changes"), but added a small effect
resetting `page` to 0 whenever `statusFilter` changes. Without it,
switching from a filter with many pages (e.g. "All") to one with fewer
matching rows (e.g. "Cancelled") while sitting on, say, page 3 would
silently request an out-of-range page and show an empty list with a
confusing "Showing 61-80 of 12" pagination line, with no way back to
page 0 except manually clicking Previous repeatedly. A small,
defensive UX fix consistent with how a filter+pagination combination
is expected to behave; does not change the given backend contract or
any other part of the fetch logic.
