STEP 2 — aiService.js: generateEmailCopy
---------------------------------------------
The given implementation called `buildCopyPrompt(signal, voice,
profileData)` and `callLLM(emailPrompt)` — neither function exists
anywhere in aiService.js (verified: the only helpers are hasKey,
anthropic, parseJsonBlock, ruleBasedNarrative). As given, the AI branch
would throw a ReferenceError on every call once an LLM key was set,
silently caught by the surrounding try/catch and always falling through
to the template — i.e. the AI path would never actually run, defeating
the feature's own stated purpose. Rewired it to the real helpers already
used by generateCopy() in this same file: anthropic() (the raw-fetch
Anthropic wrapper) + parseJsonBlock(), with a prompt built inline in the
same style/shape as generateCopy()'s own prompt.

Second, more significant fix: the given generateEmailCopy() never cached
anything — every call with an LLM key would hit the Anthropic API
directly. Since this function is invoked once per due job inside the
poller's per-job loop (one job per customer), that means one live LLM
call per customer per signal, every time — which is exactly what
CLAUDE.md's "LLM calls ... are cached in Mongo, and are never made
per-customer at send time" rule forbids, and exactly what generateCopy()
above already avoids via CopyCache (whose own doc-comment literally says
"One LLM call per product per signal per channel per voice, not per
customer"). Added the same CopyCache-backed caching generateCopy() uses,
keyed by (shopDomain, signalType, null-productId, 'email-marketing',
voiceHash) — the 'email-marketing' channel tag keeps this cache
namespace distinct from generateCopy()'s own 'email' entries, which serve
a different prompt/template. This required adding a `shopDomain`
parameter to the function signature (the given signature was
`(signal, voice, profileData)` — shopDomain wasn't there, and without it
there's no way to build a per-shop cache key, which would also mean two
shops with byte-identical `voice` could silently share one shop's
AI-generated copy with another shop's customers). Updated server.js's
call site to pass job.shopDomain accordingly.

STEP 3 — server.js: poller sends email after push
-------------------------------------------------------
Added EMAIL_SIGNAL_TYPES (hoisted to module scope rather than
re-allocated every loop iteration) and the email-send block, placed
inside the existing push-success branch, right after the existing hygiene
calls. Three fixes against the given snippet:
  - Given code re-required `./models/Store` and `./models/Profile` and
    ran a second `Store.findOne({shopDomain}, 'voice')` query — both
    modules are already imported at the top of server.js, and `voice`
    (derived from the SAME shopDomain) is already computed a few lines
    above this block for the push-copy generateCopy() call. Reused the
    existing `Profile` import and `voice` variable instead of
    re-requiring/re-querying.
  - Given code pushed `{channel:'email', signalType: job.signalType,
    sentAt, status:'sent', payload:{subject,body}}` onto
    profile.messages. Profile.messages' actual subdocument schema (in
    models/Profile.js) has fields `channel`, `type`, `sentAt`, `outcome`,
    `jobId` — no `signalType`, `status`, or `payload` fields exist.
    Mongoose's default strict mode silently drops unrecognized keys on
    save, so as given this push would have saved a message with `type`
    unset. brain.js's own 6-hour per-signal cooldown check reads
    `m.type === s.type` — with `type` never set, this new email entry
    would never register with that cooldown check on future brain runs.
    Fixed the field names to `type`/`outcome` (matching the real schema),
    dropped the unpersistable `payload` field, added `jobId: job._id` to
    match recordProfileMessage()'s existing shape, and added `$slice:
    -20` to cap the array (recordProfileMessage(), a few lines above,
    already does this — the given snippet didn't, which would let the
    array grow unbounded for shops running this automation for a long
    time).
  - Added a `job.profileId` guard around the whole block (legacy
    rule-scheduled jobs have profileId=null and no Profile document to
    look anything up on — the given snippet would have run
    Profile.findById(null), which Mongoose resolves to null without
    querying, so not a crash, just wasted work every tick for those
    jobs).
Everything else (24h dedup via profile.messages, emailAddr resolution
order, email-errors-never-block-push try/catch) implemented as given.
