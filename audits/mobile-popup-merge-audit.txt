DEVIATION FROM THE LITERAL TASK - verified, not guessed
=========================================================================
The task's given FIX 1 code introduced a new, hand-written
`MOBILE_FIELDS` constant (19 entries) instead of reusing the file's
existing `POPUP_FIELDS` constant (20 entries, already defined at the
top of this same route file, lines 384-391, and already the single
source of truth the desktop popup.* loop uses). Comparing the two
field-by-field, the given MOBILE_FIELDS list was wrong in two ways:

1. It was MISSING 4 fields that POPUP_FIELDS has: borderRadius,
   subtext, brandName, textAlign. These are not desktop-only -- a
   prior audit this session (audits/settings-slow-save-audit.txt,
   section 3) grepped every `activePopup.<field>` reference in
   Settings.jsx and confirmed the customizer UI reads/writes ALL of
   these through the SAME shared `activePopup`/`setActivePopup`
   binding used for both the desktop and mobile tabs (`const
   activePopup = popupDevice === 'desktop' ? popup : mobilePopup`).
   That means a merchant editing, say, the mobile tab's text alignment
   or corner radius sends `mobilePopup.textAlign` /
   `mobilePopup.borderRadius` in the PATCH body exactly like the
   desktop tab does for `popup.textAlign` / `popup.borderRadius` --
   had the given MOBILE_FIELDS list been used verbatim, those 4
   fields would have been silently dropped from `set` on every mobile
   save (the `if (Object.prototype.hasOwnProperty...)` check would
   simply never match them), meaning changes to the mobile popup's
   text alignment, border radius, subtext, or brand name would appear
   to save successfully (200 OK) but never actually persist -- a
   regression introduced by the task's own given field list, on the
   very feature (mobile tab parity) this task exists to support.

2. It INCLUDED 2 fields that don't belong to the popup feature at all:
   `textPosition` and `offerHeadline`. Grepped across the whole repo:
   both terms appear only in the DISCOUNT feature's files
   (backend/routes/discounts.js, backend/routes/proxy.js,
   backend/models/DiscountConfig.js, frontend/app/admin/screens/
   Discounts.jsx, and the liquid extension's discount-widget code) --
   never once in backend/routes/profiles.js or
   frontend/app/admin/screens/Settings.jsx's popup-config code paths.
   Including them in MOBILE_FIELDS would have been harmless (the
   frontend never sends `mobilePopup.textPosition` or
   `mobilePopup.offerHeadline`, so those two lines of the loop would
   just never match), but it signals the given list was adapted from
   the wrong feature rather than checked against this one.

Given both issues, I used the existing `POPUP_FIELDS` constant instead
of introducing a new, separately-maintained (and, as shown, incorrect)
list. This keeps a single source of truth for "what fields does the
popup config support" shared by desktop and mobile, matching the
file's own design intent (the "same fields, different state" comment
already present in Settings.jsx) and closing off a whole class of
future bugs where the two lists could drift apart again. Net effect on
the requested field set: SUPERSET of what the task asked for (includes
theme, customTitle, showBranding, overlayOpacity in addition to the
17 the task's list and the frontend's JSX both reference), matching
exactly what desktop popup.* already accepts -- nothing the task asked
to be droppable was dropped, and nothing outside the real popup feature
was added.

INCIDENT DURING THIS TASK: automated `git push origin main` hung
=========================================================================
After committing (95c7f76), two consecutive `git push origin main`
attempts hung indefinitely with zero output (stdout and stderr both
empty), including a retry with `GIT_TERMINAL_PROMPT=0` set (which
should force git to fail fast instead of blocking on ITS OWN terminal
prompt -- it still hung, pointing to something outside git's own
prompt handling). Both hung processes were stopped manually rather than
left running. `git config --get-all credential.helper` showed two
helpers configured: `manager` (Git Credential Manager, which can invoke
an interactive/browser-based auth flow) and `wincred`. The most likely
explanation is GCM attempting an interactive re-auth via a GUI/browser
prompt that a non-interactive sandboxed shell can neither see nor
dismiss -- consistent with previous `git push` calls earlier in this
same session completing quickly with no such issue, suggesting a
credential/token state change partway through this session rather than
a persistent environment problem.
Per the operating guidance for exactly this situation (suggest the user
run an interactive command themselves via `! <command>`), I asked the
user to run `git push origin main` directly so they could complete
whatever prompt appeared, rather than retrying indefinitely or
attempting to alter credential/security configuration myself (which is
out of scope for an automated fix). The user ran it in their own
session; `git status` afterward showed `main` even with `origin/main`
(no longer "ahead"), confirming the push succeeded. The `vercel --prod`
deploy and this self-audit were completed immediately after.
