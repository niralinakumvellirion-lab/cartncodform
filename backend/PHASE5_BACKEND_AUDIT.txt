5. DEVIATIONS FROM THE LITERAL SPEC  (all deliberate)
================================================================================

(a) automationEngine.js — `sub.customerId` -> `sub?.customerId`
    The spec's ScheduledJob.create still reads `sub.customerId`, but `sub` is
    now null on the email branch (and only assigned inside the push branch).
    `sub?.customerId` is required to avoid a TypeError on email steps.
    Behaviour for push steps is unchanged (sub is a real doc there).

(b) automationEngine.js — per-channel precheck placed INSIDE the step loop
    (after runAt), not as a single rule-level gate.
    Consequence: a rule mixing push + email steps no longer aborts wholesale
    when only one channel has no recipient — each step is evaluated on its own
    channel, and the delay timeline for subsequent steps still advances past a
    skipped step. This matches the spec's stated intent ("skip just this
    step").
    Also: scheduleCartAbandonJobs does NOT populate payload.subject (spec said
    "no other changes to scheduling logic"). Automated email steps therefore
    send with email.js's default subject; only /send-email-test passes a
    per-step subject through. If per-step subjects on automated sends are
    wanted later, add `subject: step.subject` to the payload here.

(c) server.js — push branch kept richer than the spec's replacement snippet:
      * kept the outer try/catch (spec's snippet dropped it) — a thrown error
        still marks the job 'failed' instead of crashing the poller tick.
      * kept `urlWithJob` with `?ccf_job=<jobId>` (spec's snippet dropped it)
        — this is the revenue-attribution mechanism; dropping it would break
        order attribution for automation pushes.
      * kept the 9-arg sendPushToCustomers call incl. the `false` flag and
        `job.customerId || null` fallback target (spec's snippet used 7 args).
    The email branch is implemented exactly as specified. Also dropped the
    spec snippet's unused `Store.findOne` / no-op cartUrl ternary.

(d) routes/push.js /send-email-test — IDOR (403) check placed BEFORE the DB
    lookup (spec listed the 404 first). Done so an unauthorized caller cannot
    probe which carts have a customer-with-email by status code, and to match
    the guard order used by the other protected routes in this file.
